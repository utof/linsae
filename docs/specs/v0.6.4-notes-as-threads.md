# v0.6.4 — notes-as-threads — spec

**Branch:** `v0.6.4/notes-as-threads` · **Direction doc:** `docs/canvas-vision.md` §Threads + nested
canvases (`:156-163`), principles 1/3/8 · **Builds on:** v0.2 youtube-annotation (the `comment-on`
thread primitive + `ThreadView`), v0.6 pdf-slim-slice (PDF reader in a right-dock content pane +
`source_kind='pdf'` excerpts), v0.6.2 dock-shell (ordered dock panes + `dockStore`).

## Context

linsae is a single rolling feed where **everything is a note**. v0.2 introduced the threading
primitive: a YouTube video *is* a note (`type='source'`, `source_kind='youtube'`); its annotations
are ordinary notes linked back with `links(edge_type='comment-on')` (frozen `0001_init.sql:26-32`;
`setCommentOnEdge` in `src/main/db/queries/links.ts`). `ThreadView`
(`src/renderer/src/thread/ThreadView.tsx`) renders that thread two ways — **video-order** (the rail,
`rail-layout.ts`) and **capture-order** (chronological) — with the `<webview>` player pinned
*inside* the view.

v0.6 added PDFs, but **a PDF is not yet a note**: it is a `pdf_documents` row
(`0007_pdf_documents.sql`) opened in a right-dock pane (`src/renderer/src/pdf/PdfReader.tsx`);
selecting text creates a `source_kind='pdf'` note that is **placed on the canvas** via ghost
placement, with **no `comment-on` link and no feed/thread presence**. So PDFs are effectively
ephemeral: open → excerpt-to-canvas → close.

v0.6.4 closes that gap and generalizes the thread. It is the first concrete cut of
`canvas-vision.md` §Threads — *"Any note can become a thread (its `comment-on` children — same
mechanism as YouTube annotations)"* (`:157`) — scoped to the **chronological** rendering only
(the nested-canvas rendering is deferred; see Non-goals).

## Goals

- **A PDF persists in the feed as a media note** (mirror of the YouTube video-note): importing a PDF
  creates a `type='source'`, `source_kind='pdf'` note that renders as a feed card (`PdfFeedNote`,
  sibling of `MediaFeedNote`).
- **Open the thread for a PDF** → its excerpts as a **chronological** list + composer. Unlike
  YouTube, **no second (page-order) view** — one chronological rendering only (user decision).
- **Every note is a thread.** Any note — plain `claim`/`question`, not just media — exposes an
  "open thread" affordance → its `comment-on` children, chronological, with a composer that posts
  more children.
- **Media surfaces are detachable dock panes.** The PDF reader (already a dock pane) and the YouTube
  player (today pinned inside `ThreadView`) both live in the **right dock**, decoupled from the
  center stage. While media is docked you can flip the center `feed ⇄ canvas` and the media stays
  open — so an excerpt/annotation can be read chronologically (thread) **or** placed spatially
  (canvas) without closing the document. This preserves v0.6's drag-to-canvas untouched.
- **No schema migration.** `notes.source_kind` already accepts `'pdf'`; `PdfLocator` exists;
  `links.commentsOf(slug)` is already slug-generic. The only data-model change is an **additive
  type/Zod widening** (PdfLocator excerpt-fields → optional), persisted in the existing JSON
  `source_locator` TEXT column.

## Non-goals (v0.6.4)

- **Thread as a third stage view.** Thread is a **sub-view of the feed**, not a peer of
  `feed`/`canvas` (user decision; preserves `canvas-vision.md` principle 8 "two peer full-window
  stage views"). The `feed | canvas` segmented control (`WindowFrame.tsx:8`) is **unchanged** — no
  third segment, no `mod+3`.
- **Per-note nested canvas** (`canvas_id = note.id`, the vision's `:158-160` "open the note *as* a
  canvas"). Excerpts continue to land on the **root** canvas (`canvas_id='root'`) as in v0.6. This
  defers the slug↔id seam (principle 3, `:40-42`).
- **Satellite / dot rendering** of a note's children on the current canvas (the other vision
  rendering, `:158-159`).
- **PDF page-order rail** for the PDF thread (chronological only).
- **PDF annotation (Stage 2)**, image-region excerpts, multi-document tabs, re-open-at-source
  navigation — all remain sequenced after, per `docs/canvas-vision.md` §PDFs.
- **New FTS wiring.** Excerpt/child bodies are indexed by the existing `notes_fts` triggers for free.

## The model (one mechanism)

```
A "thread" = a root note  +  its comment-on children.

  root note ──comment-on──< child, child, child …   (links: from=child.id, to=root.slug)

Three renderings of the SAME children, none of them new data:
  • THREAD  — chronological list + composer        (new; generic; this milestone)
  • CANVAS  — children placed spatially on 'root'  (exists: v0.6 excerpt-place)
  • FEED    — global chronological stream          (exists: v0.1)

A "media note" = a root note whose source_kind binds it to an external surface:
  • youtube → player (webview)   ┐ both render in the RIGHT DOCK as a detachable
  • pdf     → reader (pdf.js)    ┘ content pane, independent of the center stage.

Center stage stays `feed | canvas`. "Thread" is a drill-in STATE of the feed surface
(root + children + composer, with a back-out to the global feed).
```

**Today's structure is the opposite — and relocating it is batch 1.** Currently `ThreadView` is
opened at the **body-row** level and *replaces the whole row, unmounting both docks*
(`App.tsx:873-1093`: `{threadNoteId ? <ThreadView/> : <><DockHost left/><main>feed|canvas</main>
<DockHost right/></>}`; the right dock that holds the PDF reader lives only in the non-thread branch
at `App.tsx:1086`). So as shipped, opening a thread **closes the docked reader** — which makes the
core goal (read chronologically *or* place spatially without closing the document) impossible. The
fix is structural and is the **first batch**: move the `threadNoteId ?` branch *inside* `<main>` so
the thread becomes a sub-state of the feed view and the docks stay mounted:

```
<> <DockHost side="left"/>
   <main>{ view === 'canvas' ? <CanvasStage/>
           : threadNoteId   ? <ThreadView root=…/>   // thread = feed sub-state
           :                  <Feed/> }</main>
   <DockHost side="right"/> </>
```

`threadNoteId` then persists across the `feed⇄canvas` toggle (it only changes what the *feed* view
renders), so toggling to canvas and back keeps the thread open and the reader docked. This is a real
behavior change (not a no-op extraction) and is sequenced before the PDF-thread batches.

## Data model (no migration — reuse + one additive type widening)

### `notes` / `links` — frozen, unchanged
- **PDF source note:** `type='source'`, `source_kind='pdf'`,
  `source_locator = {"media":"pdf","pdf_id":"<uuid>"}` (document-level locator — **no** page/rect/
  quote). **`body=''`** so the slug falls back to the note's uuid (`save-note.ts:149`), exactly as
  the YouTube video-note does (`App.tsx:475`). This is **collision-proof** — two PDFs with the same
  `/Title` or filename fallback would otherwise both slug to the same value and the second
  `saveNote` would throw the duplicate-slug guard (`save-note.ts:160-165`). The display title comes
  from `pdf_documents.title` (read by `PdfFeedNote`), never from the body — mirroring how
  `MediaFeedNote` reads `video_sources.title`.
- **PDF excerpt note (a child):** **`type='claim'`** (v0.6 created excerpts as `type='source'` —
  that was wrong for a comment and is corrected here, batch 4), `source_kind='pdf'`,
  `source_locator = {"media":"pdf","pdf_id","page","rect","quote","prefix","suffix",textStart?,textEnd?}`
  (the full v0.6 hybrid anchor), linked to the PDF source note via
  `links(from_note_id=child.id, to_slug=pdfSourceNote.slug, edge_type='comment-on')`.
- **Plain-note thread:** identical mechanism — a child links `comment-on` to the root note's slug.
  The root carries no `source_kind`.

**New resolver query** (`src/main/db/queries/notes.ts` + a `notes:bySourceId` IPC, or folded into
the PDF family): *"the live source note whose `json_extract(source_locator,'$.pdf_id') = ?`"* →
returns `{id, slug} | null`. Needed for (a) import idempotency — don't create a second source note
for an already-imported `pdf_id` — and (b) the excerpt's `commentOn` target slug. No such query
exists today (`grep json_extract|pdf_id src/main` is empty); it is small and additive.

**Pre-v0.6.4 excerpts** in the dogfood vault are `type='source'` + a *full* (page-bearing) locator.
The `PdfFeedNote` discriminator (below) requires a **document-level** locator (`page` absent), so
those legacy rows fall through to the normal text-bubble render — correct, not a card. No data
migration; a one-time normalization to `type='claim'` is optional (batch 4 only changes *new*
excerpts).

This reuses the YouTube precedent verbatim (`0001_init.sql:26-32`, `setCommentOnEdge`,
`commentsForVideo`). Slugs are immutable after create (save-note "preserves slug" on update), so
slug-targeted `comment-on` edges are stable — the principle-3 seam only bites for the **deferred**
nested-canvas (`canvas_id` = id), not here.

### `pdf_documents` — frozen, unchanged
Stays the document-metadata table (the PDF analog of `video_sources`): `id`, `sha256`, `base_path`,
`title`, `page_count`, … (`0007_pdf_documents.sql`). The note↔document join is
`source_locator.pdf_id → pdf_documents.id`. **One PDF source note per live `pdf_documents` row**
(dedup at import; see Flows).

### `PdfLocator` — additive type/Zod widening (the only data-model change)
A document-level anchor needs only `{media:'pdf', pdf_id}`. So the **excerpt-only fields become
optional** (`src/shared/types.ts:26-36`), mirroring how `YoutubeLocator.t` is optional for the
video-note and present on comments:

```ts
export interface PdfLocator {
  media: 'pdf'
  pdf_id: string
  page?: number                                 // was required — excerpt-only
  rect?: [number, number, number, number]       // excerpt-only
  quote?: string                                 // excerpt-only
  prefix?: string                                // excerpt-only
  suffix?: string                                // excerpt-only
  textStart?: number
  textEnd?: number
}
```

`PdfLocatorSchema` (`src/shared/zod-schemas.ts`) mirrors this (those fields `.optional()`); the
`SourceLocator` `z.discriminatedUnion('media', …)` is **kept** (still one `pdf` member — the
discriminant is unaffected). The excerpt-creation path (`useExcerptCapture`) still writes all
fields; the re-anchor order (quote→position→rect) already guards on presence, so optionality is
safe. **Trade-off (reviewer check):** this slightly weakens excerpt validation (a malformed excerpt
locator could pass Zod). Mitigation: excerpts are constructed internally, never user-supplied JSON;
the alternative (a second `pdf` union member discriminated by a `kind` field, requiring a plain
`z.union`) is heavier and loses discriminated-union ergonomics — rejected here, ADR records it.

## Surfaces & components

### `PdfFeedNote` — a PDF in the feed (new; sibling of `MediaFeedNote`)
Renders for a **document-level** PDF locator:
`note.source_kind === 'pdf' && note.source_locator?.media === 'pdf' && note.source_locator.page == null`.
The `page == null` test is load-bearing: today's excerpts are *also* `type='source' + source_kind=
'pdf'` (`App.tsx:248`) but carry a `page` (`useExcerptCapture.ts:75`), so a `type`/`source_kind`-only
check (like the YouTube branch at `NoteBubble.tsx:242-245`) would mis-render every excerpt as a
document card. `NoteBubble.tsx:242` gains this `pdf` branch beside the `youtube` `isSource` branch.
Card content (reuse `MediaFeedNote`
structure / v21 visual language, no new tokens): document title; `page_count` chip; child-note count
+ open-question count (amber, reusing v0.1 question/status semantics); an accent **"open notes"**
button → opens the thread (and the docked reader). A small page-1 thumbnail is **optional/deferred**
(pdf.js render in the feed is a perf cost; first cut may ship a generic doc glyph — plan decides).

### Generic `ThreadView` (chronological) — extracted
Today's `ThreadView` is YouTube-shaped. Extract the **chronological** core (it already exists as the
`'capture'` sort path) into a generic thread surface that takes a **root note** and renders:
back-bar (title) → root header → its `comment-on` children chronologically → pinned composer.
Source-specific extras layer on top:
- **plain note:** generic only.
- **pdf:** generic + the docked reader (right dock) is opened; thread is chronological-only.
- **youtube:** generic + the **video-order rail + sort toggle** (existing `Rail.tsx`/`rail-layout.ts`
  kept) + the docked player.

The data hooks `useThreadNotes` / `links.commentsOf` are already generic (`useThreadNotes.ts:104`
derives `t=null` for non-youtube locators, so a PDF/plain thread renders as the all-anchorless
capture-order list); the rename is `commentsForVideo` → `commentsForNote` (and its call sites at
`ipc/notes.ts:31,115`, `MediaFeedNote.tsx:75`, `useThreadNotes.ts:93` — landed in **one** batch so
`knip`/`tsc` stay green). But three pieces are **new work, not free reuse** (do not under-budget):
- **A simple generic composer.** The shipped `ThreadComposer.tsx` (~405 lines) is deeply
  YouTube-specific — timestamp chip, freeze/resume (`composer-chip.ts`), `Camera` capture, frame
  chip. The generic/PDF thread needs a **new minimal composer**: Enter-sends, `commentOn = root.slug`
  target, no chip/camera. The YouTube composer stays as the youtube specialization.
- **A root header.** There is no analog today — the YouTube thread fills that slot with the *player*
  (`ThreadView.tsx:516-559`), not the root note. The generic thread renders the **root note's card**
  (a `NoteBubble`) at the top.
- **Wikilink navigation** in thread cards — `Rail`'s in-card handler is a NOOP (`Rail.tsx:166-167`);
  the generic thread wires real wikilink resolution (reuse the feed's handler).

### Detachable media dock pane
- **PDF:** already a right-dock content pane (`Pane.kind='content'`, v0.6 §6) — reused as-is.
- **YouTube:** the player is a `<webview>` (ADR 0016 superseded the iframe) singleton attached to
  `document.body` as a `position:fixed` overlay that is **synced to a placeholder `<div>` each
  frame** and is **never re-parented** (`playerSingleton.ts:215-283`; the electron#9529/#7700
  teardown is already designed around — header comment `:8-22`). So "lifting" the player out of
  `ThreadView` reduces to **moving the placeholder `<div>` into a right-dock content pane** and
  pointing `host` at it; the auth cookie survives via `partition="persist:yt-player"`
  (`playerSingleton.ts:229`, ADR 0017), independent of DOM lifecycle. This makes the lift **low
  risk** and **cleanly separable** — batch 1's extraction does *not* require it; YouTube keeps its
  pinned-in-thread placeholder until batch 5, which simply relocates that placeholder.

### "Open thread" affordance on every `NoteBubble`
Each note exposes an affordance to open its thread/comment-section (e.g. a comment glyph with child
count; source cards already have "open notes"). Clicking drills the feed into that note's thread.

## Key flows

### Import a PDF → feed note
`File→Open`/picker → `pdf:import` (existing: bytes → sha256 → dedup → `pdf_documents` row, returns
`{pdfId,…}`). **New, in the renderer** (mirroring `handlePasteText`'s YouTube path at
`App.tsx:470-499`, *not* inside `pdf:import` — the PDF IPC family has no `NotesDir` and `saveNote`
needs one, `ipc/pdf.ts:16`): query the new `pdf_id` resolver; if no live source note exists for that
`pdf_id`, `api.notes.create('', 'source', {source_kind:'pdf', source_locator:{media:'pdf',pdf_id}})`
(empty body → uuid slug; see Data model). It appears in the feed as `PdfFeedNote`. Re-importing the
same bytes reuses the existing document (sha dedup) **and** its source note (the resolver), so the
flow is idempotent.

### Open a thread (any note)
Click "open thread"/"open notes" → feed drills into the thread for that root note (records access,
`recordAccess`). For a media note, the corresponding reader/player opens in the right dock. A
back-out returns to the global feed. Toggling center to `canvas` (media stays docked) and back keeps
the thread.

### Excerpt → comment-on child (unifies thread + canvas)
Select text in the docked PDF reader → arm excerpt (existing `useExcerptCapture` + `excerptState`).
The note is already created **at arm time** today (`App.tsx:243-260` runs when `armed` flips true,
before any canvas drop). v0.6.4 keeps create-at-arm but changes **three** things:
`type='source'` → **`type='claim'`**; add **`commentOn:<pdfSourceNote.slug>`** (resolved via the
`pdf_id` query) so `save-note.ts` writes the `comment-on` edge (existing param); and **drop the
unconditional `setViewMode('canvas')`** the excerpt bridge fires today (`App.tsx:265`). The child
then appears in the PDF's **thread** regardless of the current view. Canvas placement becomes
**conditional**: only if the center is already on `canvas` does the existing ghost-placement path
*also* place that same note spatially on `'root'` (notes are live references, principle 1) —
**v0.6's drag-to-canvas survives** for the canvas-view case, but excerpting from feed/thread no
longer yanks the user to the canvas.

### YouTube parity
Comment-on creation unchanged. The player's placeholder `<div>` moves from inside `ThreadView` into
a right-dock content pane (the `position:fixed` overlay then syncs to it there); `ThreadView`'s
pinned-player slot is replaced by the generic root-header. Video-order rail + sort toggle retained.

## Risks

- **`ThreadView` relocation (batch 1)** — moving the thread from a full-body replacement into a feed
  sub-state of `<main>` restructures the App body row (`App.tsx:873-1093`) and rewrites the
  `App.test.tsx` assertions around it. This is the milestone's biggest *structural* change; it gates
  the PDF-thread batches. Mitigation: it is its own batch with the rename, behind the green suite.
- **YouTube player-lift (batch 5)** — **lower risk than it looks.** The player is a `position:fixed`
  `<webview>` overlay synced to a placeholder each frame, never re-parented (`playerSingleton.ts:215-283`);
  the cookie lives in `partition="persist:yt-player"` (ADR 0017), independent of DOM lifecycle. The
  lift = relocate the placeholder `<div>` into a dock pane. Mitigation: the Playwright smoke is the
  gate; clean fall-back is deferring batch 5 to v0.6.5.
- **`PdfLocator` widening weakens excerpt validation** — see Data model trade-off; mitigated by
  internal-only construction.
- **PDF feed thumbnail perf** — rendering page 1 in every feed card is a pdf.js cost; first cut may
  ship a glyph, defer the thumbnail. Plan decides.
- **Excerpt double-meaning at commit** (thread child vs canvas place) — must create the note exactly
  once and place conditionally; an integration test pins "no duplicate note, edge always written".
- **Slug-rename of a thread root** — out of risk because slugs are immutable post-create (ADR 0002);
  noted so a future "rename slug" feature knows it owns re-pointing `comment-on` edges.
