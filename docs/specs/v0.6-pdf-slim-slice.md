# v0.6 pdf-slim-slice — spec

**Branch:** `v0.6/pdf-slim-slice` · **Direction doc:** `docs/canvas-vision.md` §PDFs (reviewers:
check §Future contracts below against it) · **Evidence:** `docs/research/2026-27-06-pdf-libs-and-architecture.md`
(binding research) + `local_files/preresearch/2026-06-27-pdf-support-handoff.md` (architecture handoff).
**Builds on:** v0.4 canvas-mvp (right dock embryo + canvas drop target), v0.2 YouTube annotation
(`source_kind`/`source_locator` precedent).

## Goal

A PDF document opens in a **right-dock content pane beside the canvas**; the user reads it, selects
text, and **captures an excerpt onto the canvas** as a note carrying a robust source locator pointing
back into the PDF (page + rect + quote + text offsets). No PDF annotation in this milestone — only
read + excerpt-drag. This is the slim slice of `canvas-vision.md` §PDFs, pulled forward ahead of the
full dock shell because the excerpt-drag is "the entire point" and the narrowest right-dock slice
honors the binding "dock-shell design must protect the excerpt-drag path from day one" constraint
without pulling in tabs, multi-pane, or left-dock changes.

**Vision-sequencing note:** `canvas-vision.md:194` lists "PDFs only after the node/edge/tab/pane
workflow is nailed" as a binding ordering constraint. This slim slice does NOT ship the full PDF
milestone — it ships read + excerpt-drag only, defers annotation (Stage 2), and ships only the embryo
right-dock growth (no tabs, no multi-pane, no edge work). It is the narrowest cut that makes the
excerpt-drag work; the full dock shell + PDF annotation remain sequenced after. `canvas-vision.md:82`
notes vision items are "commitments to a direction, not a date or an order"; this slice advances the
PDF *direction* without foreclosing the dock-shell sequencing.

## Non-goals (v0.6)

Explicitly out, all with direction in `docs/canvas-vision.md`: PDF ink annotation (deferred to Stage 2
— requires canvas-ink `PdfScene` sibling type per the ink-reuse contract) · highlight/stamp/freetext
annotation · pdf.js native editor layer · the full dock-shell grammar (right dock ships, but **no**
tab strips, **no** ≥2-pane coexistence, **no** tab dragging, **no** left-dock changes) · image-region
excerpt (only text excerpts in v0.6; region-image is annotation-adjacent) · PDF outline/bookmark
navigation pane · PDF search · full-text search of PDF body text (the note body carries the excerpt
text, which IS FTS-indexed via the existing `notes_fts`; the rest of the PDF is not) · reflowing
PDFs · PDF import-via-drag-onto-canvas (import is a File→Open / picker action; excerpt-drag is the
canvas gesture) · multi-document tabs (one PDF open at a time in the single content pane) · OCR of
scanned PDFs · PDF metadata editing · `EmbedPDF` engine (tracked v2 alternative; spike in Stage 3).

## Product decisions (locked in auto-brainstorm 2026-06-27, backed by `docs/research/2026-27-06-pdf-libs-and-architecture.md`)

1. **Engine:** `pdfjs-dist` v6 (Apache-2.0), rendered directly in the sandboxed renderer via a thin
   in-house React component. **NOT** a third-party React wrapper, **NOT** a `<webview>`. Security
   baseline = the existing hardened webPreferences (`sandbox:true`, `contextIsolation:true`,
   `nodeIntegration:false`) + strict CSP + pinning a current v6.x and tracking upstream. ADR 0043
   records this + the EmbedPDF v2 alternative.
   - **NOTE (verified via context7 `/mozilla/pdf.js` + pdf.js v6.0.227 source, 2026-06-27):**
     `isEvalSupported` was a v4/v5 `getDocument` option; it was **removed in the v5→v6 major API
     cleanup** (PR #21245) and is NOT in the v6 `DocumentInitParameters` typedef. The CVE-2024-4367
     mitigation is therefore NOT "set `isEvalSupported:false`" (a v6 no-op) — it is "use pdf.js v6+,
     where the eval-based font path was pruned along with the option." Pin v6.x; do not downgrade.
2. **Integration point:** pull forward the narrowest "right dock + one wide content pane" slice of the
   dock shell. The existing embryo (`src/renderer/src/panes/Pane.tsx`, `Dock.tsx`) grows a right-dock
   host and a content-pane class; tabs/multi-pane/left-dock changes stay deferred.
3. **`source_locator` shape (Stage 0 lock — costs nothing now, expensive to retrofit):** hybrid
   anchor persisted in the existing JSON `source_locator` column (NO `notes` migration):
   ```json
   {"media":"pdf","pdf_id":"…","page":42,
    "rect":[x,y,w,h],"quote":"the exact selected text",
    "prefix":"…","suffix":"…","textStart":1234,"textEnd":1290}
   ```
   `rect` = PDF user-space units (scale-independent). `quote`/`prefix`/`suffix` = TextQuoteSelector
   (primary re-anchor). `textStart`/`textEnd` = TextPositionSelector over page text. Re-anchor order
   at render time: quote → position → rect.
4. **Drag UX:** MarginNote-style capture→place. Selection → excerpt affordance (a small "excerpt"
   button/handle appearing on selection) → pending note packaged in zustand → user clicks/drops onto
   canvas → note created with `source_kind='pdf'` + the hybrid locator + placed via existing
   `api.canvas.placeNote`. **NOT** HTML5 drag-and-drop from the raw text layer.
5. **Schema:** new additive `pdf_documents` table (mirrors `video_sources`). `notes.source_kind='pdf'`
   + enriched `source_locator` JSON. **Do NOT touch the `attachments` CHECK** — SQLite cannot add a
   value to `CHECK (kind IN ('screenshot','clip'))` in place (12-step table recreation, violates
   additive discipline).
6. **File storage:** content-addressed `<userData>/attachments/<yyyy>/<mm>/<sha256>.pdf`, reusing the
   existing pattern verbatim. No separate `pdfs/` dir. Dedup at the file layer (rare for PDFs but
   idempotent re-import).
7. **Security:** pin pdf.js v6.x (the eval-font path was removed with the v6 `isEvalSupported`
   option — CVE-2024-4367 vector is structural-gone, NOT opt-out) + `worker-src blob:` added to CSP
   + `.pdf → application/pdf` added to the loopback shell MIME map + keep `X-Content-Type-Options:
   nosniff` + keep `will-attach-webview` YouTube-only (no PDF webview). Treat imported PDFs as
   untrusted input.
8. **One PDF at a time** in the single content pane. Opening a new PDF replaces the open one (the
   previously-open PDF id is remembered in `app_settings` as `pdf.openDocId` so reopening restores it).

## §1 Schema (migration `0007_pdf_documents.sql`)

```sql
-- v0.6 schema. Additive only. Mirrors video_sources (0002) for PDF metadata.
-- The note itself carries source_kind='pdf' + the hybrid source_locator JSON
-- (no notes-table migration); this table holds document-level metadata only.
CREATE TABLE pdf_documents (
  id           TEXT    PRIMARY KEY,            -- uuidv7
  sha256       TEXT    NOT NULL,               -- content hash of the .pdf bytes
  base_path    TEXT    NOT NULL,               -- abs path under userData/attachments/<yyyy>/<mm>/<sha>.pdf
  title        TEXT,                            -- PDF /Title metadata or filename fallback
  page_count   INTEGER,                         -- page count at import (pdf.js getDocument().numPages)
  imported_at  INTEGER NOT NULL,
  deleted_at   INTEGER
);
-- one row per distinct content (mirrors the partial-unique pattern in 0001_init.sql:16)
CREATE UNIQUE INDEX idx_pdf_documents_sha_live ON pdf_documents(sha256) WHERE deleted_at IS NULL;
CREATE INDEX idx_pdf_documents_title ON pdf_documents(title) WHERE deleted_at IS NULL;
```

- **Soft-delete** (`deleted_at`) per house convention; bytes on disk are NOT reclaimed (deferred
  concern, same as screenshots).
- **No `attachments` migration.** The existing `attachments` table's `CHECK (kind IN ('screenshot','clip'))`
  stays untouched. A future Stage 2 (PDF annotation) introduces `pdf_annotations(pdf_id, page, …)`
  as a separate additive table; it does NOT reuse `attachments` because the CHECK cannot be extended
  in place.
- **No `notes` migration.** `source_kind` and `source_locator` are already TEXT columns on `notes`
  (frozen `0001_init.sql:13-14`). The hybrid locator is JSON in the existing column.
- **Filename = `<sha256>.pdf`** (content-addressed, same as PNG captures). Sidecar annotations (Stage 2)
  would live at `dirname(base_path)/<pdf_id>/<page>.svg` or as `pdf_annotations` rows — decided in
  Stage 2 based on observed stroke volume, NOT here.

## §2 `source_locator` TypeScript (widening `src/shared/types.ts`)

The current `SourceLocator` (`src/shared/types.ts:12-16`) is YouTube-only. Widen to a discriminated
union:

```ts
export interface YoutubeLocator {
  media: 'youtube'
  video_id: string
  t?: number
}

export interface PdfLocator {
  media: 'pdf'
  pdf_id: string               // → pdf_documents.id
  page: number                 // 1-indexed
  rect: [number, number, number, number]  // PDF user-space [x, y, w, h]
  quote: string                // TextQuoteSelector — exact selected text
  prefix: string                // disambiguator
  suffix: string               // disambiguator
  textStart?: number            // TextPositionSelector over page text (best-effort; see §12)
  textEnd?: number              // best-effort; omitted if getTextContent() ordering is unreliable
}

export type SourceLocator = YoutubeLocator | PdfLocator
```

Zod schema (`src/shared/zod-schemas.ts`) mirrors this as a discriminated union. The widening is
spelled out in §3 (it is the load-bearing Zod delta a plan-writer cannot infer). The YouTube channels
that currently construct `source_locator` are unchanged (their values still satisfy `YoutubeLocator`).

**PDF metadata extraction at import (pdf.js in main process):** `pdf:import` (below) extracts `/Title`

## §4 pdf.js renderer component (`src/renderer/src/pdf/`)

New directory. The component is a thin in-house wrapper over `pdfjs-dist` — **not** a third-party
React wrapper. Files:

- `pdf/PdfReader.tsx` — the content pane body. Owns the loaded `PDFDocumentProxy`, the current page,
  and renders the active page's canvas + text layer. Hosts the selection→excerpt affordance.
- `pdf/usePdfDocument.ts` — react-query hook: `useQuery(['pdf', pdfId], () => fetch(mediaUrl) → pdfjs.getDocument(...))`.
  Configures the worker via `workerSrc` (blob-wrapped, same-origin per mozilla/pdf.js #9676). Disposes
  the document on unmount/query invalidation by calling **`loadingTask.destroy()`** (the v6
  `PDFDocumentLoadingTask.destroy()` async method — NOT `PDFDocumentProxy.destroy()`, which PR #21245
  removed in v6; verified via context7 `/mozilla/pdf.js` + v6.0.227 source).
- `pdf/useExcerptCapture.ts` — on selection (`mouseup`/`selectionchange` debounced), computes the
  hybrid locator: `window.getSelection().getRangeAt(0).getClientRects()` → subtract page container
  `getBoundingClientRect()` → `viewport.convertToPdfPoint(x, y)` per corner → persist PDF user-space
  rect. Extracts `quote`/`prefix`/`suffix` from the selection; `textStart`/`textEnd` from the page's
  text content (`page.getTextContent()`) by locating the quote substring. Emits a "pending excerpt"
  into zustand.
- `pdf/excerptState.ts` — zustand store (mirrors ADR 0040 command-registry store pattern): holds the
  pending excerpt payload (text + locator) between capture and place. Cleared on place or Esc.

**Worker/CSP:** pdf.js `workerSrc` is a blob-wrapped same-origin worker (mozilla/pdf.js #9676). The
CSP `worker-src blob:` addition (§5) permits this. No `script-src` relaxation — keep `'self'`, no
`unsafe-eval`.

**Coordinate space.** pdf.js `viewport = page.getViewport({scale})` maps PDF user space (origin
bottom-left, points = 1/72") to canvas/CSS pixels (origin top-left) via the transform
`[scale,0,0,-scale,0,height]`. The persisted `rect` is in **PDF user-space units** (scale-independent)
so the locator survives zoom/DPI changes. The conversion is `viewport.convertToPdfPoint(x, y)`
(verified in pdf.js source — `PageViewport` class, `src/display/page_viewport.js`).

## §5 CSP + loopback MIME changes

**CSP** (`src/renderer/index.html:17-18`) — add `worker-src blob:`:
```html
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; style-src 'self' 'unsafe-inline'; font-src 'self'; img-src 'self' data: https://i.ytimg.com https://*.ytimg.com; script-src 'self'; worker-src blob:;" />
```
`default-src 'self'` already covers workers; the explicit `worker-src blob:` is belt-and-suspenders
for the blob-wrapped worker. No `child-src`/`frame-src` changes (pdf.js renders to canvas + text
layer, no iframes). No `unsafe-eval`.

**Loopback MIME** (`src/main/http-shell.ts:43-55`) — add `.pdf`:
```ts
'.pdf': 'application/pdf',
```
The shell already emits `X-Content-Type-Options: nosniff` on every response, is GET-only, 127.0.0.1-bound,
and path-traversal-guarded. Serving `application/pdf` over it is safe. (pdf.js fetches bytes via
`fetch`/XHR and renders itself; no browser navigation, so Content-Disposition is moot.)

**`will-attach-webview`** (`src/main/index.ts:275-299`) — UNCHANGED. YouTube-only. No PDF webview.

## §6 Right-dock + content-pane slice (dock-shell embryo growth)

The embryo (`src/renderer/src/panes/Pane.tsx`, `Dock.tsx`) currently: left dock only, one pane
(shelf), in-memory width clamped `[220, 400]` px, resize via pointer-drag. Growth in v0.6:

- **`Pane.homeDock`** already accepts `'left' | 'right'` — the field anticipated this. Register a
  `pdf` pane with `homeDock: 'right'`.
- **`Pane.kind`** (NEW optional field, additive): `kind?: 'utility' | 'content'` defaulting to
  `'utility'` (so the existing `shelf` registration at `Pane.tsx:21` needs no change — truly
  additive, not a breaking shape change). Shelf = utility (narrow); PDF = content (wide). This is
  the two-pane-class mechanism from `canvas-vision.md:90-92` landing in embryo form. Content panes
  get a wider width clamp and default width ~600.
- **`Dock`** gains the ability to render on the right side (a `side: 'left' | 'right'` prop). The
  left-dock behavior is unchanged; a right-dock instance is created when a content pane is open.
  **No tab strips, no multi-pane coexistence** — exactly one right-dock pane (the open PDF) at a time.
  The width clamp becomes side-dependent: left/utility keeps `[MIN_WIDTH_UTILITY=220, MAX_WIDTH_UTILITY=400]`
  (existing values at `Dock.tsx:5-7`); right/content uses `[MIN_WIDTH_CONTENT=400, MAX_WIDTH_CONTENT=900]`
  with default ~600. Two named constants, one `Dock` component parameterized by `side`.
- **Open/close + width** stays in-memory view-state for v0.6 (matching the embryo's existing
  non-persistence). The open PDF id IS persisted (via `app_settings` `pdf.openDocId`, §3) so reopening
  the app restores the document; the pane open/closed state is not.
- **Keyboard resize** (WAI-ARIA separator) stays deferred to the full dock-shell milestone — same as
  v0.4's decision.

**The right dock must coexist with the canvas** (not replace it). When the PDF pane is open, the
layout is `[left dock: shelf] [center: canvas] [right dock: pdf]` — three regions. The Feed|Canvas
toggle (`src/renderer/src/topbar/WindowFrame.tsx`) is unchanged; the PDF pane is dock chrome, not a
third `viewMode`. This is option 2 from the research, explicitly chosen over option 1 (third
`viewMode`, defeats coexistence) and option 3 (thread-replacement, throws away coexistence).

## §7 Excerpt-drag data flow (the MarginNote move)

1. **User selects text** in the pdf.js text layer of the open PDF page.
2. **`useExcerptCapture`** fires on `selectionchange` (debounced) / `mouseup`:
   - Computes the PDF user-space rect via `viewport.convertToPdfPoint`.
   - Extracts `quote` (exact), `prefix`/`suffix` (disambiguators), `textStart`/`textEnd` (page text
     offsets via `page.getTextContent()` substring search).
   - Sets the pending excerpt in `excerptState` zustand store: `{ text, locator, pdfId, page }`.
3. **Excerpt affordance** appears (a small "excerpt →" button anchored to the selection rect, or a
   floating handle in the PDF pane header). Clicking it **packages the pending excerpt** into
   `excerptState` (zustand) and arms place-mode — it does NOT place yet. Esc clears the pending
   excerpt (esc-precedence audit #18 — every canvas mode re-audited).
4. **User clicks on the canvas.** The excerpt reuses the canvas's existing one-shot ghost
   placement path. The exact sequencing (the plan must wire this precisely):
   (a) `api.notes.create(text, 'source', { source_kind: 'pdf', source_locator: {...} })` resolves →
       yields the new note `id`.
   (b) App sets `placing = { noteId: <new id>, title: <excerpt text> }` — the `placing` prop shape
       at `CanvasStage.tsx:86` (`{ noteId: string; title: string } | null`) is satisfied verbatim.
       This arms the ghost (the existing `useEffect` at `CanvasStage.tsx:1189-1222` tracks the
       cursor and commits on canvas click).
   (c) Canvas click fires the existing handler at `CanvasStage.tsx:1212` → `placeAt(placing.noteId,
       world, 'absent')` → `api.canvas.placeNote(...)` at `CanvasStage.tsx:1043-1051`.
   (d) `excerptState` cleared.
   This mirrors the existing feed→canvas `onPlaceOnCanvas` flow (`App.tsx:559-566` precedent — id
   known up-front, then `placing` set). The create-on-canvas path at `CanvasStage.tsx:1228-1254` uses
   a different single-transaction `api.canvas.createNoteAt` and is NOT the model here (the excerpt
   needs the note created first to attach the locator).
5. **World-coordinate conversion** reuses the existing `screenToWorld(camera, screenPoint)` recipe
   (defined at `src/renderer/src/canvas/camera.ts:37-39`; the `clientToWorld` wrapper that calls it
   is at `src/renderer/src/canvas/useCanvasInteractions.ts:134-143`). No new coordinate code.

**The note is the excerpt.** The note body = the selected text (FTS-indexed via existing `notes_fts`
triggers). The `source_locator` carries the back-link. The note appears on the canvas like any other
card. Clicking a future "open source" affordance on the note would re-open the PDF at `page` and
re-anchor via quote→position→rect — **but that re-open affordance is out of v0.6 scope** (the data is
persisted; the UX to navigate back ships later). v0.6 ships the capture direction only.

## §8 Security

- **Treat imported PDFs as untrusted input.** A malicious PDF is the realistic threat.
- **CVE-2024-4367** (arbitrary JS execution via crafted font, disclosed April 2024, patched in pdf.js
  v4.2.67) defines the threat model. The vulnerable path required `isEvalSupported: true` — a v4/v5
  `getDocument` option that was the pdf.js default. **`isEvalSupported` was REMOVED in the v5→v6 major
  API cleanup (PR #21245) and is NOT a v6 option** (verified via context7 `/mozilla/pdf.js` + pdf.js
  v6.0.227 source, 2026-06-27). The v6 mitigation is therefore structural — pin v6.x and do not
  downgrade; the eval-based font path was pruned with the option. (Round-2 reviewer flag: the prior
  research doc's "set `isEvalSupported:false`" instruction is a v6 no-op and has been corrected here;
  the research doc remains stale on this point and should be amended — tracked as a nit.)
- **Existing baseline is strong:** `sandbox:true`, `contextIsolation:true`, `nodeIntegration:false`
  (`src/main/security.ts:42-53`) — the critical backstop preventing XSS-in-renderer from becoming
  RCE. This is now the *primary* mitigation, not a secondary one.
- **CSP** keeps `script-src 'self'` (no `unsafe-eval`); adds only `worker-src blob:` for the
  blob-wrapped pdf.js worker.
- **pdf.js version:** pin a current 6.x; track upstream for security releases. A dependabot/renovate
  config is out of scope for v0.6 but the ADR notes the maintenance signal.
- **No `<webview>` for PDF.** The YouTube `<webview>` precedent exists only because the IFrame needs
  a real HTTP origin; a local PDF has a different threat model and gains nothing from a webview while
  losing all selection access. `will-attach-webview` stays YouTube-only.
- **Smoke test must verify:** (a) the blob-URL pdf.js worker actually boots under `sandbox:true` +
  the literal §5 CSP (mozilla/pdf.js #9676 notes the blob-wrapper is real but its author calls
  `worker-src blob:` "not much different from not having a CSP for workers" — acceptable for a
  sandboxed renderer, but verify the worker boots); (b) whether the v6 worker uses `importScripts`
  inside the blob (which would require `script-src 'self' blob:` relaxation — if so, update §5). If
  the blob worker fails to boot, fallback is a `workerSrc` URL served by the loopback shell (requires
  copying `pdf.worker.mjs` into `rendererDir` at build time, or adding a third resolved root to
  `resolveAppRequest`).

  `toHaveScreenshot()` starts at v0.2; deliberately deferred). NOT added in v0.6.
- **Perf gate:** no manual harness in v0.6 (the PDF reader is not a 60fps animated surface like the
  canvas; pdf.js's own rendering perf is the floor). Revisit if a canvas-perf interaction appears.

## §10 Perf / ABI / build

- **New dep:** `pdfjs-dist` (Apache-2.0). ADR 0043 required (no new dep without an ADR).
- **No native module.** pdf.js is pure JS + a worker; no better-sqlite3-style ABI dance. Existing
  `pnpm rebuild:electron` / `rebuild:node` unaffected.
- **Bundle size:** pdf.js core + worker ~1–2 MB. Acceptable for a desktop app; the worker is loaded
  on-demand when a PDF opens, not at app boot.
- **React Compiler 1.0** (ADR 0006): the thin in-house component is the safest re: compiler
  compatibility (a third-party wrapper's compiler compat is undocumented — another reason to avoid
  wrappers, per the research).

## §12 Open questions / risks

- **pdf.js + Electron 39 sandbox worker load:** the blob-wrapped worker is same-origin per
  mozilla/pdf.js #9676; should work under `sandbox:true`, but the smoke test (§9) is the verification.
  If it fails, fallback is a `worker_src` URL served by the loopback shell (add a route).
- **Rect drift across pdf.js major versions / different PDF builds of "the same" document:** the
  hybrid anchor (quote→position→rect) mitigates but cannot fully guarantee re-anchoring across
  genuinely different PDF builds (Hypothesis documents this). Flag for QA; not a v0.6 blocker.
- **React Compiler + pdf.js:** pdf.js is framework-agnostic; the thin wrapper is compiler-safe by
  construction. Verify in the build.
- **`getTextContent()` for `textStart`/`textEnd`:** the offset computation depends on pdf.js's text
  item ordering, which can differ from visual reading order in some PDFs. The `quote`/`prefix`/`suffix`
  fields are the primary anchor; `textStart`/`textEnd` is a secondary fallback. The schema (§2) makes
  `textStart`/`textEnd` optional from day one; v0.6 populates them best-effort and may omit them
  entirely if `getTextContent()` ordering proves unreliable for a given PDF. No future schema change
  is needed to drop them.
