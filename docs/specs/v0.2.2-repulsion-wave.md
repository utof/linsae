# v0.2.2 — Selectable feed entrance animations (repulsion-wave + pluggable seam)

*Spec. Branch `v0.2.2/repulsion-wave`. Makes the send entrance a **pluggable strategy** with
three selectable animations — `glide` (today's shipped scroll-glide), `flip`, and `pbd` —
behind one clean seam. Extends ADR 0019 (Motion) / 0020 (glide reveal, ghost removed). The
mechanics, the bug, and the fix were proven in the dev spike (`src/renderer/src/dev/
RevealPlayground.tsx`, `5ba17cc`) and the fix + harness (`scripts/wave-reveal.mjs`, `3eeabb7`).*

## Context

Today a sent note rises via a **rigid scroll-glide**: `useAppendReveal.ts` animates the
scroller's `scrollTop` so the whole feed slides up as one block (ADR 0020 superseded the
v0.2.1 flying ghost, ADR 0018). It works and is the no-regression baseline.

The dev spike validated a different entrance: each note behaves like a **same-polarity
magnet** — the newcomer rises from below the fold and pushes the notes above it up in a
propagating wave, conveying "weight" (bigger note ⇒ stronger push). Two wave models exist:
- `flip` — a staggered make-room settle; punchy, but neighbouring notes **overlap softly**
  (no constraint). The user judged this "good enough — more real even though it intersects."
- `pbd` — `flip` plus a per-frame up-only non-overlap **projection**; **guarantees no two
  notes intersect**. The "punchy magnet" target.

The spike proved (harness, frame-by-frame) that the wave needs the virtualizer's append-follow
machinery turned OFF *at the `useVirtualizer` call on the append render* (see §Guard) — and that
once it is, both wave models rise cleanly (flip overlaps by design; pbd holds zero overlap).

**The user wants all three kept as genuine, switchable options**, with code that stays clear for
humans and agents (no one bloated file), and `glide` retained as the safe fallback.

## Goals

1. `glide`, `flip`, `pbd` all selectable for the rolling-feed send entrance.
2. A **clarity-first strategy seam**: one small contract, each animation in its own focused
   module, a shared engine for the two wave models (they differ only by the projection step).
3. A **user-facing preference** (Settings → display), persisted, defaulting to `glide` (zero
   behaviour change for existing users; `flip`/`pbd` opt-in).
4. **No regressions**: no #66 white-wall, no #67 spurious overlap (for glide/pbd), 60 fps,
   and the existing reduced-motion / short-feed / scrolled-away no-ops all still hold.
5. The seam is shaped so a future "pick-your-animation module" is an extension, not a rewrite —
   without building that module now (YAGNI).

## Non-goals (informational / → issues)

- **Composer → note morph.** The bigger future direction: the *composer card itself* morphs
  into the landing note bubble (same rectangle, border, radius; swap the send icon for the
  date), layered ON TOP of whichever entrance is selected — the entrance force/feel is
  unchanged, only the thing that rises changes from "a note from the bottom" to "the composer
  becoming a note." **Explicitly out of scope here**; recorded so the seam below doesn't
  preclude it. Do not build it in this milestone.
- A user-facing animation **module / marketplace** (third-party entrances, per-animation
  tuning UI in prod). The seam must not *preclude* it; we don't build it.
- Thread / capture-composer send entrance (rolling feed only — same staging as v0.2.1).
- Shipping the `pbd` tuning knobs (stagger/stiffness/damping/projection-passes) in the prod
  UI. They stay in the dev playground; prod ships tuned constants.

## Decisions (locked this batch — all reversible, here so the plan is unambiguous)

- **Scope:** all three land in the real Feed this batch (`glide` + `flip` + `pbd`).
- **Default:** `glide`. It is today's shipped behaviour, so the default is a *no-op change*;
  `flip`/`pbd` are opt-in. Making `flip` the default later is a one-line change to the pref
  default — deferred to the user's taste call after living with it.
- **Fallback:** *manual*. `glide` stays selectable; "if a wave model misbehaves, switch the
  setting to glide." No automatic runtime error-recovery / glide-substitution wrapper (YAGNI).
  Each strategy independently **no-ops** (the note just appears) on its gates — that is the
  per-strategy safety net, not a cross-strategy fallback.
- **Selection mechanism:** a persisted preference `lib/anim-pref.ts` mirroring `lib/clock-pref.ts`
  (localStorage + same-document custom event + reactive hook), surfaced as a `<select>` in the
  Settings *display* section. Read at send time, so changing it takes effect on the next send.
  Concrete API (tests + the harness assert these exact names): key `linsae.feedEntrance`, event
  `linsae:feed-entrance`, `getFeedEntrance()` / `setFeedEntrance(v)` / `useFeedEntrance()`,
  default `'glide'`, and an **unknown/legacy stored value parses back to `'glide'`** so a bad
  localStorage value can't break the feed.

## Architecture — the strategy seam

New directory `src/renderer/src/feed/entrance/`. Five focused modules + minimal Feed wiring.
Each module answers: *what does it do, how do you use it, what does it depend on.*

### `entrance/types.ts` — the contract

```ts
export type FeedEntrance = 'glide' | 'flip' | 'pbd'

/** What the dispatcher passes a strategy runner. The dispatcher (not the ctx) owns the
 *  suppression STATE; it hands each runner the SETTERS it needs, so a runner never reaches
 *  back into Feed internals. */
export interface EntranceCtx {
  virtualizer: Virtualizer<any, any>            // index-agnostic APIs only (as useAppendReveal)
  scrollerEl: HTMLElement | null
  notes: Note[]
  setWaveSettling: (on: boolean) => void        // wave family — extends suppression past append
  revealingRef: { current: boolean }            // glide family (today's useAppendReveal args)
  setRevealing: (on: boolean) => void           //  …
  suppressThumbResizeRef: { current: boolean }  // shared with the morph (scrollbar thumb)
}
```

The seam is a single Feed-facing hook (next), not a class hierarchy — strategies are small
enough that a hook + a couple of pure helpers per family is the clearest unit. The glide runner
keeps **exactly** today's `useAppendReveal` arguments (so the port is behaviour-preserving); the
wave runner adds `setWaveSettling`. Both read `estimateSize`/`isAtEnd`/`scrollEndThreshold` via
`virtualizer.options`, as `useAppendReveal` already does.

### `entrance/useEntranceAnimation.ts` — the Feed-facing hook (the dispatcher)

Replaces the direct `useAppendReveal(...)` call in `Feed.tsx`. Responsibilities:
- Read the active `FeedEntrance` (from the pref) **at append time** (a ref kept fresh each
  render), so the choice is per-send.
- Detect a single genuine append (the existing `useAppendReveal` detection: count grew by 1,
  new last id, non-empty prior list) and dispatch to the chosen strategy's runner.
- Expose **`suppressFollow: boolean`** to the Feed so the Feed can pass the correct
  `anchorTo`/`followOnAppend` *into* `useVirtualizer` (see §Guard). Defined as
  `sendInFlight || waveSettling || revealing` — the submit→append bridge, the wave's spring
  window, and glide's own scroll-settle, respectively. The Feed then ORs in the morph
  (`morphingIndex`) to compute the final `anchorTo`/`followOnAppend`, in **one place**, so
  morph / send / wave never clobber one another.
- Honour the **shared** no-op gates before dispatching: reduced motion, no scroller, a
  bulk/initial load (>1 note added at once), a zero-height newcomer. Keep the **at-end**
  determination **per family**, NOT shared: glide's is estimate-aware
  (`isAtEnd(grewBy + scrollEndThreshold)`, `grewBy = max(noteH, estRow)`,
  `useAppendReveal.ts:152-154`) — hard-won against the "reveal skipped for tall notes" bug
  (commits `9a9fc11`, `6f99196`); the wave uses plain `isAtEnd`. Collapsing at-end into one
  shared predicate would regress glide.

### `entrance/glideReveal.ts` — the scroll-glide (ported from `useAppendReveal.ts`)

The current `useAppendReveal` logic, moved here largely intact and renamed to fit the seam
(its `revealTween` size-blended bezier, the estimate-error landing correction, the
`settle()`/fail-safe). It drives `scrollTop` and **cooperates** with the virtualizer's follow,
so it needs only `anchorTo:'start'` for its window (already true today). `glide` does **not**
touch `--wy`. This is the fallback and the default. Net behaviour: unchanged from today.

### `entrance/waveReveal.ts` — the shared wave engine (`flip` + `pbd`)

The per-row `--wy` offset substrate, validated in the spike:
- On append: pin `scrollTop = scrollHeight`; seed an id-keyed `Map<noteId,{off,vel,delay}>`
  from the newcomer up at `off = +shift` (shift = newcomer `offsetHeight`, transform-immune),
  `delay = (newIndex − idx) × staggerMs`, so the wave travels up; the newcomer (delay 0) leads,
  rising from one note-height below its slot.
- One Motion `frame.update(tick,true)` loop integrates each offset toward 0 with a spring
  (semi-implicit Euler), writes every rendered row's `--wy` via `style.setProperty`, retires
  settled rows, and sets `waveSettling=false` (→ Feed re-render restores the follow) when the
  last offset retires.
- **Parameterised by an optional `project` step.** `flip` passes none (offsets overlap softly).
  `pbd` passes the projection (next). This is why flip and pbd are one engine, not two copies.
- State lives in a ref **outside the rows** (id-keyed) so it survives virtual-row recycling.

### `entrance/pbdProjection.ts` — the non-overlap projection (pure)

A pure function: given the ordered rendered rows' offsets + heights (top→bottom) and a pass
count, return projected offsets with **no adjacent gap negative**, swept **bottom→top, up-only**
(the newcomer is the pinned anchor; only the upper row of an overlapping pair is pushed up, and
the sweep propagates the shove upward — the magnet impulse emerges from the constraint). Pure ⇒
node-env unit-testable in isolation. `flip` never imports it.

### `Feed.tsx` — minimal, shared changes

1. **Row transform** (`Feed.tsx:556`): `translateY(${vItem.start}px)` →
   `translateY(calc(${vItem.start}px + var(--wy, 0px)))`. `--wy` defaults to 0, so glide and
   the static feed are byte-for-byte unchanged; the wave engine sets it per row.
2. **Guard into the options** (see §Guard): move the `anchorTo` / `followOnAppend` gating from
   the post-`useVirtualizer` mutations (`Feed.tsx:303-314`) **into the `useVirtualizer({…})`
   options object**, derived from `suppressFollow` (and still composing with the morph's
   `morphingIndex`). `shouldAdjustScrollPositionOnItemSizeChange` stays a render-body instance
   assignment (it is read live at `resizeItem` time, so that one is fine where it is).
3. Swap `useAppendReveal(...)` → `useEntranceAnimation(...)`.

No new dependency (Motion `frame`/`cancelFrame` are already used; verified in the spike).

## The Guard — spec-load-bearing (proven by `scripts/wave-reveal.mjs`)

The single most important real-Feed requirement, and the spike's hard-won finding:

> **`anchorTo` and `followOnAppend` must be passed *into* `useVirtualizer` and be correct on
> the append render** — not set by mutating `virtualizer.options.*` after the hook call.

Why: virtual-core gates its **entire** append-follow + scroll-anchor block on
`merged.anchorTo === "end"` evaluated inside `setOptions` (`@tanstack/virtual-core@3.16.1`
`dist/esm/index.js:274`), and `_willUpdate` — which fires `scrollToEnd()` → arms the
`reconcileScroll` rAF loop that re-pins the newcomer to the bottom every frame and cancels the
`--wy` rise — runs in `useVirtualizer`'s **own earlier** layout effect (react-virtual
`index.js:102`), before any Feed layout effect. A post-hook `virtualizer.options.anchorTo =
'start'` (what `Feed.tsx:303` does today, and what the spike's first failed guard did) does
**not** feed back into the next render's `setOptions`, because react-virtual rebuilds
`resolvedOptions = {...options}` fresh every render (`index.js:53`) and re-invokes
`setOptions(resolvedOptions)` in the render body each render (`index.js:98`). `glide` survives the
post-hook form only because it drives `scrollTop` itself and *cooperates* with the follow; the
wave does **not**, so the follow must be genuinely OFF.

Concrete requirements:
- `Feed.tsx` passes `anchorTo: suppressFollow ? 'start' : 'end'` and
  `followOnAppend: !suppressFollow` *inside* the `useVirtualizer({…})` options.
- `suppressFollow` must be **guaranteed true on the append render**, independent of how long the
  create round-trip takes. `createMut` is **not** optimistic — `onSuccess` invalidates and
  refetches (`App.tsx:155, 214-215`), so `notes` grows only after submit → IPC → SQLite →
  refetch, an unbounded wall-clock gap. Therefore `sendInFlight` must be cleared **when the
  append is observed** (the `notes` count grows in `App`), NOT on the fixed `setTimeout(…, 700)`
  it uses today (`App.tsx:117-118`): a 700 ms timer racing the round-trip can expire first, and
  on a wave that means `anchorTo:'end'` enters the hook on the append render and `reconcileScroll`
  arms — the snap the harness catches. Keep a generous fail-safe timeout only as a backstop.
  `sendInFlight` is the bridge that covers the append render for **all** strategies; the wave
  engine's `waveSettling` (true from append through spring retire) and glide's existing
  `revealing` then carry suppression through their respective settles. If suppression drops
  mid-wave, `reconcileScroll` re-arms and the newcomer snaps.
- The guard must still **compose with the expand/collapse morph** (`morphingIndex`): the final
  `suppressFollow`/`anchorTo` is the logical OR of morph, send, and wave reasons, in one place,
  so none of the three clobbers another.

## Real-Feed deltas the dummy spike did not exercise (requirements)

- **Async send pipeline.** Unlike the spike's synchronous `setNotes`, a real send is
  composer-submit → `createMut` → IPC → SQLite → react-query refetch → `notes` grows → append
  render, arriving *after* a round-trip. `sendInFlight` (armed at submit) covers the pre-append
  window — but its clear must be **append-coupled** (cleared when `notes` grows, generous timeout
  only as fail-safe), not the current fixed 700 ms timer, or a slow round-trip leaves suppression
  off on the append render (see §Guard). `waveSettling` then covers the settle. The wave seeds in
  the same append-detection layout effect the glide uses. Note `createMut.onSuccess` also bumps
  `successCount` → the Composer remounts (`App.tsx:218, 464`); the harness's type→Enter loop and
  the rapid-send stress must tolerate that remount between sends.
- **Markdown-rendered, variable heights** (incl. KaTeX, `DayDivider` rows): the seed `shift`
  is the newcomer's measured `offsetHeight`, so any real height is handled; verify a tall
  markdown note in the harness (estimate→real measure must not snap, given the guard).
- **No `resizeItem`.** The wave is transform-only, so the row stays `measureElement`-measured
  (ADR 0007 — never mix `measureElement` + `resizeItem` on one row). The estimate→real measure
  still fires once, but with the guard on it cannot ride the scroll.
- **No-op gates (the note just appears), every strategy:** reduced motion; a bulk/initial load
  (more than one note added at once); the user scrolled away from the bottom (`!isAtEnd`); a
  zero-height row; no scroller; a short non-overflowing feed (already bottom-anchored — no
  room to push). These mirror today's `useAppendReveal` gates and live in the shared hook.

## Key flows

**Send (wave, flip/pbd).** Submit → `sendInFlight=true` (so `suppressFollow` true → the append
render passes `anchorTo:'start'`/`followOnAppend:false` into `useVirtualizer` → `reconcileScroll`
never arms) → async create → `notes` grows → append layout effect: pin `scrollTop=scrollHeight`,
seed `--wy=+shift` bottom→top, `waveSettling=true`, start the spring loop → each frame integrate
toward 0 (pbd projects), paint `--wy` → last offset retires → `waveSettling=false` → re-render
restores `anchorTo:'end'`/`followOnAppend:true`.

**Send (glide).** Unchanged from today, now reached through the seam (the dispatcher calls the
glide runner; `--wy` stays 0).

  `maxSingleFrameJump / totalRise < 0.5` (no one-frame snap); `scrollTop` stable through the

- `pbd`: **no overlap** — min adjacent row gap ≥ −1 px (sub-pixel tolerance) every frame.
  `flip`: overlap is allowed
  (by design) — assert it rises, do **not** gate its gap.
- `glide`: unchanged (still rises; existing behaviour).
- Run `scripts/reveal-stress.mjs` (rapid/overlapping sends) for `glide` and `pbd`: **no #66
  white-wall, no #67 overlap**; the post-settle invariants stay green. (flip exempt from the
  overlap invariant.)

**Unit (node-env Vitest, pure — no DOM):** the spring integrator step; the **PBD projection**
(offsets+heights in → non-overlapping offsets out; covers the up-only/bottom→top propagation +
the newcomer-anchor case); `anim-pref` get/set/default; the shared no-op-gate predicates and the
seed geometry (delay/shift). Pin `// @vitest-environment node`.

**Component (RTL + happy-dom):** the Settings select changes the active strategy; reduced-motion

branches only — *trajectory and the scroll-snap are the harness's job* (happy-dom cannot

## Risks

- **Guard window too short → re-snap.** If `waveSettling` clears before the spring retires,
  `reconcileScroll` re-arms mid-wave. Mitigation: the wave engine owns `waveSettling` and
  clears it only on retire; the harness's `scrollTop`-stable assertion catches a regression.
- **Three guards (morph/send/wave) clobbering each other.** Mitigation: one derived
  `suppressFollow` in one place; a component test that a morph during a pending wave doesn't
  desync (and vice-versa).
- **Tall markdown/KaTeX note estimate→real measure.** Transform-only avoids `resizeItem`, and
  the guard blocks the wasAtEnd ride; verify explicitly in the harness with a big note.
- **Pref read timing.** Reading the pref per-send (not per-render) avoids mid-wave strategy
  swaps; the dispatcher snapshots it at append. An in-flight wave is allowed to **finish**; a
  pref change applies from the **next** send (no mid-wave cancel).
- **`directDomUpdates` must stay OFF.** Feed uses the default React-rendered `translateY`;
  react-virtual's optional `directDomUpdates:'transform'` path writes `el.style.transform`
  directly (react-virtual `index.js:46-47`), which would clobber the `--wy` `calc()` transform.
  Invariant: do not enable `directDomUpdates`. Record in ADR 0021.
