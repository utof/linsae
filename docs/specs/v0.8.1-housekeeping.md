## 1. Goal

Close the gap between what the repo's documentation *claims* and what it *does*, and make the
app distributable. No product surface changes. Eight milestones of features have shipped on top of a
v0.1-era README, a `progress.md` three milestones stale, a CLAUDE.md asserting a CI that does not
exist, and a `package.json` still carrying electron-vite template placeholders.

One genuine engineering deliverable rides along: the **visual-regression harness**, which CLAUDE.md
has mandated since v0.2 and which has never existed.

### Success criteria

1. `pnpm build` produces a distributable whose `app.asar` is **under 20 MB** (currently 110 MB /
   9,801 entries) and which launches.
2. No template placeholder remains in `package.json` or `electron-builder.yml`.
3. `pnpm test:visual` runs `@playwright/test` against a real Electron window with deterministic seed
   data and compares committed baselines; a deliberate color regression fails it.
4. Every factual claim in `CLAUDE.md` and `README.md` is true of the repo at `v0.8.1`.
5. `memory/progress.md` reflects reality through v0.8.
6. No ADR that has been superseded reads `Status: Accepted` without saying so.

### Non-goals

- **CI.** Explicitly declined by the user (2026-08-01): single developer, lefthook is the gate.
  CLAUDE.md's two CI claims are *removed*, not implemented.
- **Draining the nit backlog by fixing nits.** This batch adds a retirement *rule* and does one
  verification sweep; it does not fix 70 nits.
- **Visual baselines for non-Linux platforms.** `{platform}` keeps the path per-OS; only `linux`
  baselines are committed. Documented, not solved.
- Any change to product behavior, schema, IPC, or Zod surface.

## 3. Packaging (§findings 1–3)

### 3.1 The asar fix

**Revised 2026-08-01 after source verification. The original mechanism in this section was wrong and
would have been a silent no-op — recorded here rather than deleted, because the wrong answer is the
intuitive one and will be re-proposed otherwise.**

#### What does NOT work

Adding `!node_modules/**` (with a re-inclusion) to `electron-builder.yml`'s `files:` list. Verified
against electron-builder's own source via context7 (`/electron-userland/electron-builder`):

- `fileMatcher.ts` — *"When files patterns are configured, electron-builder **always injects
  `!**/node_modules/**`** to exclude node_modules from the general file walk (they are handled
  separately)."*
- `nodeModulesCollector.ts` — *"Node modules are collected via package-manager-specific dependency
  tree analysis — **NOT by walking the filesystem with user patterns**. Only dependencies +
  optionalDependencies are considered (devDependencies excluded)… This is how electron-builder
  determines what goes into `node_modules` in the app, **completely independently of the files
  config**."*

`files:` never governed this. The 110 MB comes from the production **dependency graph**.

#### What the 110 MB actually is

`electron.vite.config.ts` applies `externalizeDepsPlugin()` to **`main` and `preload` only**. Those
two processes therefore do *not* bundle their imports — they `require` them from `node_modules` at
runtime, and those packages must ship. The **renderer has no such plugin**: it is fully bundled by
Vite into `out/renderer`, so every renderer-only package is already inside the bundle and its
`node_modules` copy is pure duplication.

Runtime-required by main/preload (enumerated from every bare-package import under `src/main` and
`src/preload`, excluding `node:` builtins and `electron` itself):

| package | why it must stay |
|---|---|
| `better-sqlite3` | native `.node` binding; auto-unpacked by electron-builder's `isLibOrExe` detection |
| `pdfjs-dist` | `src/main/media/extract-pdf-metadata.ts:5` imports `pdfjs-dist/legacy/build/pdf.mjs` for /Title + numPages |
| `js-yaml` | frontmatter |
| `uuidv7` | id generation |
| `zod` | IPC-boundary validation |

Everything else in `dependencies` is renderer-only and already bundled: `lucide-react` (3,962
entries — the single largest contributor), `motion` (+ transitive `motion-dom`, `framer-motion`,
~1,020), `@tanstack/*` (616), `katex` (231), `cmdk` (+ transitive `@radix-ui`, 162), the
`react-markdown` / `remark-*` / `rehype-*` / `micromark` / `mdast` / `unified` / `unist-util-visit`
chain, `rbush`, `perfect-freehand`, `react-hotkeys-hook`, `zustand`.

#### The fix

**Move the renderer-only packages from `dependencies` to `devDependencies`.** electron-builder
excludes devDependencies from the production graph automatically and *transitively* — which is the
decisive advantage over a hand-maintained keep-list in `files:`, since a keep-list cannot track
transitive deps and silently rots.

This is semantically defensible and not a hack: for a **bundled** renderer these are build-time
inputs, not runtime requirements. That is precisely the distinction `dependencies` encodes.

#### Risks specific to this mechanism

1. **knip may object.** knip classifies dependency-vs-devDependency placement and may flag packages
   used in `src/` as belonging in `dependencies`. knip runs in the lefthook gate, so this can block
   the commit. If it fires, the fix is a knip config change — **not** `--no-verify`, and **not**
   reverting the move. Verify empirically; do not assume either outcome.
2. **`pdfjs-dist` and `zod` stay**, so the win is smaller than a naive "exclude everything"
   estimate. Expect roughly 9,801 → ~1,300 entries.
3. Nothing here touches `asarUnpack` or `npmRebuild: false`; both remain correct.

#### Acceptance — empirical, in this order

1. `pnpm exec electron-vite build && npx electron-builder --linux dir`
2. `app.asar` entry count drops to ~1,300 and size well under 20 MB.
3. **Launch the packaged binary and exercise a path through every retained dep**: the feed must
   render (proves `better-sqlite3` + `zod` + `js-yaml`), and **a PDF must open** (proves
   `pdfjs-dist` survived in main *and* that the renderer's bundled copy still resolves its worker).
   A size assertion alone would pass a build that is broken in exactly the way this change risks.
4. Re-run `pnpm knip` explicitly — the lefthook gate covers it, but a silent config relaxation here
   is the kind of thing that hides a real finding.

`dist/` is already gitignored; no artifact is committed. **Success criterion 1 in §1 is amended from
"under 20 MB" to reflect that `pdfjs-dist` + `zod` must remain.**

### 3.2 Placeholders

## 4. Visual regression (§finding 5)

### 4.1 Why a new dependency is justified here

`toHaveScreenshot()` is a Playwright **test-runner** assertion. Per the official API docs
(context7, `/microsoft/playwright`, `class-locatorassertions.md`): *"Note that screenshot assertions
only work with Playwright test runner."* The bare `playwright` library this repo uses for its
`.mjs` smokes cannot do it at any effort. CLAUDE.md's "no new dep" is a clause of the **inline-fix
gate**, which is scoped to nits — it never applied to milestone deliverables. The gate was
misapplied at v0.2 and the mandate has been dead ever since.

`@playwright/test` is pinned to **exactly `1.60.0`** to match the installed `playwright` 1.60.0.
A version skew between the two packages is a documented source of protocol errors.

### 4.2 Shape

- `playwright.config.ts` at the repo root: `testDir: 'tests/visual'`, `snapshotPathTemplate`
  including the **`{platform}`** token, `expect.toHaveScreenshot` thresholds, `fullyParallel: false`
  (Electron launches are not parallel-safe against a shared user-data dir), `workers: 1`.
- `tests/visual/*.spec.ts` — `@playwright/test` specs using `_electron.launch`, mirroring the
  existing launch/teardown discipline in `scripts/pdf-render-smoke.mjs` (throwaway
  `--user-data-dir` under `mkdtempSync`, `app.close()` in `finally`).
- `pnpm test:visual` / `pnpm test:visual:update` scripts.
- Vitest must **not** collect these. `vitest.config.ts`'s include/exclude has to be checked and, if
  it would glob `tests/visual/*.spec.ts`, excluded explicitly. A `@playwright/test` spec imported by
  Vitest fails in a confusing way.

### 4.3 Determinism — the hard part

A screenshot test that is not deterministic is worse than none; it trains you to ignore red. Four
sources of nondeterminism, each of which must be handled explicitly:

1. **Seed data.** The app reads a real vault + SQLite. Specs must launch against a throwaway
   `--user-data-dir` seeded with a **fixed** note set — fixed bodies *and fixed ids/timestamps*,
   since uuidv7 is time-ordered and the feed sorts by it. A helper that writes a deterministic
   vault is the reusable core of this deliverable.
2. **Animation.** Motion is app-wide (ADR 0019) and the feed has entrance animations (ADR 0022).
   Pass `animations: 'disabled'`, and assert on a settled state.
3. **Fonts.** Text rendering differs across machines. This is the reason for `{platform}` and for a
   non-zero `maxDiffPixelRatio` rather than pixel-exactness.
4. **Timestamps in the UI.** Any rendered relative time ("2h ago") drifts. Either the seed pins a
   fixed clock or those regions are `mask`ed. Prefer masking — it is local and cannot be defeated by
   a later timezone change.

### 4.4 Surfaces

The original motivation, `docs/specs/v0.1-rolling-feed-and-search.md:368`, is explicit: *"The user
specifically called out the 'AI writes black-on-black' failure mode."* Coverage is chosen to catch
that class — a token regression making text invisible — not to freeze layout.

Four shots, one per major surface: **feed**, **canvas**, **PDF reader**, **thread view**. Each at a
fixed viewport. Start here; more shots are cheap once the seeding helper exists, and a large
baseline set committed on day one is a maintenance liability before it is an asset.

### 4.5 Proving the harness works

**A harness that has never gone red is not known to work.** Acceptance requires demonstrating a
caught regression: perturb a color token, confirm `pnpm test:visual` fails, revert, confirm green.
This is the same mutation discipline that caught ten vacuous tests in v0.8, and it is the only
evidence that distinguishes a working gate from four `.png` files.

## 9. Risk

The only change that can break the product is §3.1. Everything else is prose, metadata, or additive
test infrastructure. §3.1's failure mode is specific and known: an over-broad exclusion that ships
an app which launches but cannot open its database. §3.1's acceptance test is written to catch
exactly that, and it must not be reduced to a size assertion.
