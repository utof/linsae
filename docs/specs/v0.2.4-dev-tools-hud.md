# v0.2.4 — Dev-tools HUD

## Problem

Four DEV-only overlays (`DevFpsMeter`, `DevBootMeter`, `WaveTuner`, `RevealPlayground`)
are gated inconsistently and are hard to toggle:

| Tool | Today's gate | Toggle UX |
| --- | --- | --- |
| `DevFpsMeter` | `import.meta.env.DEV` only (`main.tsx:58`) | always on in dev — no way to hide it |
| `DevBootMeter` | `import.meta.env.DEV && localStorage.devbootmeter` (`main.tsx:53`) | edit `localStorage` in DevTools, reload |
| `WaveTuner` | `import.meta.env.DEV && localStorage.wavetuner` (`App.tsx:26`) | edit `localStorage` in DevTools, reload |
| `RevealPlayground` | `DEV_PLAYGROUND` + `playgroundOpen` React state (`App.tsx:296`) | `mod+shift+r` |

Every overlay is still walled behind `import.meta.env.DEV` (tree-shaken from prod), but
beyond that the controls are scattered: one is always-on, two need hand-edited localStorage
keys + a reload, one has a dedicated hotkey. As more dev overlays are added this gets worse —
each new tool either eats a global hotkey or invents another localStorage flag.

## Goal

A single dev-tools HUD, opened with **`mod+shift+d`**, listing every overlay with a live
on/off checkbox. One global hotkey forever; adding a tool is adding a row, not a keybinding.
All overlays stay DEV-only (tree-shaken from production); the HUD only adds discoverable,
live control on top of the existing `import.meta.env.DEV` wall.

## Decisions (settled in brainstorming)

1. **Shape:** one HUD toggled by `mod+shift+d` — *not* one hotkey per tool. Scales to N tools
   without consuming N global combos.
2. **Modifier:** `mod+shift+d`, consistent with the codebase's existing `mod+` hotkeys
   (`mod+k`, `mod+shift+r`, `mod+shift+c`). `mod+` resolves to ⌘ on macOS, Ctrl elsewhere —
   so *not* a literal `ctrl+shift`.
3. **Persistence:** always-on overlays (fps / boot / wave) persist their on/off state in
   `localStorage` so a choice survives a dev reload. The reveal *modal* is session-ephemeral —
   it must not reopen itself on reload.
4. **Defaults** on a fresh dev boot (no stored value): **fps on**, boot off, wave off, reveal off.
   Preserves today's behavior (fps is currently always-on); the HUD only adds a way to hide it.
5. **Reveal folds into the HUD too** — the HUD shows a reveal row reflecting the same state that
   `mod+shift+r` toggles. The dedicated `mod+shift+r` hotkey keeps working.

## Architecture

Three small units, each independently testable.

### 1. `dev/devOverlays.ts` — the overlay store

A tiny external store (React's built-in `useSyncExternalStore`, **no new dependency**) holding
one boolean per overlay. This is the single source of truth that both render roots
(`main.tsx`'s fps/boot and `App.tsx`'s wave/reveal) and the HUD read from, so a toggle
re-renders every consumer live — no reload.

```ts
export type DevOverlayKey = 'fps' | 'boot' | 'wave' | 'reveal'
```

Per-key config:

| key | default | persistence | localStorage key |
| --- | --- | --- | --- |
| `fps` | `true` | localStorage | `devfpsmeter` |
| `boot` | `false` | localStorage | `devbootmeter` (existing) |
| `wave` | `false` | localStorage | `wavetuner` (existing) |
| `reveal` | `false` | **in-memory only** | — (ephemeral; never persisted) |

Persisted value encoding: `'1'` = on, `'0'` = off, **absent** = the key's default. Reading
treats any non-`'0'`, non-empty stored string as on, so a pre-existing hand-set
`localStorage.wavetuner = 1` (or `= "true"`) still reads as on — backward compatible with the
current manual workflow. Writes always normalize to `'1'` / `'0'`.

Public surface:

```ts
export function getOverlay(key: DevOverlayKey): boolean
export function setOverlay(key: DevOverlayKey, on: boolean): void   // writes + notifies
export function toggleOverlay(key: DevOverlayKey): void
export function useDevOverlay(key: DevOverlayKey): boolean          // useSyncExternalStore subscriber
```

A module-level `Set<() => void>` of subscribers is notified on every `setOverlay`. Ephemeral
keys (`reveal`) keep their value in a module-level record instead of localStorage; everything
else round-trips localStorage. `getServerSnapshot` returns the static default (happy-dom/test
safety; the app has no SSR).

### 2. `dev/DevToolsHud.tsx` — the panel

A DEV-only floating panel (corner that avoids fps/boot — e.g. top-left), registering
`mod+shift+d` via `react-hotkeys-hook` to toggle its *own* open/closed React state
(ephemeral, default closed; `enableOnFormTags: ['textarea','input']` so it fires from the
composer too). When open it renders one labelled checkbox row per `DevOverlayKey`, each bound
to `useDevOverlay(key)` and `toggleOverlay(key)`. Styled with the existing dev playground
primitives (`dev/playgroundKit.tsx`) / inline v21 CSS-variable tokens — it's a dev tool, so
visual polish is low priority but it stays token-consistent (no Tailwind, no design-token drift).

### 3. Wiring each overlay to the store

Each tool stays mounted where it is today (their React-context needs differ — `DevBootMeter`
must stay inside `QueryClientProvider`; `WaveTuner`/`RevealPlayground` stay in `App`), but its
*gate* changes from a boot-time check to a live store read.

- **`main.tsx`** — replace the two inline conditionals with gate wrappers (top-level module
  code can't call hooks):
  - `<BootMeterGate />` (inside `QueryClientProvider`, today's line 53): `useDevOverlay('boot') ? <DevBootMeter/> : null`.
  - `<FpsMeterGate />` (outside the provider, today's line 58): `useDevOverlay('fps') ? <DevFpsMeter/> : null`.
  - `<DevToolsHud />` mounted once (DEV-gated) alongside the fps gate.
  - All three stay wrapped in `import.meta.env.DEV && …` so production tree-shakes them.
- **`App.tsx`** —
  - `WaveTuner`: keep the module-level `import.meta.env.DEV ? lazy(import('./dev/WaveTuner')) : null`
    (preserves tree-shaking), but mount it on `const waveOn = useDevOverlay('wave')` instead of
    folding `localStorage.wavetuner` into the module const.
  - `RevealPlayground`: replace the `playgroundOpen` `useState` with `useDevOverlay('reveal')`;
    `mod+shift+r` calls `toggleOverlay('reveal')`; the modal's close button calls
    `setOverlay('reveal', false)`. Availability stays gated on `DEV_PLAYGROUND`
    (`DEV || VITE_PLAYGROUND`) so the Playwright `VITE_PLAYGROUND` harness can still drive it via
    `mod+shift+r` (the HUD itself is DEV-only and absent from that harness build — unchanged for
    the harness, which uses the hotkey, not the panel).

## Data flow

```
mod+shift+d ─► DevToolsHud open state (local) ─► renders checkbox rows
checkbox / mod+shift+r ─► toggleOverlay(key) ─► store notifies subscribers
                                                   │
        ┌──────────────────────────────┬──────────┴───────────┬─────────────────┐
   useDevOverlay('fps')        useDevOverlay('boot')   useDevOverlay('wave')  useDevOverlay('reveal')
   FpsMeterGate (main)         BootMeterGate (main)    WaveTuner (App)        RevealPlayground (App)
```

## Error handling / edge cases

- **localStorage unavailable / throws** (private-mode quirks): reads fall back to the key's
  default, writes are best-effort wrapped in try/catch — a dev tool must never crash the app.
- **Mounting boot meter mid-session**: `DevBootMeter` reads boot-timing once; toggling it on
  *after* boot may show already-elapsed timings. Acceptable — its persisted value means it's
  on from boot on the next reload, which is the useful path. Noted, not fixed.
- **Reveal reload behavior**: because reveal is in-memory-only, reloading always closes the
  playground (intended — a modal should not resurrect itself).

## Testing

- **Unit (Vitest, `// @vitest-environment node` or happy-dom localStorage):** `devOverlays.ts` —
  defaults per key; `setOverlay`/`toggleOverlay` round-trip localStorage for persisted keys;
  `reveal` never writes localStorage and resets to default on a fresh module/store; backward-compat
  read of a pre-set truthy `wavetuner`; subscriber notified on change.
- **Component (Vitest + RTL):** `DevToolsHud` — renders a row per key; checkbox reflects store
  state; clicking a row toggles the store; `mod+shift+d` opens/closes the panel. `FpsMeterGate` /
  `BootMeterGate` — render their child iff the store key is on.
- Existing `mod+shift+r` reveal behavior covered by re-pointing it at the store (App-level test
  only if one already exists; otherwise the HUD + store tests cover the toggle path).

## Out of scope (YAGNI)

- No prod-facing dev menu, no settings-panel integration — strictly `import.meta.env.DEV`.
- No reordering / drag, no per-overlay config inside the HUD (WaveTuner keeps its own panel).
- No new hotkeys beyond `mod+shift+d`; `mod+shift+r` stays as the reveal alias.
