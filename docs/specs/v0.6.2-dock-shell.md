# v0.6.2 dock-shell — spec

**Branch:** `v0.6.2/dock-shell` · **Direction doc:** `docs/canvas-vision.md` §Dock shell + Locked
principle 7 (reviewers: check §Future contracts below against it) · **Builds on:** v0.4 canvas-mvp
(`docs/specs/v0.4-canvas-mvp.md` §10 — the embryo `Pane`/`Dock`), v0.6 pdf-slim-slice
(`docs/specs/v0.6-pdf-slim-slice.md` §6 — the right dock + content-pane class), v0.5 command-search
(`adrs/0040-command-palette-generalization-and-zustand.md` — the zustand command registry this reuses).

## Goal

"Back up" the slim PDF slice with the real **constrained-tiling window grammar**: a dock holds **more
than one pane**, and a **tab strip appears once 2+ panes share a dock** (vision principle 7: "tabs as
text labels… a user who never opens a second pane never sees a tab"). The forcing function is
**promoting backlinks to a dockable utility pane** so the right dock can hold PDF (content) + backlinks
(utility) → tabs. The load-bearing deliverable is the **mechanism** — a dock = an ordered list of pane
ids + an active id, home-dock routing, per-pane width — shared by both docks, so future panes (AI chat,
a second content pane, shelf tab-mates) drop in without a rewrite.

This replaces the two hardcoded single-pane `<Dock>` instances + their ad-hoc boolean open-state
(`dockOpen` for shelf, `pdfPaneOpen`/`openPdf` for pdf) with one in-memory **zustand dock store**.

## Non-goals (v0.6.2) — all with direction in `docs/canvas-vision.md` §Dock shell

- **Cross-dock tab dragging** ("tab dragging between docks as pure rearrangement"). Vision: "pure power
  feature… Do not build until proven." Deferred whole.
- **WAI-ARIA keyboard resize** (the `role="separator"` splitter pattern) — deferred since v0.4/v0.6;
  still pointer-only.
- **Persistence of dock layout** — open panes / active tab / widths stay in-memory per-window
  view-state (vision: "no saved workspaces/presets until layouts demonstrably hurt to reconstruct").
  The one already-persisted bit is unchanged: `pdf.openDocId` in `app_settings` (ADR 0042) still
  restores *which* PDF, not the pane geometry (see §4 C2 for the restore seam this implies).
- **AI-chat pane** — the vision's other named utility pane; a separate feature subsystem (LLM provider,
  keys, streaming). Out of a window-grammar milestone.
- **Left-dock content panes / shelf tab-mates** — the mechanism supports any pane homing left and the
  left dock gaining a tab strip, but v0.6.2 adds **no** new left-dock pane (shelf stays solo there).
- **The two quiet outline dock-toggle chrome affordances** at top-right (vision §Dock shell). Opening
  panes in v0.6.2 reuses existing triggers (shelf toggle, Open-PDF flow, the new backlinks command); the
  dedicated toggle chrome lands with cross-dock drag.
- **Replacing the backlinks focus-overlay.** The transient focus→overlay peek stays (see Decision 4);
  v0.6.2 *adds* a deliberate dock pane beside it, it does not remove the overlay.

## Product decisions (locked in brainstorm 2026-06-29)

1. **A dock = ordered pane ids + active id.** Tab strip renders only at `length ≥ 2`; at exactly 1 the
   header stays today's quiet `title ×` row (the v0.6 look is preserved for the single-pane case). A
   pane id lives in exactly one dock — its `homeDock` from the registry — so opening routes
   deterministically.
2. **State lives in a zustand dock store** (`src/renderer/src/panes/dockStore.ts`), in-memory only.
   This is the codebase's second zustand store after the command registry (ADR 0040); dock layout is
   genuinely mutable app-global **client** view-state → a store, not react-query (no DB) and not App
   `useState` (it outgrew booleans). Per-window, not persisted.
3. **Per-active-pane width.** Each pane remembers its own width in `widths[paneId]`, defaulting to its
   kind default and clamped to its kind band (utility 220–400, content 400–900 — the existing
   constants in `Dock.tsx`). The dock renders at the **active tab's** width; tabbing pdf↔backlinks
   resizes the dock and the center stage reflows. This is the honest resolution of wide-content +
   narrow-utility coexisting in one dock.
4. **Backlinks gets a dual surface, not a replacement.** The existing **focus→transient overlay**
   (`App.tsx:949`, absolute-positioned so it does not shift the feed) is **untouched** — it is the
   lightweight peek a single bubble-click earns. v0.6.2 **adds** backlinks as a **deliberately-opened
   right-dock utility pane** (via a command). A deliberately-opened pane pushing the stage is fine —
   identical to opening a PDF — because it is an intentional action, not a focus side-effect. **Why
   dual:** `App.tsx:723-731` records that an earlier flex-sibling backlinks "shifted the entire feed;
   user feedback called that 'annoying and too much for such a small action'" (quote at `App.tsx:725-726`).
   Keeping the overlay for the small action while making the dock pane deliberate honors that feedback.
   - **Suppression rule:** while the backlinks dock pane is open, the overlay does not render (no double
     backlinks).
   - **Close-clears-focus (I1):** closing the backlinks dock pane (its tab `×`) also clears `focusedId`
     (mirroring the overlay's own close at `App.tsx:952`). So "close backlinks" fully dismisses it and
     does NOT resurrect the suppressed overlay.
   - **Focus-clear-auto-closes (I2):** when `focusedId` clears while the backlinks dock pane is open
     (Esc `App.tsx:552`, or re-clicking the focused bubble `App.tsx:878`), the pane auto-closes — a
     backlinks pane with no subject note is dead chrome, and this keeps "no focus ⇒ no backlinks
     anywhere" consistent with the command (un)registration in Decision 5.
   - These two settle without a loop: close → clear-focus → auto-close is an idempotent no-op on the
     already-removed pane.
5. **Deliberate open = a command-palette entry**, not a dedicated hotkey (hotkey deferrable). The
   `backlinks.open` command is **registered/unregistered by its OWN App effect keyed on `[focusedId]`** —
   present in `⌘K` only while a note is focused, absent otherwise. It is **NOT** a register-once + `when`
   gate: `CommandMenu` evaluates `when()` against the closure captured at registration time
   (`CommandMenu.tsx:93-96`, `useMemo([registry])`), so a register-once `when: () => focusedId != null`
   would capture `focusedId` from the mount render (null) and never update. The v0.5 `view.recent`
   command only works because its registration effect re-registers on `viewMode` change (`App.tsx:340`
   deps); rather than churn the whole base-command set on every focus change, backlinks gets a dedicated
   `[focusedId]` effect.
6. **`Dock` stays presentational; a new `DockHost` is the store glue.** Existing `Dock.tsx` keeps its
   pure-render character (eases its existing `Dock.test.tsx` / `Dock.right.test.tsx` pattern); a thin
   `DockHost({ side })` subscribes to the store and feeds props. App renders `<DockHost side="left"/>`
   and `<DockHost side="right"/>` in the same flex slots the two `<Dock>`s occupy today.

## §1 The dock store (`src/renderer/src/panes/dockStore.ts` — NEW)

```ts
import { create } from 'zustand'
import { getPane } from './Pane'

export type DockSide = 'left' | 'right'
interface DockSlice { openPaneIds: string[]; activeId: string | null }

interface DockStore {
  left: DockSlice
  right: DockSlice
  /** Per-pane remembered width (px), clamped to the pane's kind band on write. */
  widths: Record<string, number>
  /** Open a pane at its home dock (registry `homeDock`); append if absent, then activate. No-op for unknown id. */
  openPane: (paneId: string) => void
  /** Close a pane in whichever dock holds it; active falls back to its neighbor; empty slice ⇒ activeId null (dock hidden). */
  closePane: (paneId: string) => void
  /** Open if closed, close if open (shelf / backlinks toggles). */
  togglePane: (paneId: string) => void
  /** Switch the active tab within a dock. Takes `side` (unlike the id-only actions) because the tab
   *  strip already knows its side — saves a registry lookup; do NOT "normalize" it into id-only (N3). */
  setActive: (side: DockSide, paneId: string) => void
  /** Set + clamp a pane's remembered width (store is the SOLE clamp site — see §2). */
  setWidth: (paneId: string, width: number) => void
  /** Test-only: reset to the empty initial state (mirrors `command-store.ts` `reset()`, used in
   *  `beforeEach` so cases don't leak across the module singleton). */
  reset: () => void
}
```

Behaviour the implementation must satisfy (these become the `dockStore.test.ts` cases, with `reset()`
in `beforeEach`):

- **`openPane('pdf')`** → looks up `getPane('pdf').homeDock === 'right'` → if `'pdf'` not in
  `right.openPaneIds`, append it; set `right.activeId = 'pdf'`. Idempotent: re-opening an already-open
  pane just re-activates it (no duplicate in the list).
- **`closePane('pdf')`** → find the side holding it; remove from `openPaneIds`; if it was active, set
  `activeId` to the previous neighbor (or the new last, else `null`). A `null` active ⇒ `DockHost`
  renders nothing (dock hidden).
- **`togglePane('shelf')`** → if `'shelf'` is open, `closePane`; else `openPane`.
- **`setWidth('backlinks', w)`** → `widths.backlinks = clamp(w, band(kind))` where band is derived from
  `getPane(id).kind` (utility 220–400, content 400–900). Unknown panes default to the utility band.
- A pane's **default width** (when `widths[id]` is unset) = its kind default (utility 280, content 600).
  `DockHost` reads `widths[activeId] ?? defaultWidthFor(activeId)`.

The width constants move out of `Dock.tsx` into a tiny shared `dock-widths.ts` (or stay in `Dock.tsx`
and are imported by the store) — the plan picks; the constraint is **one source of the band numbers**,
consumed by both the store's clamp and `DockHost`'s default. `Dock` itself no longer references them
(see §2, I4).

## §2 Components

### `DockHost({ side }: { side: DockSide })` — NEW (`src/renderer/src/panes/DockHost.tsx`)
Store connector. Selects `useDockStore(s => s[side])` + the active pane's width; returns `null` when
`activeId == null`; else renders `<Dock>`. The generic callbacks bind straight to store actions —
`onActivate → setActive(side, id)`, `onWidthChange → setWidth(activeId, w)`. **`onClose` is NOT a bare
`closePane`** — it's an App-supplied `onPaneClose(id)` prop, because closing certain panes has side
effects only App owns: closing `pdf` must also `openPdf(null)` (clear the persisted `pdf.openDocId`,
else the §4 boot-restore effect reopens it), and closing `backlinks` must clear `focusedId` (I1). App's
handler does `closePane(id)` + those side effects. Kept separate from `Dock` so `Dock` stays prop-driven
and store-free in tests.

### `Dock` — MODIFIED (`src/renderer/src/panes/Dock.tsx`)
Props change from `{ open, paneId, onClose, side }` to:
```ts
interface DockProps {
  side: DockSide
  openPaneIds: string[]
  activeId: string
  width: number
  onActivate: (paneId: string) => void
  onClose: (paneId: string) => void
  onWidthChange: (width: number) => void
}
```
- Header: `openPaneIds.length >= 2` → render `<DockTabs>`; else the existing quiet `title ×` header
  (verbatim look, now driven by `activeId`'s pane + `onClose(activeId)`).
- Body: `getPane(activeId)?.render()`.
- Resize handle: unchanged geometry/`side` mirroring. **The Dock is fully controlled — it holds NO
  local width state (I5).** Pointer-drag calls `onWidthChange(next)` every `pointermove`; `DockHost`
  routes it to `setWidth` (the store is the SOLE clamp site) and the clamped value flows back as the
  `width` prop. No Dock-side clamp, no double-clamp.
- **Width no longer derives from `pane.kind` inside `Dock` (I4)** — the kind→band/default mapping lives
  in the store (`setWidth` clamp) + `DockHost` (`widths[activeId] ?? defaultWidthFor(activeId)`). So the
  migrated `Dock.right.test.tsx` asserts only the side-mirroring chrome (border-left vs -right, resize
  handle at `-3px`); the band/default numbers are asserted in `dockStore.test.ts`.
- `open`/`null`-when-closed moves up to `DockHost` (it renders `null`, so `Dock` always has an
  `activeId`).

### `DockTabs` — NEW (`src/renderer/src/panes/DockTabs.tsx`)
A quiet horizontal strip of **text-label** tabs (principle 7; v21 tokens, no icon chrome). Each tab =
`getPane(id).title`; the active tab is visually marked (token-based, e.g. `--fg-1` vs `--fg-2` + a
1px bottom accent); each tab carries a `×` (visible on hover/active) → `onClose(id)`. Tab body click →
`onActivate(id)`. Keyboard: Left/Right arrow moves active tab when the strip has focus (cheap; full
roving-tabindex polish is fine to keep minimal — this is the only new keyboard affordance, distinct from
the deferred WAI-ARIA resize splitter). Esc is **not** owned here (no new Esc layer — the #18
esc-precedence audit notes nothing to add for tabs).

### Pane registry — MODIFIED (`src/renderer/src/panes/Pane.tsx`)
Add the backlinks pane:
```ts
{ id: 'backlinks', title: 'backlinks', homeDock: 'right', kind: 'utility', render: () => <BacklinksPaneBody /> },
```

## §3 Backlinks as a dockable pane

- **Extract `BacklinksPaneBody`** from `src/renderer/src/backlinks/BacklinksPane.tsx` — the list render
  (the `useQuery` + results, `BacklinksPane.tsx:103-130`), with NO props; it reads `{ focusedId, onJump }`
  from a new **`BacklinksContext`** (mirrors `ShelfContext` in `ShelfPane.tsx` exactly: an exported
  `BacklinksContextValue` interface, a `createContext` with a safe no-op default, a `useBacklinks()`
  hook). The overlay's header/close chrome (`BacklinksPane.tsx:71-102`) stays with the overlay shell,
  which now renders `BacklinksPaneBody` as its child — **one list implementation, two surfaces** (the
  body query needs only `focusedNoteId` + `onJump`, so the extraction is clean, no hidden coupling).
- **App provides `backlinksContextValue`** (memoized, like `shelfContextValue`) around the dock region:
  `{ focusedId, onJump: setFocusedId }`. `focusedId` stays App-owned `useState` (unchanged).
- **Deliberate-open command** (Decision 5): a dedicated App effect keyed on `[focusedId]` calls
  `register({ id: 'backlinks.open', label: 'Open backlinks', group: …, run: () => useDockStore.getState().openPane('backlinks') })`
  when `focusedId != null`, and `unregister('backlinks.open')` in its cleanup (i.e. when focus clears
  or App unmounts). **No `when` gate** (Decision 5 explains why a register-once `when` closure never
  updates). So the command is literally absent from `⌘K` unless a note is focused.
- **Overlay suppression** (Decision 4): the existing `{focusedId && <BacklinksPane …/>}` at `App.tsx:949`
  becomes `{focusedId && !backlinksDockOpen && <BacklinksPane …/>}`, where
  `backlinksDockOpen = useDockStore(s => s.right.openPaneIds.includes('backlinks'))`.

## §4 App wiring (`src/renderer/src/App.tsx`)

- **Shelf:** delete `const [dockOpen, setDockOpen] = useState(false)`; the shelf toggle (WindowFrame
  `onToggleDock`, StatusBar `onOpenShelf`) calls `useDockStore.getState().togglePane('shelf')` /
  `openPane('shelf')`. `dockOpen` reads (e.g. the WindowFrame indicator, which takes `dockOpen: boolean`
  unchanged) become `useDockStore(s => s.left.openPaneIds.includes('shelf'))`.
- **PDF open + boot-restore sync (C2 — load-bearing, do not drop):** today the dock mounts by pure
  derivation — `pdfPaneOpen = pdfOpenId !== null` (`App.tsx:156`) → `{pdfPaneOpen && <Dock/>}`
  (`App.tsx:939`), so a persisted `pdf.openDocId` reopens the dock on boot with no imperative call.
  Under the store this becomes an explicit **App effect keyed on `[pdfOpenId]`** (`pdfOpenId` from the
  existing `usePdfOpenId` settings query): when `pdfOpenId != null` and `'pdf'` is not open,
  `openPane('pdf')`. The user Open-PDF flow (`useOpenPdf` / `onChoosePdf`) ALSO calls `openPane('pdf')`
  on success (idempotent-safe). Closing the pdf pane (App's `onPaneClose('pdf')`, §2) calls **both**
  `closePane('pdf')` **and** `openPdf(null)` — clearing `pdf.openDocId` is what stops the `[pdfOpenId]`
  restore effect from instantly re-opening the just-closed pane. `pdfPaneOpen` is removed; visibility is
  the store slice. This pdf-specific persistence sync lives in **App**, not `DockHost` (generic).
- **Backlinks focus↔pane sync (I1/I2):** App's `onPaneClose('backlinks')` clears `focusedId` (I1); an
  App effect keyed on `[focusedId]` calls `closePane('backlinks')` when `focusedId == null` and the
  pane is open (I2). See Decision 4.
- **Replace the docks:** the two `<Dock>` JSX blocks (`App.tsx:750`, `:940`) become `<DockHost side="left"
  onPaneClose={handlePaneClose}/>` and `<DockHost side="right" onPaneClose={handlePaneClose}/>` in the
  same flex positions (left of `<main>`, right of `<main>`), where `handlePaneClose(id)` does the
  generic `closePane` + the pane-specific side effects above.
- Wrap the dock region in `BacklinksContext.Provider` (alongside the existing `ShelfContext.Provider`).

## §6 Future contracts (binding seams — reviewers check against `docs/canvas-vision.md`)

- **Cross-dock tab dragging** extends `DockTabs` + the store (`moveTab(paneId, toSide)`); the
  ordered-list model is built to accept it without reshape. A dragged content pane keeps its width
  band. No new state shape needed beyond the move action.
- **Left-dock multi-pane / shelf tab-mates** are already supported by the mechanism — a future pane with
  `homeDock: 'left'` makes the left dock show tabs automatically. No code change to land that capability;
  only a new pane registration.
- **AI-chat pane** registers as `{ kind: 'utility', homeDock: 'right' }` and slots into the existing
  tab grammar; only its body + feature wiring is new.
- **Dock-layout persistence** (if ever) serializes `{ left, right, widths }` — a self-contained store
  snapshot — behind a settings toggle; nothing else changes. Deliberately not built (vision).
- **The two dock-toggle chrome affordances** attach to `togglePane` on the home dock; they are pure
  view over the store.

## §7 ADRs to write

- **Dock as ordered-panes + active-tab, zustand-backed, in-memory** — records the model (a dock is a
  list, not a single pane), why zustand (second store after the registry; client view-state, no DB),
  and why no persistence yet. Alternatives: App `useState` (outgrew it), react-query (no DB), persisted
  workspaces (vision says not yet).
- **Backlinks dual surface (transient focus-overlay + deliberate dock pane)** — records the
  prior-feedback tension (`App.tsx:723-731`, quote at `:725-726`) and the keep-overlay-add-pane
  resolution + the suppression / close-clears-focus / focus-clear-auto-close rules.

## §8 Open questions / risks

- **Stage reflow on tab-switch width change** (Decision 3): tabbing pdf(600)↔backlinks(280) resizes the
  dock, so the canvas/feed reflows. Expected and intentional, but watch for a jarring jump — if it reads
  badly in dogfood, a short width tween is a cheap follow-up (not in v0.6.2 scope; flag for QA).
- **`Dock` prop-shape change is a hard-gate surface** (exported component contract) — this milestone
  goes through the full spec→plan→SDD workflow, not the inline-fix gate. The existing two Dock test
  files must be migrated in the same task that changes the props (no half-migrated state).
- **`BacklinksPaneBody` extraction must preserve the overlay's current behavior exactly** (focus list,
  jump, close) — the refactor is semantics-preserving; the overlay's own tests guard it.
- **Command lifecycle (RESOLVED — see Decision 5 / §3):** `backlinks.open` is registered/unregistered by
  a dedicated App effect keyed on `[focusedId]`, NOT a register-once + `when` gate (that closure would
  capture `focusedId` at mount and never update — `CommandMenu.tsx:93-96`).
