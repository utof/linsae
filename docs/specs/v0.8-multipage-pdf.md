# v0.8 — multipage PDF (continuous scroll + read-back)

Status: **reviewed** (round 1 applied; review cap reached per CLAUDE.md)
Branch: `v0.8/multipage-pdf`
Issues: **#154** (multi-page navigation), **#155** (re-open PDF at a note's `source_locator`)

---

## 1. Goal

Read a **whole** PDF in the right-dock reader — continuous vertical scroll across every page, at
book scale (500+ pages) — with excerpt-capture working on **any** page, and a read-back path that
re-opens a pdf-sourced note at the location it was captured from.

Today `PdfReader` renders exactly one page: `doc.getPage(1)` (`src/renderer/src/pdf/PdfReader.tsx:176`).
Pages 2..N of every imported document are unreachable. That is the hole this milestone closes.

### Success criteria

1. Opening a PDF shows page 1 and scrolls continuously to page N; the scrollbar reflects the whole
   document, not one page.
2. A 500-page PDF opens without a visible stall and scrolls at interactive framerate.
3. Resident canvas memory stays bounded **at every zoom level up to `ZOOM_MAX`** (§4.4), not only at fit.
4. Selecting text on **any** page produces an excerpt whose `source_locator.page` is that page and
   whose `rect` is correct in that page's PDF user space.
5. Excerpt-drag → canvas placement behaves exactly as in v0.6 for a page-1 selection (no regression).
6. A pdf-excerpt note offers "open source", which opens the reader for its `pdf_id`, scrolls to its
   `page`, and flashes its `rect`.
7. Reader position (page + within-page fraction) and zoom survive a restart.

### Non-goals

- **Annotation / highlighting inside the PDF** — the Stage-2 PDF milestone (`docs/canvas-vision.md` §Sequencing).
- **Zoom-out below fit-to-width.** `ZOOM_MIN` stays `1`. §4.5.
- **Tiled rendering** (rasterizing only the visible region of a zoomed page). This is the *correct*
  long-term answer to §4.4 and is deliberately deferred — §4.4 ships a pixel cap instead.
- **Text-offset re-anchoring** across document revisions. §5.3.
- **Horizontal / spread / facing-page scroll modes.** Vertical single-column only.
- **In-document text search.**
- **Multi-document concurrency.** `usePdfDocument` stays one-PDF-at-a-time.
- **Canvas `NoteCard` read-back** — §5.1; follow-up issue.

## 3. The model

The reader becomes a **vertically virtualized list of pages** inside `PdfReader`'s own root scroll
container (`PdfReader.tsx:243-256` — the element is the reader's, not the dock's). Each list item is
one page: a wrapper sized to that page's fit-width dimensions, containing a `<canvas>` and a
`TextLayer` div, rasterized only while inside the scroll window.

```
┌ scroll container (PdfReader root) ───────┐
│  ┌ spacer: virtualizer.getTotalSize() ─┐ │
│  │  [page 41]  ← translateY(start)     │ │   only windowed pages
│  │  [page 42]  ← rasterized            │ │   hold a canvas +
│  │  [page 43]                          │ │   text layer
│  └─────────────────────────────────────┘ │
└──────────────────────────────────────────┘
```

Three facts make this tractable at 500+ pages:

1. **A page's height is computable without rasterizing it.** `page.getViewport({scale:1})` gives
   unscaled dims; fit-width height is arithmetic. Scroll geometry never requires a raster.
2. **Those dims are scale-independent**, so once cached they stay valid across every zoom and dock resize.
3. **Most PDFs are dimensionally uniform**, so page 1's dims are a near-perfect estimate for the rest.

## 4. Architecture

### 4.1 Virtualization engine — `@tanstack/react-virtual`

**Decision: hand-roll the page list on `@tanstack/react-virtual`, not pdf.js's `PDFViewer`.**

`pdfjs-dist` ships a full web viewer (`pdfjs-dist/web/pdf_viewer.mjs`) that already does continuous
scroll. Rejected because it owns what this app must own: its own scroll container and scroll modes,
its own event bus, its own `pdf_viewer.css` visual language, and its own page lifecycle. Our
excerpt-drag, fit-to-width derived from live dock width, v21 tokens, and session persistence would
each be a fight against it — and the viewer build is a web-app artifact, not part of the stable
documented core API that `adrs/0043-pdf-engine-pdfjs-dist.md` committed us to.

`@tanstack/react-virtual` is already a direct dependency (`3.14.5`, symlinked to `virtual-core@3.17.3`),
is the subject of ADR 0005 and the whole feed-scroll saga, and was bumped as recently as v0.7.

**Verified API surface.** Read from
`node_modules/.pnpm/@tanstack+virtual-core@3.17.3/node_modules/@tanstack/virtual-core/dist/esm/index.d.ts`
and `pdfjs-dist@6.0.227` type defs. Every symbol below was confirmed to exist at the cited line.

*Virtualizer options:* `estimateSize` (55), `overscan` (66), `gap` (76), `indexAttribute` (77),
`initialMeasurementsCache` (78), `initialOffset` (72), `getItemKey` (73).

*Virtualizer instance:* `measureElement` (160), `resizeItem` (161), `getVirtualItems` (162),
`getVirtualItemForOffset` (166), `getOffsetForIndex` (172), `scrollToOffset` (173), `scrollToIndex` (174),
`getTotalSize` (177), `measure` (190), `measurementsCache` (98).

> `shouldAdjustScrollPositionOnItemSizeChange` is an **instance property (`index.d.ts:117`), not an
> option** — it is assigned after `useVirtualizer` returns. Repo precedent: `feed/Feed.tsx:679`,
> `dev/RevealPlayground.tsx:198`.

> `getMeasurements` is **private**; read `virtualizer.measurementsCache` (public, `:98`) instead.

*pdf.js v6:* `PDFDocumentProxy.numPages` (`api.d.ts:856`) — the virtualizer's `count`, the single
most load-bearing symbol here — `getPage` (:880), `getViewport({scale,rotation,offsetX,offsetY,dontFlip})`
(:1417), `streamTextContent` (:1466), `PDFPageProxy.cleanup(resetStats?) → boolean` (:1494),
`RenderTask.cancel(extraDelay?)` (:1612), `TextLayer` ctor `{textContentSource, container, viewport, images?}`

### 4.2 Page dimensions — the dims cache, and how it actually invalidates

New hook `usePdfPageDims(doc)` owns a **ref-backed** `Map<pageNumber, {w, h}>` of **unscaled**
viewport dims (`page.getViewport({scale:1})`).

- On document load it resolves **page 1 only** — a 500-page document costs exactly one `getPage` at
  open (criterion 2) — and stores its dims as `estimateDims`.
- Pages fetched for rasterization record their real dims.
- Pages inside the window + overscan get their dims resolved even if not yet rasterized.
  **This prefetch must be coalesced and cancellable**: a fast fling through 500 pages must not issue
  hundreds of `getPage` worker round-trips. Prefetch only for the settled window (skip while
  `virtualizer.isScrolling`), and drop results for pages no longer windowed.

`estimateSize(index)`:

```
dims = dimsRef.current.get(index + 1) ?? estimateDims
fitScale = containerWidth / dims.w          // per page — a landscape page still fits the width
return Math.floor(dims.h * fitScale * zoom) // == computePdfRender().cssH exactly
```

The page wrapper therefore carries **no border, padding, or shadow** — inter-page separation comes
from the virtualizer's `gap` option, not from box model on the item — or `estimateSize` under-reports.

#### 4.2.1 Invalidation — the part that does not happen for free

**Mutating the dims Map does *not* make the virtualizer recompute.** `getMeasurements` is memoized on
`[getMeasurementOptions(), itemSizeCacheVersion]`, and `getMeasurementOptions` deps are
`[count, paddingStart, scrollMargin, getItemKey, enabled, lanes, laneAssignmentMode]`
(`index.js:558-567`, `:589-590`). `estimateSize` is **not** a dep, and `memo` (`utils.js:1-15`) is
strict reference comparison. A new `estimateSize` closure alone changes nothing.

Two explicit invalidation paths, and no others:

1. **A single page's real dims arrive** → `virtualizer.resizeItem(index, exactHeight)`
   (`index.js:826-882`): it writes `itemSizeCache`, bumps `itemSizeCacheVersion`, and routes the
   delta through `shouldAdjustScrollPositionOnItemSizeChange` so the viewport does not jump when a
   page *above* the user resolves. This is the API built for exactly this.
2. **Global scale change** (zoom or dock width) → `virtualizer.measure()` (`index.js:1093-1099`),
   which bumps the version so every item re-derives from `estimateSize`. §4.5.

**Boot gate.** `containerWidth` is `0` until the `ResizeObserver` fires (`PdfReader.tsx:76-83`), which
makes `fitScale = 0` and every `estimateSize` return `0` → `getTotalSize() === 0`, with nothing to
recompute it afterwards. The virtualized list must therefore **not render until `containerWidth > 0`**.
Today's single-page reader sidesteps this with an explicit bail (`PdfReader.tsx:172`); the multipage
reader needs the equivalent gate.

**Why our own cache rather than the virtualizer's measurement cache:** the virtualizer caches *pixel
heights at the current scale*; `measure()` clears them all. On a 500-page book that would discard
hundreds of resolved measurements on every zoom step. Unscaled dims are scale-free, so after
`measure()` `estimateSize` returns exact heights for every page ever seen. `measureElement` stays
wired (cheap, corrects sub-pixel disagreement) but is not load-bearing.

This is ADR 0057.

### 4.3 Per-page render lifecycle

A `PdfPage` component per virtual item, keyed by page number.

**Mount / scale change:**

1. `doc.getPage(n)` → record dims (§4.2), `resizeItem` if this is new information.
2. `computePdfRender(containerWidth, dims.w, dims.h, dpr, zoom)` — **unchanged function**.
3. `capBitmapPixels(...)` (§4.4) → possibly-reduced backing-store size.
4. Size canvas backing store + CSS box as `PdfReader.tsx:186-200` does today, using the capped
   `transform`.
5. `page.render({canvas, viewport, transform})`; await.
6. `new TextLayer({textContentSource: page.streamTextContent(), container, viewport})`, set
   `--scale-factor` / `--total-scale-factor` to `viewport.scale`, `await textLayer.render()`.
   Both CSS vars are still set explicitly — the reason in `PdfReader.tsx:205-210` still holds
   (this markup has no `.pdfViewer .page` ancestor).
7. Register `{page, viewport, contentEl}` in the page registry (§4.7).

**On a scale change specifically, steps 8–10 below do NOT run.** Cancel the in-flight render, then
re-render into the **same** canvas element, exactly as today's reader mutates one canvas in place
(`PdfReader.tsx:186-202`). Zeroing the backing store per wheel notch across 3–5 pages would produce a
full-pane white flash on the reader's most-used interaction — a visible regression versus v0.6.

**Unmount only, in this order:**

8. `renderTask.cancel()`  → then `textLayer.cancel()`
9. `page.cleanup()`
10. `canvas.width = canvas.height = 0`, then deregister from the registry

The order is verified against pdf.js source: `PDFPageProxy.#tryCleanup()` (`build/pdf.mjs:15701-15716`)
returns `false` before touching `_intentStates` or `objs` while any intent state has
`renderTasks.size > 0 || !operatorList.lastChunk`. Calling `cleanup()` before cancelling is a no-op
*at that instant*. Note the accurate framing for ADR 0056: `cleanup()` sets `#pendingCleanup = true`
and does not clear it on failure, and the render task's completion handler calls `#tryCleanup()` again
(`build/pdf.mjs:15535`) — so an out-of-order call yields a **deferred** cleanup, not a permanent leak.
The order buys promptness, which at book scale is what matters.

`renderTask.cancel()` rejects the awaited promise with `RenderingCancelledException`; expected and
swallowed exactly as `PdfReader.tsx:227` does today.

### 4.4 Memory budget — a function of zoom, not a constant

`ZOOM_MAX = 5` (`computePdfRender.ts:54`) and backing-store area scales with **zoom²**. Unbounded,
one page at max zoom on a 900px dock at dpr 2 is `9000 × 11646 × 4 B ≈ 419 MB`; three to five
resident pages would be **1.25–2.1 GB**. That is the reachable worst case, and it is why criterion 3
is stated per-zoom.

**Two bounds, both required:**

1. **Pixel cap.** New pure function `capBitmapPixels(dims, maxPx)` — deliberately *separate* from
   `computePdfRender` so that verified function stays byte-identical and the page-1 no-regression
   claim (criterion 5) still holds:

   ```
   effectiveDpr = min(dpr, sqrt(maxPx / (cssW * cssH)))
   bitmapW = round(cssW * effectiveDpr);  bitmapH = round(cssH * effectiveDpr)
   transform = effectiveDpr !== 1 ? [effectiveDpr, 0, 0, effectiveDpr, 0, 0] : undefined
   ```

   CSS size is untouched, so beyond the cap the page CSS-upscales (progressively softer at extreme
   zoom) instead of allocating without limit. `MAX_PAGE_BITMAP_PX = 16_777_216` (2²⁴), matching
   pdf.js's own `maxCanvasPixels` default — the same trade-off its viewer makes. Below the cap the
   function is **identity**, so fit-zoom rendering is provably unchanged.

2. **Overscan is zoom-dependent:** `overscan = zoom > 1 ? 0 : 1`. At fit, prefetching a neighbour is
   cheap and makes scrolling smooth; when zoomed in the user is reading one page closely, the window
   holds ~1 page, and each page costs up to 4× more.

**Resulting ceiling:** ~3 resident × 17 MB ≈ **50 MB** at fit; ~1–2 resident × 67 MB ≈ **67–134 MB**
at `ZOOM_MAX`. Bounded, and independent of document length.

The smoke (§8) measures at `ZOOM_MAX`, not only at fit. Tiled rendering is the proper fix and is a
deferred non-goal.

### 4.5 Zoom

Unchanged model: `scale = fitScale × zoom`, ctrl/cmd-wheel, `clampZoom` to `[ZOOM_MIN=1, ZOOM_MAX=5]`.
Fit stays the floor; zoom-out-below-fit is additive, would break the "fit is the baseline" invariant
that `computePdfRender` and the persisted `zoom` are written against, and is not asked for by #154 —
deferred to an issue.

A zoom or dock-resize change must:

1. Capture the current anchor `{page, fraction}` (§4.6) **before** anything changes.
2. Let `containerWidth`/`zoom` update → `estimateSize` now yields new heights.
3. `virtualizer.measure()` to drop stale pixel measurements (§4.2.1 path 2).
4. Re-scroll to the captured anchor.

Without 1/4, a zoom step at page 300 throws the reader hundreds of pages away, because total size
changes underneath a fixed pixel offset.

### 4.6 One scroll primitive: the page anchor

A **page anchor** is `{page: number, fraction: number}` — `fraction` is the normalized position
within that page (`0` = top edge, `0.5` = halfway). Scale-independent, which is what makes it valid
across zoom changes and restarts.

**Pure core** (plain numbers, genuinely DOM-free and unit-testable):

```
anchorFromOffset(offset: number, item: {index, start, size}) -> {page, fraction}
offsetFromAnchor(fraction: number, item: {index, start, size}) -> number   // item.start + fraction * item.size
```

**Impure adapter** supplies `item` from `virtualizer.getVirtualItemForOffset(offset)` (`:166`) or
`virtualizer.measurementsCache[page - 1]` (`:98`), then calls
`virtualizer.scrollToOffset(offset, { align: 'start' })`.

`getOffsetForIndex` is **not** used. It returns `readonly [number, align] | undefined` — a tuple, not
a number (`index.d.ts:172`) — it reads `measurementsCache` as a side-effect of a prior measurement
pass, and with the default `align: 'auto'` it returns the *current* scroll offset whenever the item
is already on screen (`index.js:963`), so a read-back jump would frequently not scroll at all. It
also returns `0` when `!this.scrollElement` and clamps against `getMaxScrollOffset()` → `scrollHeight - clientHeight`
(`:918`), which under happy-dom is `0 - 0 = 0`. Alignment is therefore always passed **explicitly**.

**The same primitive serves all four jumps** — zoom re-anchor (§4.5), boot restore (§6), read-back
jump (§5.2), page-number jump (§7). One mechanism, one set of tests.

### 4.7 The excerpt seam — coordinate resolution across pages

The load-bearing risk of the milestone: excerpt-drag is why PDF exists in this app, and it currently
assumes one page, one viewport, one origin element (`useExcerptCapture.ts:42-52`).

**Page registry.** A **ref-backed** `Map<pageNumber, {page, viewport, contentEl}>`, populated and
removed by each mounted `PdfPage` (§4.3). Ref, not state: a state-backed registry mutated by N
children would re-bind the `mouseup` listener on every scroll (today's hook re-binds on
`[page, viewport, pageEl, contentEl, …]`, `useExcerptCapture.ts:104`). The handler reads `.current`
at event time. It holds only windowed pages, which suffices — a selection can only exist inside a
rasterized page.

**Each page wrapper carries `data-page-number={n}`** and `data-index={n-1}` (the virtualizer's
`indexAttribute` default).

**Capture algorithm:**

1. On `mouseup` in the scroll container, take the selection; bail if collapsed/empty (unchanged).
2. Resolve the **anchor page** from `range.startContainer`, handling the Element case:
   `(n.nodeType === 1 ? n as Element : n.parentElement)?.closest('[data-page-number]')`.
   A bare `.parentElement?.closest(…)` is wrong when `startContainer` is an Element — a legal Range
   boundary point is `(element, childIndex)` — and would climb past the page wrapper. Bail if absent.
3. Look up `{page, viewport, contentEl}` in the registry. Bail if missing.
4. `pageRect = contentEl.getBoundingClientRect()` — the anchor page's own content box.
5. **Filter** `range.getClientRects()` to rects whose vertical centre lies within `pageRect`. Without
   this, a cross-page drag yields a bounding box smeared across the page gap and a rect taller than
   the page. (Sound under partial scroll: both `getClientRects()` and `getBoundingClientRect()` are
   unclipped viewport-space boxes — ancestor overflow does not clip them.)
6. `clientRectsToPdfRect(viewport, pageRect, filteredRects)` — **unchanged function**.
7. `page: anchorPageNumber` in the locator.

Steps 4–6 are the v0.6 math with a different origin element — which is what makes criterion 5 checkable.

**Cross-page selections anchor to the start page** (ADR 0058):

- `quote` = the **full** selected text.
- `rect` = the start page's portion only (step-5 filter).
- `page` = the start page.
- `prefix`/`suffix`/`textStart`/`textEnd` come from the anchor page's `getTextContent()`. For a
  cross-page selection `fullText.indexOf(text)` returns `-1`, so the **existing** `idx >= 0` guards
  (`useExcerptCapture.ts:68-72`) already omit all four. Deliberate, honest degradation; no new branch.

Two facts to state rather than imply:

- **"Start page" is unambiguous regardless of drag direction.** Per the DOM standard a Range's start
  is always before-or-equal its end in *tree order*
  (https://dom.spec.whatwg.org/#concept-range), and the virtualizer emits items in ascending index —
  so `range.startContainer` is the visually **upper** page even on an upward drag. Direction is
  exposed only via `Selection.anchorNode`/`focusNode`. Recording this stops a later "fix" to
  `sel.anchorNode`.
- **Cross-page means *adjacent windowed* pages only.** Pages unmount past overscan, destroying the
  selection's end container mid-drag. ADR 0058 must say so rather than claim general cross-page support.

`SourceLocatorSchema` / `PdfLocatorSchema` are **unchanged** — no migration, no public schema churn,
every existing v0.6/v0.6.4 locator stays valid.

## 5. Read-back — open a note at its source (#155)

### 5.1 Entry point

An "open source" affordance on note cards whose locator is a **pdf excerpt**, i.e.
`source_locator.media === 'pdf' && source_locator.page != null`. The `page != null` clause matters:
`media === 'pdf'` alone also matches the document-level source note, which returns early at
`NoteBubble.tsx:255-269` into `PdfFeedNoteContainer` and never reaches the bubble body. This mirrors
the existing `isPdfDoc` discriminator.

**Store-driven, not prop-driven.** `NoteBubble` is rendered by the feed *and* by the generic thread
child list (`src/renderer/src/thread/ThreadView.tsx:937-949`), and the thread call-site passes no
`onOpenReader` — the feed passes it at `App.tsx:1417`. A prop-driven affordance would be silently
dead in threads, which is exactly where excerpt notes are read. The handler therefore calls the
read-back store directly.

`canvas/NoteCard.tsx` is a separate component with no `source_locator` knowledge (verified: no canvas
file references it). Since excerpts are placed on the canvas, that is a natural second entry point —
**deferred to a follow-up issue**, both because it is a distinct component and because §5.2's
reader-side handoff should prove itself on one surface first.

### 5.2 The jump — and the channel that carries it

The integration seam #155 actually turns on. `handleOpenPdfReader` (`App.tsx:841-847`) takes **only**
`pdfId`: it calls `openPdf(pdfId)` → `useOpenPdf` → `setSetting.mutateAsync` (an async SQLite write),
and `PdfReader` reads the id back out via `useSetting('pdf.openDocId')`. There is no path by which a
locator reaches the reader, and the reader mounts before the id arrives.

**New: a consumed-once pending-jump store** (`pdf/pendingJumpState.ts`, a zustand store beside
`pdf/excerptState.ts` — the existing idiom for reader-scoped transient state).

`openPdfAt(pdfId, locator)`:

1. `setPendingJump({pdfId, locator})`.
2. Write `pdf.openDocId` + `openPane('pdf')` via the existing `handleOpenPdfReader` path, so
   pane-opening semantics stay in one place.
3. `PdfReader` **drains** the pending jump once (a) the document matches `pdfId` and (b) the target
   page's dims are resolved (§4.2), then scrolls to `{page, fraction}` (§4.6) and flashes (§5.4).

**Ordering against §6 restore is explicit: a pending jump wins.** The persisted-position restore must
be skipped for that open, or the reader would restore to the last-read page and then fight the jump.

`fraction` derives from the rect's **visual top**, which in PDF user space is `y + h`, not `y` — see
§5.4. A locator with no `page` scrolls to page 1 and does not flash.

### 5.3 Which selector wins: `rect`, primarily

#155 proposes preferring `textStart`/`textEnd` + `quote`/`prefix`/`suffix` "for resilience across
pdf.js render drift", falling back to `rect`. **This spec inverts that.**

Verified reasoning: `rect` is stored in **PDF user space** — `clientRectsToPdfRect` divides the
viewport scale out at capture (`clientRectsToPdfRect.ts:22-23`). `getViewport` defaults `rotation` to
`page.rotate` at both capture and read-back (`build/pdf.mjs:15436-15441`) and `viewBox = page.view`
(the cropBox), so `convertToPdfPoint` inverse-maps into absolute cropBox-origin user space —
invariant under rotation, zoom, dpr and dock width. `userUnit` is folded into the transform
(`pdf.mjs:810`) and divided back out, and was already `scale *= userUnit` in v4
(`src/display/display_utils.js@v4.10.38:134`), so there is no cross-major shift there either.
Text-offset selectors, by contrast, depend on `getTextContent()` item ordering, which does vary
across pdf.js versions.

**But the categorical claim "there is no drift to be resilient against" is too strong**, and the
counterexample is in our own code path: `clientRectsToPdfRect` returns `[0,0,0,0]` for empty rects
(`:16`) and capture writes it unconditionally (`useExcerptCapture.ts:79-84`). So:

- `rect` is the anchor **when non-degenerate**; a `[0,0,0,0]` (or zero-area) rect scrolls to the page
  and **skips the flash**.
- `quote` is carried for the flash label and for a future different-edition re-anchor.
- Full text-based re-anchoring — which matters only when the underlying file has been *replaced* by a
  different edition — is deferred.

ADR 0059 records the reversal **with this accurate reasoning**, not the categorical version.

### 5.4 Flash — and the y-flip

PDF user space is **y-up**: `PageViewport` sets `rotateD = -1` for rotation 0 (`build/pdf.mjs:838-841`),
and `clientRectsToPdfRect` returns `[minX, minY, w, h]` where `minY` is the *lowest* PDF-space y
(`clientRectsToPdfRect.ts:22-29`) — i.e. the **visual bottom** of the selection.

So `pdfRectToCssBox(viewport, rect)` must map `convertToViewportPoint(x, y + h)` to the CSS
**top-left**. Mapping `(x, y)` places the flash one rect-height too low. This is stated here because
the naive "inverts `clientRectsToPdfRect`" phrasing would otherwise be encoded into the unit test as
a bug.

The overlay is absolutely positioned inside the target page's content box, accent-tinted, fading
after `FLASH_MS` — reusing the value the thread already uses (`600`, `src/renderer/src/thread/ThreadView.tsx:25`)
so the app has one "here it is" idiom. Tokens from v21; no new colors.

## 6. Persistence

`PdfViewV1Schema` (`zod-schemas.ts:535`) gains one optional field:

```ts
z.record(z.string(), z.object({
  zoom: z.number(),
  page: z.number().int().positive().optional(),   // reserved in v0.7, first written here
  pageFraction: z.number().min(0).max(1).optional(),
}))
```

Named `pageFraction`, not `offset` — the whole rationale below is that *pixel offsets* are the wrong
unit, so the field must not be called one. Additive and optional, so every persisted v0.7 payload
still parses — no migration. (`page` also gains the `.int().positive()` constraint it lacked.)

**The existing writer cannot be reused as-is.** `PdfReader.tsx:104-151` opens with:

```ts
const storedZoom = view?.[pdfId]?.zoom ?? 1
if (storedZoom === zoom) return   // :106-107
```

and is keyed `[zoom, pdfId]` (`:123`). A scroll at constant zoom hits that `return` and never writes,
and the effect never re-runs — success criterion 7 would fail silently. Required changes:

- Generalize the echo guard to compare the whole `{zoom, page, pageFraction}` triple.
- Add the anchor to the dep array.
- **Trailing throttle, not debounce, for the scroll-driven value.** A 200 ms debounce on a
  continuously-changing value keeps resetting and writes nothing during a scroll. The thread uses a
  trailing throttle for exactly this reason (`thread.scroll.v1`, `ThreadView.tsx:27-30`).

All three existing flush sites are preserved and reused — debounce timer, `visibilitychange`→hidden,
and doc-swap cleanup (`PdfReader.tsx:104-151`). Position must **not** get a second, differently-flushed
writer.

**Restore:** on document open, restore `zoom` first (existing behavior), then scroll to
`{page, pageFraction}` once that page's dims resolve — unless a pending read-back jump is queued,
which wins (§5.2).

**Why not `initialOffset` / `initialMeasurementsCache`** (the v0.7 feed technique, ADR 0055): those
seed a *pixel* offset, meaningful only if the measurement set matches. A document may reopen at a
different dock width or dpr, so the pixel offset is not portable; the scale-independent page anchor
is. Different problem, different tool — ADR 0055 is not contradicted.

## 7. UX surfaces

- **Page indicator** — floating, bottom-right, `42 / 517`, fading on scroll idle in the manner of the
  feed's `ScrollDatePill`. Reads the live anchor (§4.6).
- **Jump to page** — clicking the indicator turns it into a number input; Enter scrolls (§4.6), Esc
  cancels. Not a luxury at 500 pages.
- **Keyboard** — `PageUp`/`PageDown`/`Home`/`End` scroll a `div` only when it is focused, and the
  reader root has no `tabIndex` today (`PdfReader.tsx:243-256`). Add `tabIndex={0}` to the scroll
  container so native paging works; do not hand-implement it.
- **Loading state** — an unrasterized windowed page shows its correctly-sized empty box (dims known
  before raster), so scrolling never collapses layout. No per-page spinner.
- The **"Excerpt → place on canvas"** sticky bar is unchanged.

## 8. Testing

**Unit (pure, no DOM)**
- `anchorFromOffset` / `offsetFromAnchor` round-trip over plain `{index,start,size}` items; clamping
  at document start/end.
- `capBitmapPixels`: identity below the cap; correct `effectiveDpr` and `transform` above it;
  `ZOOM_MAX` case bounded by `MAX_PAGE_BITMAP_PX`.
- `estimateSize` from the dims cache: known page exact, unknown falls back to the estimate, per-page
  `fitScale` for a landscape page among portrait pages, and `containerWidth === 0` handled by the gate.
- Client-rect filtering: rects spanning two pages reduce to the start page's only.
- `pdfRectToCssBox`: maps `(x, y + h)` to the CSS top-left (the y-flip, §5.4).
- `computePdfRender` regression: existing tests pass untouched.

**Component (RTL + happy-dom)**
- Renders a windowed subset of a 500-page doc, not 500 canvases.
- Selection inside page 3's element → locator with `page: 3`.
- **Page-1 no-regression:** the v0.6 excerpt assertions produce an identical locator.
- Cross-page selection → `page` = start page, `quote` = full text, `textStart`/`textEnd` absent.
- Zoom preserves the anchor (`measure()` called, re-scroll issued with explicit `align`).
- Persistence writes `{zoom, page, pageFraction}` **on scroll at constant zoom** (the M7 regression)
  and flushes on `visibilitychange`.
- Read-back drains the pending-jump store, scrolls to the page, mounts the flash; a degenerate
  `[0,0,0,0]` rect scrolls without flashing.

**Integration (Vitest, real disk + real SQLite in `mkdtempSync`)** — required by CLAUDE.md §Tests every
batch and genuinely warranted here: §6 adds a persisted schema field. Round-trip `pdf.view.v1` through
the real settings store: write `{zoom, page, pageFraction}` → reparse → restore; and assert a stored
**v0.7-shaped payload** (no `pageFraction`) still parses, proving backward compatibility.

**Visual regression (Playwright `toHaveScreenshot()`)** — one shot of the reader at page 1 and one
mid-document, to pin the page gap and indicator chrome.

**happy-dom limitation — stated, not worked around.** happy-dom performs no layout
(`memory/progress.md` §Load-bearing facts): `clientWidth`/`offsetHeight` are 0, `getBoundingClientRect`
is zeroed, `canvas.getContext('2d')` returns null. Every geometry number above must be injected via
mocks. **Component tests cannot prove this feature works.** They pin logic; the smoke is the gate.

**Real-Electron smoke (mandatory, blocking)** — `scripts/pdf-multipage-smoke.mjs`, modelled on
`scripts/feed-scroll-restore-smoke.mjs`:
1. open → scroll to page N → the page-N canvas has non-zero pixels;
2. select text on page N → locator has `page: N` and a plausible rect;
3. zoom at page N → still near page N afterwards;
4. **zoom to `ZOOM_MAX` and sample memory** — the criterion-3 gate (§4.4);
5. quit + relaunch → reader restores to page N;
6. read-back from the captured note → lands on page N with the flash present.

**Fixtures.** `tests/fixtures/multi-feature.pdf` already exists (3 pages) alongside `tiny.pdf` (1 page).
3 pages is enough for the cross-page and page-N cases; add a mixed-page-size fixture only if the
landscape-among-portrait unit case cannot be covered synthetically. The 500-page document is generated
at runtime by the perf check, never committed.

## 9. Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Excerpt regression — the load-bearing path | **High** | §4.7 keeps both geometry functions byte-identical; explicit page-1 no-regression test; smoke step 2 |
| happy-dom proves nothing about scroll/canvas | **High** | Smoke is a blocking deliverable landing *before* read-back (§10) |
| Memory at high zoom | **High** | §4.4 pixel cap + zoom-dependent overscan; smoke step 4 measures at `ZOOM_MAX` |
| Missed virtualizer invalidation (B1 class) | **High** | §4.2.1 names the only two valid paths and the boot gate |
| Memory growth over a long book | Medium | §4.3 ordered teardown, §4.4 budget, smoke after a long scroll |
| Scroll drift on non-uniform docs | Medium | §4.2 dims cache + coalesced prefetch; `shouldAdjustScrollPositionOnItemSizeChange` keeps the viewport stable |
| Text-layer cost on dense pages | Low | Only windowed pages build one; `TextLayer.cancel()` on teardown |
