# v0.2 — Loopback HTTP shell (YouTube-embed origin fix)

> **Status:** spec + plan, awaiting fresh-Opus review. Corrective sub-work inside the v0.2 milestone (branch `v0.2/youtube-annotation`). Supersedes the `app://`-document decision in Plan 2 / the research doc's R3 and the embed-origin assumptions in `docs/plans/v0.2-youtube-annotation-3-player-thread-ui.md` (Plan 3) Task B1.

## 1. Problem (empirically established)

Plan 2 shipped an `app://bundle` custom-scheme document on the assumption (research doc `docs/research/2026-05-30-youtube-player.md` §R3 line 453 + line 47; comment `src/main/app-protocol.ts:5`) that a privileged `app://` scheme gives "an HTTP-style origin with a non-null Referer" and therefore behaves like `http://localhost` for YouTube embeds — i.e. avoids **Error 153**. That assumption was **never tested against a live embed**: `scripts/capture-smoke.mjs` captures with `videoId: 'smoke-test'` and never loads a YouTube iframe.

Three automated `_electron` spikes against the **built** app (Plan 3 Task B1) disprove it:

| Spike | Condition | Result |
|---|---|---|
| v1 | embed under `app://bundle`, `referrerpolicy` set | `ERROR:153` ×2; console: *postMessage target origin ≠ recipient origin `app://bundle`* |
| v2 | + `referrerpolicy` before load + main `webRequest` `Referer: https://www.youtube.com/` injection | `153` → `ERROR:152` ×2 |
| v3 | Referer injection + **known-embeddable** videos (`M7lc1UVf-VE`, `jNQXAC9IVRw`) | `ERROR:152` ×2, `getDuration()=0`, never cued |
| **dev** | **same videos under `http://localhost:3939`, no Referer injection** | **`state:5`→`1`, `getDuration` 1344/19, `seekTo`→33.4, ZERO errors** |

**Conclusion.** YouTube's IFrame embed rejects the `app://` document origin (read via `ancestorOrigins`/postMessage — not fixable by HTTP-header injection), exactly as it rejects Tauri's `tauri://` (research line 49). It **accepts `http://localhost`**. The only variable that flips success is the document origin.

## 2. Decision

**Serve the production renderer over a loopback `http://127.0.0.1:<port>` origin instead of `app://bundle`.** This is the minimal change that gives the embed a valid origin while preserving the existing renderer bundle, preload/contextIsolation, and `_media` attachment routing.

- A `node:http` server in main, bound to **`127.0.0.1`** on an **ephemeral port** (`listen(0)` → read `address().port`), serves GET requests for the built renderer (`out/renderer`) and the `/_media/` attachment route, **reusing the existing pure `resolveAppRequest` traversal guard** (`src/main/app-protocol.ts:42`).
- The window loads `http://127.0.0.1:<port>/` (prod). Dev is unchanged: it already loads `ELECTRON_RENDERER_URL` (the vite `http://localhost` dev server), which is why the embed already works in dev.
- `_media` becomes **same-origin** (`/_media/<yyyy>/<mm>/<sha>.png` relative to the document) in prod, which **dissolves** the A2 dev-vs-prod cross-scheme image problem. `mediaUrlFromPath` is revised to emit a relative `/_media/<tail>` URL; the CSP `app:` `img-src` token (A2) is removed; dev serves `/_media` via a vite proxy to the same loopback server (see §4, Task L4).
- The `app://` scheme + handler are **retired** (no longer the document origin and no longer needed for `_media`). `registerSchemesAsPrivileged(['app', …])` and `registerAppProtocol`/`registerAppScheme` are removed; `resolveAppRequest` (the pure resolver + its tests) is **kept and reused** by the loopback handler.
- No `webRequest` `Referer`/`Origin` rewriting is needed (the dev spike confirms a bare `http://localhost` origin works). Keep `host: youtube-nocookie` + `referrerpolicy="strict-origin-when-cross-origin"` on the player iframe (they are harmless and policy-aligned).

### Alternatives considered
- **`WebContentsView` overlay loaded from `youtube-nocookie.com`** — keeps `app://`, embed origin is youtube's own. Rejected for v0.2: a larger player-subsystem + capture-path redesign (capturePage from a separate WebContents, overlay geometry sync) than the loopback shell, for no extra benefit now. Revisit only if the loopback footprint proves unacceptable.
- **Keep `app://`, host only the player iframe under a nested `http://localhost` document** — hybrid; adds cross-origin postMessage plumbing between `app://bundle` and the localhost player frame for marginal benefit. Rejected.

## 3. Security analysis (must be reviewed)

A loopback HTTP server is reachable by **any local process** on the machine (not remote, since bound to `127.0.0.1`). Threat model for a single-user local notes app:

- **Served content:** the renderer bundle (app code — not secret) and `/_media/` screenshot attachments (**user content** — sensitive). A malicious local process that learns the port could `GET /_media/<path>` — but it must also know the `<yyyy>/<mm>/<sha>.png` path (sha256-named, not enumerable; no directory listing). No mutating endpoints exist (GET only; all writes stay on the IPC/preload bridge).
- **Baseline hardening (this spec):** bind `127.0.0.1` only (never `0.0.0.0`); ephemeral random port; **GET-only** (405 otherwise); reuse the `resolveAppRequest` traversal guard (400 on escape); no directory listing (404 on a dir); no `Access-Control-Allow-Origin` header (so other web origins can't read it via fetch). The server lifetime is the app process.
- **Optional hardening (flagged for review):** an unguessable per-launch **path-token prefix** (`http://127.0.0.1:<port>/<token>/…`) so a port-scanner can't reach any asset without the token. Feasibility depends on the renderer asset base being **relative** (electron-vite `base`); if assets are absolute (`/assets/…`) a token prefix needs a rewrite. Task L1 verifies the build `base`; if relative, include the token; if not, document port-only as the v0.2 baseline and file a hardening nit. **Reviewer: weigh token-prefix necessity vs. the base-path complication for a single-user binary.**

## 5. Acceptance criteria

- A production launch (`electron-vite build` + the loopback shell) loads a real YouTube video that **reaches cued/playing with no Error 153/152** (verified by the L6 smoke, mirroring the dev spike that already passed).
- `_media` attachment images render in **both dev and prod** with no CSP/cross-origin error.
- Traversal guard still rejects `/../` escapes (L2 test); the server is GET-only, `127.0.0.1`-bound, no CORS header.
- Full precommit chain green; no `app://` document references remain; `resolveAppRequest` + its tests retained.
- ADR 0008 reflects reality.
