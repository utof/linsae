**Date:** 2026-07-05 · **Reviewer:** fresh Opus subagent (adversarial, read-only) · **Scope:** committed Batches 0–3 on
`v0.7/session-persistence` (`git log main..HEAD`), spec `docs/specs/v0.7-session-persistence.md`, plan

## Summary

Overall health: **good** — the mechanism is sound, the defensive reads are complete, the fail-open latch (`snapSettled`)
is applied to all three `usePersistedWrite` writers (not `isSuccess`-only), and several subtle traps the spec called out
(backlinks clobber, dock hydrate echo, StrictMode double-hydrate, compacted-snapshot seeding) are correctly handled. I
found **1 Important, 3 Minor, 4 Nit** issues, plus a solid set of things I checked and cleared. The one finding worth
acting on before merge is a **boot-ordering race that drops the restored PDF dock pane** — a cross-cutting regression
between v0.6's `pdf.openDocId` restore and v0.7's new `dockStore.hydrate`, invisible to every per-task review because it
only emerges when both boot effects run in the same mount, and the component tests mock `usePdfOpenId` synchronously so
the async ordering never occurs. No crashes, no data-corruption, no security issues. A clean-ish bill with one real bug.

Counts: **Critical 0 · Important 1 · Minor 3 · Nit 4.**

## Findings (most-severe first)

### 1. [Important · CONFIRMED] Dock `hydrate` clobbers the restored PDF pane when `pdf.openDocId` resolves before the snapshot

**Where:** `src/renderer/src/App.tsx:234-236` (pdf-open effect) vs `App.tsx:562-566` (dock hydrate effect);
`src/renderer/src/panes/dockStore.ts:179-200` (`hydrate` full-replaces the side slice, filtering content panes).

**Mechanism.** Two independent async boot effects both write the dock store, with **no ordering coordination**:

- `App.tsx:234` — `useEffect(() => { if (pdfOpenId != null) useDockStore.getState().openPane('pdf') }, [pdfOpenId])`.
  `pdfOpenId` comes from `usePdfOpenId()` → `useSetting('pdf.openDocId', null)` → its **own** react-query query
  (`['setting','pdf.openDocId']`, `use-setting.ts:12-15`), resolving on an independent timeline from the snapshot.
- `App.tsx:562` — the dock hydrate effect calls `useDockStore.getState().hydrate(snap.data.dockLayout)`, and `hydrate`
  does `set(() => ({ left: filterSide(...), right: filterSide(...), … }))` — a **full replace** of both side slices
  (`dockStore.ts:193-199`), with `filterSide` dropping every content-kind pane (`dockStore.ts:181-182`). `pdf` is
  `kind:'content'` (`Pane.tsx:37`).

Failure scenario (restore a session that had a PDF open): if the single-key `settings:get` for `pdf.openDocId` resolves
**before** the 7-key `settings:getMany` (it does strictly less work, so this is the *likely* ordering, and if both
resolve in one batched render the pdf effect at `:234` is declared **before** the hydrate effect at `:562` so it runs
first regardless), then: `openPane('pdf')` adds pdf to `right` while `hydrated` is still `false` → `hydrate` then runs
(`if (…hydrated) return` is still false) → the full-replace **drops pdf** (content pane filtered) → the pdf effect never
re-runs (`[pdfOpenId]` unchanged) → **the PDF dock pane is gone for the whole session** even though `pdf.openDocId` is
still set. This is a regression *introduced* by v0.7: before this milestone the dock started empty and the `:234` effect
was the sole boot opener, so nothing clobbered it.

Not caught by tests: `App.test.tsx:1190` ("not empty content panes") provides a `dock.layout` with `pdf` but leaves
`usePdfOpenId` mocked to `null` (`App.test.tsx:116-117`); the pdf-restore test (`:906`) sets `usePdfOpenId` to a value
**synchronously** with no `dock.layout`. No test exercises both together with realistic async timing, so the race is
structurally invisible to the suite.

**Suggested fix.** Re-assert the content pane *after* hydrate. Simplest: in the hydrate effect, after
`hydrate(...)`/`setState({hydrated:true})`, `if (pdfOpenId != null) useDockStore.getState().openPane('pdf')`; or add
`hydrated` (a store selector) to the `:234` effect's deps so the opener re-fires once the dock is hydrated. Either makes
"utility panes from layout + content panes from media context" order-independent, which is the design the spec intended
(§Key flows step 2).

### 2. [Minor · CONFIRMED] The dock-layout writer has no `visibilitychange` flush — the one writer that can silently lose its last change on quit

**Where:** `src/renderer/src/App.tsx:571` — `useEffect(() => subscribeDockPersist((s) => void api.settings.set('dock.layout.v1', s)), [])`;
`dockStore.ts:251-271` (`subscribeDockPersist` is a bare `setTimeout` debouncer, **no** visibilitychange/beforeunload
listener). The only `visibilitychange` flush in the codebase lives inside `usePersistedWrite`
(`usePersistedWrite.ts:34-44`), which the dock does **not** use.

Spec §Write-through: *"Flush all pending writes on `document.visibilitychange` when `document.hidden` (authoritative)"*;
Risks: *"`visibilitychange=hidden` is authoritative."* The three `usePersistedWrite` surfaces (ui.session, thread.scroll,
feed.scroll) honor this; the dock does not. Scenario: resize a dock or toggle a pane, then Cmd-Q within the 400 ms
debounce → the change is lost with no last-chance flush, contradicting the "authoritative" guarantee for the writer most
likely to have *just* changed when the user quits (you resize, then close). Bounded (≤ one debounce interval) and
non-crashing, hence Minor — but it's a real spec-contract gap a per-task review (Task 1.5 built the subscriber in
isolation) could not see.

**Suggested fix.** Either route the dock through `usePersistedWrite` (feeding it a memoized `SerializedDock` from a
`useDockStore` selector), or add a `visibilitychange`→hidden flush inside `subscribeDockPersist` that fires the pending
`write(snap)` immediately.

### 3. [Minor · CONFIRMED] Boot "restore echo": the first-render skip doesn't cover async-landed restores, so every boot re-writes the just-restored value once

**Where:** `usePersistedWrite.ts:19-32` (skips the first *enabled* render only), against three writers whose restored
value arrives **after** that skip:
- `ui.session.v1` (`App.tsx:845-849`) — the restore IIFE (`App.tsx:824-838`) `setFocusedId`/`openThread`s *after* the
  writer's first enabled render skipped `{null,null}`, so the restored `{…}` is scheduled as a (redundant) write.
- `thread.scroll.v1` (`App.tsx:876`) — the map is seeded in an effect (`App.tsx:856-861`), landing after the writer
  skipped `{}`, so `saved` is written back.
- `feed.scroll.v1` (`App.tsx:882`) — the restore's programmatic scroll (`Feed.tsx:693-698`, or the `initialOffset`
  seed) fires the capture listener (`Feed.tsx:733-764`) → `setFeedScroll` → a write of the just-restored position.

Each is a redundant `settings.set` of (essentially) the value already on disk — one extra IPC + SQLite write per key on
every boot that restores something. Harmless to correctness (values match, or in the feed's `index`/`bottom` case
coarsen to the same *place*), but it defeats the "don't echo the hydrated value" optimization the skip was written for,
and #2's dock writer inherits the same echo when the post-hydrate `openPane('pdf')` (finding #1's good path) triggers a
`dock.layout` write. Rank Minor (perf/write-amplification only).

**Suggested fix (optional).** Accept it (bounded, one write/key/boot) or gate each writer's arm on a per-surface
"restore-applied" latch instead of `usePersistedWrite`'s render-count skip. Not worth churn unless write volume matters.

### 4. [Minor · CONFIRMED] Orphaned backlinks pane when the persisted focused note was deleted between sessions

**Where:** `App.tsx:504-517` (the `[focusedId]` auto-open/close-backlinks effect) + `App.tsx:824-838` (stale-drop leaves
`focusedId` null) + `dockStore.hydrate` restoring a saved-open `backlinks`.

Scenario: user quits with a note focused **and** the backlinks pane open (the normal coupled state); that note is deleted
before the next launch. On boot: `hydrate` re-opens `backlinks` from the saved `dock.layout`; the ui.session restore
calls `api.notes.get(deletedId)` → null → `focusedId` stays `null` (correct stale-drop). But the `[focusedId]` effect
only ran once, at mount, when `focusedId` was already `null` and the dock was still empty (`right.openPaneIds` did not yet
include `backlinks`), so its `else if (…includes('backlinks')) closePane` branch was a no-op; it never re-runs because
`focusedId` never changes from its mount value. Result: an **empty backlinks pane** (no subject) sits open — exactly the
"dead chrome with no subject" the effect's own I2 comment says it wants to avoid. Self-heals on the next focus toggle.
Narrow trigger (focused note deleted between sessions), non-crashing → Minor/low.

**Suggested fix.** After the stale-drop resolves `focusedId` to null, if `backlinks` is open with no focus, close it — or
have the restore explicitly reconcile the backlinks pane against the restored `focusedId`.

### 5. [Nit · CONFIRMED] `thread.scroll.v1` stale entries are never pruned — contradicts the spec and grows monotonically

**Where:** seed at `App.tsx:856-861` sets the **whole** saved map verbatim (`setThreadScrollMap(saved)`), and
`ThreadScrollV1Schema = z.record(z.string(), z.number())` (`zod-schemas.ts:529`) performs no filtering. Spec §Data model
(line 144) says *"entries for missing roots dropped on read"* and §Stale references (line 259) *"pruned lazily"* — neither
happens. A `rootNoteId → scrollTop` entry for a since-deleted thread is never removed; the map accumulates one number per
plain/pdf thread ever scrolled, forever. Functionally harmless (a deleted root can't be opened, so its entry is never
read/applied), but the spec's stated prune does not exist and the value grows unbounded. Same lazy-prune gap applies to
the (out-of-scope, uncommitted) `composer.draft.thread` map by the same pattern.

**Suggested fix.** On seed, intersect `saved` with the live note ids (drop unknown roots), or prune opportunistically when
`onThreadScroll` runs. Cheap.

### 6. [Nit · CONFIRMED] `feed.scroll.v1` payload is not "roughly the overscan window" — it's every row measured since mount

**Where:** spec §Data model (lines 153-154) claims the snapshot is bounded to *"roughly the overscan window … so the JSON
stays small."* Actual behavior: `virtualizer.takeSnapshot()` (virtual-core 3.17.3, `index.js:1068-1081`) returns every
measurement whose key is in `itemSizeCache`, and `itemSizeCache` **accumulates** every row rendered this session and is
never pruned. `Feed.tsx:88-92` and `:743-748` even document this ("returns EVERY row measured so far"). So after scrolling
the full feed the persisted array is ~all notes (up to the 500-note page), not overscan-bounded — ~40 KB JSON written
(debounced) on scroll. Also `start`/`end`/`lane` are persisted but unused by the seed path (virtual-core only harvests
`key→size`, then rebuilds densely by index — `index.js:622-660`; verified, and why the compacted snapshot is *safe*). No
correctness impact; a spec inaccuracy + mild storage/write cost.

**Suggested fix.** Update the spec's "bounded" claim, or cap/trim the persisted snapshot (e.g. keep only the visible ±
overscan slice, or drop the unused `start/end/lane`), since only `key`+`size` (seed) and `key`+`index` (match) are used.

### 7. [Nit · PLAUSIBLE] Generic-thread scroll restore is skipped for a childless-but-tall root

**Where:** `ThreadView.tsx:580-593` — the restore layout effect returns early while `target > 0 && sorted.length === 0`
(waiting for children to establish scrollHeight). A plain-note thread whose **root body alone** is tall enough to scroll
but has **no** comment-on children keeps `sorted.length === 0`, so a saved non-zero `scrollTop` is never re-applied
(`scrollRestoredRef` also never latches, but `[sorted.length]` never changes so it can't retry). Edge case (long root, no
replies, scrolled) → Nit.

**Suggested fix.** Gate on the scroller's own `scrollHeight > clientHeight` (or simply attempt the set and let the browser
clamp) rather than child count.

### 8. [Nit · CONFIRMED] Boot-restore IIFE swallows an `api.notes.get` *rejection* as an unhandled promise rejection

**Where:** `App.tsx:829-838` — `void (async () => { … await api.notes.get(…) … })()` has no `.catch`. `notes.get`
*resolves* null for a missing id (the stale-drop path, fine), but an IPC-level **rejection** during boot restore escapes
as an unhandled rejection (boot still fails open — nothing restores — but it's noisy and uninstrumented). This is an
additional swallow/observability point beyond the snapshot-read + persist-write pair already tracked in issue #173.

**Suggested fix.** Wrap the IIFE body in try/catch (log + continue), and fold this call site into #173's observability
pass.

## Verified-correct (checked and cleared)

- **Object-form test assertions (hunt item #4): clean.** Every `settings.set`/`notes.get` assertion on the branch uses
  the IPC object shape — `usePersistedWrite.test.tsx:34,39,58` (`{key,value}`), `App.test.tsx:1293` (`{id:'t1'}`),
  `App.test.tsx:1294` (`.not.toHaveBeenCalledWith({id:'n1'})` — the negative is *meaningful* because it matches the real
  `{id}` shape, so it would catch a thread-precedence regression), `App.test.tsx:1321` (`thread.scroll.v1` object form),
  `use-setting.test.tsx`, `NoteCard.test.tsx`. A positional-first-arg grep across all v0.7 test files returned **zero**
  hits. `usePersistedWrite.test.tsx:9-12` documents the layering explicitly. No positional false-pass.
- **Fail-open latch on all writers (hunt item #2): correct.** All three `usePersistedWrite` calls use
  `enabled: snapSettled` (`= snap.isSuccess || snap.isError`), not `isSuccess` (`App.tsx:848,876,882`); the dock arms
  unconditionally at mount and relies on the `hydrated` latch, which is set on the error path too
  (`App.tsx:565`). A transient snapshot-read failure cannot permanently disable any writer. `App.test.tsx:1217` proves
  boot completes on a rejected `getMany`.
- **Boot gate: correct.** Splash lift and Feed first-mount both gate on `snapSettled` **and** notes-present
  (`App.tsx:546-553`, `App.tsx:1255`), so Feed's first render receives `restore` (the load-bearing condition), and the
  error path fails open instead of white-hanging.
- **Defensive reads complete (hunt item #3).** All 7 keys go through `safeParseOr(schema, …, default)`
  (`useSessionSnapshot.ts:28-36`); every committed consumer is null-safe (`snap.data?.…`, `if (!s) return`,
  `pickFeedRestore(null)`); on `isError` (`snap.data === undefined`) every path degrades to its default. The
  `z.partialRecord` choice for `widths`/`collapsed` (`zod-schemas.ts:498-499`) is the correct one — `z.record(z.enum())`
  is exhaustive in zod v4 and would discard the whole layout on a single-side map.
- **Snapshot staleness (hunt item #6): no live-reader bug.** Every committed consumer treats `snap.data` as boot-initial
  only (one-shot dock hydrate, one-shot restore, one-shot thread-scroll seed, Feed first-render seed). `staleTime:
  Infinity` + global `refetchOnWindowFocus:false` + `retry:false` (`query-client.ts:29-34`) means the query never
  refetches mid-session, so the `didRestoreSession`-guarded restore effect cannot spuriously re-fire on window focus
  (a real concern I specifically chased and cleared).
- **Feed seed with a compacted snapshot: safe.** `takeSnapshot()` is measured-only/compacted, but virtual-core
  consumes `initialMeasurementsCache` purely to seed `itemSizeCache` by `key`, then rebuilds a dense measurements array
  by index from `min=0` (`index.js:622-660`), so sparsity/offset in the persisted snapshot cannot corrupt the restore.
- **`pickFeedRestore` branch order: matches spec.** `atEnd` is checked before `indicesMatch`
  (`feedScrollRestore.ts:16-17`), so a bottom-anchored exit always restores to the *new* bottom (spec §Feed scroll), even
  when indices still match.
- **Dock hydrate echo + StrictMode guards: correct.** `subscribeDockPersist` latches on the `prev.hydrated → s.hydrated`
  transition (`dockStore.ts:254-255`) rather than reference equality (zustand v5 passes fresh state), so the hydrate is
  never echoed; the App hydrate effect guards `if (…hydrated) return` (`App.tsx:563`) against a StrictMode double-invoke;
  the returned unsub clears the pending timer (`dockStore.ts:267-270`).
- **Backlinks-suppression: robust.** `restoredFocusRef` holds the specific restored id and is value-matched+cleared
  (`App.tsx:510-513`), not a bare boolean, so a genuine focus to a *different* note racing the restore can't be
  swallowed. Tested at `App.test.tsx:1238`.
- **YouTube thread-scroll exclusion: structural.** The v0.7 restore/persist refs are bound only in the generic branch
  (`ThreadView.tsx:875-877`); the youtube `notesPane` uses `onNotesScroll` and never the `onScroll` prop
  (`ThreadView.tsx:631-633`), so no youtube root ever enters `thread.scroll.v1`.
- **Writer value memoization / re-render churn (hunt item #7): fine.** `ui.session` value is `useMemo`'d
  (`App.tsx:847`); `threadScrollMap`/`feedScroll` are stable state refs; `usePersistedWrite`'s effect deps are primitives
  (`opts.enabled`, `opts.debounceMs`), so a fresh `opts` object literal each render does not re-arm. A ~5 Hz scroll
  re-render re-arms only the one writer whose value actually changed.
- **Thread-scroll seed-before-openThread ordering (hunt item #1): sound.** The synchronous `setThreadScrollMap(saved)`
  in the seed effect and the async `openThread` (after `await api.notes.get`, a later macrotask for a real IPC) both land
  as default-lane updates that batch, so `ThreadView` mounts with `threadScrollMap[root]` already seeded; the
  `restoreTargetRef` snapshot-once (`ThreadView.tsx:575`) then guards against the "echo stomp" prop feedback loop.
