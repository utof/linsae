# Technology & Architecture for a Semantic-Zoom Mind-Map / Graph Surface (Local-First Electron Note App)

## TL;DR
- **Build the core surface yourself as a hybrid renderer (DOM cards near + canvas/WebGL dots-and-edges far), driven by your own SQLite-backed property graph — do NOT adopt a turnkey canvas SDK as the foundation.** tldraw (the most capable whiteboard SDK) is disqualified on licensing (source-available, watermark, paid production license) and on owning its own layout/state; React Flow and the WebGL graph libraries (Sigma/Cytoscape) each solve only one end of your zoom continuum. Your two fixed principles (position is view-state; nodes are live references) plus "custom layout is first-class" mean the substrate must be a thin, position-accepting renderer you control.
- **The semantic-zoom continuum is a renderer-swap problem, not a single-library problem.** No existing OSS library natively does "readable markdown card → title → dot" across a 60fps pan/zoom from 500 cards to 10,000 dots. The proven pattern (Figma, tldraw, gravity-ui) is: spatial index (rbush/flatbush) → viewport culling → LOD thresholds that swap DOM cards for canvas/GL primitives. Borrow individual MIT/ISC libraries (d3-force, graphology, perfect-freehand, rbush) rather than a framework.
- **Freehand ink is well-supported and not foreclosed by this architecture**, because perfect-freehand (MIT, by tldraw's founder) is a pure point→polygon function you render however you like; strokes live in a per-canvas stroke table and "promote strokes to node" is a data operation (insert a `notes` row + `node_layouts` row, attach stroke IDs) your model already accommodates.

## Key Findings

1. **The hard requirement (one surface, semantic zoom) rules out every single-purpose library as *the* surface.** Graph-viz libraries (Sigma.js/Cytoscape) render dots-and-edges superbly at 10k+ but cannot show rich, editable markdown cards with KaTeX. DOM/React node libraries (React Flow) render rich cards beautifully but degrade as DOM node counts climb into the low thousands. The continuum *between* these is exactly the gap, and it is bridged by an LOD swap you orchestrate, not by any one library.

2. **tldraw is the closest existing "semantic-zoom + ink + cards" engine, and it is disqualified for the core surface on three independent grounds:** (a) **License** — the tldraw SDK is *source-available, not open source*; production use requires a license key, and the default/hobby license forces a "made with tldraw" watermark on the canvas. (b) **Layout ownership** — tldraw owns its own store, camera, and shape state; your "run my own force sim in a worker and stream positions at 60fps" requirement fights its architecture. (c) **Live-reference model** — tldraw shapes are the source of truth for their own data; your notes must remain canonical in SQLite with positions as separate view-state. It remains the best *reference implementation* to study (its LOD, culling, and perfect-freehand integration are documented and excellent).

3. **The rendering-substrate decision is settled by primary evidence: DOM is the wrong substrate for the far-zoom whole-vault view, but the right one for near-zoom cards.** Therefore: hybrid.

4. **Custom layout integration is a solved pattern with a clean contract.** d3-force exposes an explicit `simulation.tick()` / `simulation.stop()` API designed for manual stepping in a worker; graphology ships `FA2Layout` web-worker supervisors. The standard production pattern (e.g., markuslerner/d3-webworker-pixijs) runs the CPU-bound simulation in a worker at a lower rate and interpolates positions on the main thread for smooth 60fps.

5. **Obsidian/Roam graph views fail as *hairballs* for product reasons, not just technical ones** — and this is the most important unknown-unknown finding: a force-directed flat graph of typed-but-undifferentiated links becomes "navigationally useless" past a few hundred notes. Tools whose spatial surfaces people *live in* (Heptabase, Scapple, Tinderbox, MarginNote) are **manual-placement-first with optional structure**, not auto-layout-first. This challenges the MVP's emphasis on force layout.

## Details

### §1 Rendering substrate — verdict: hybrid, DOM-near / canvas-or-WebGL-far

**Primary evidence that DOM does not scale to the far-zoom target.** Figma's co-founder/then-CTO Evan Wallace documented why they built a custom WebGL renderer instead of using the DOM: "HTML and SVG contain a lot of baggage and are often much slower than the 2D canvas API due to DOM access. These are usually optimized for scrolling, not zooming, and geometry is often re-tessellated after every scale change." Figma ultimately built "our own DOM, our own compositor, our own text layout engine." This "optimized for scrolling, not zooming" point is precisely the pan/zoom workload of a mind map. Google's own tooling quantifies the DOM ceiling: Lighthouse "warns when the body element has more than ~800 nodes" and "errors when the body element has more than ~1,400 nodes"; as of Lighthouse 13 (Oct 2025) the audit became the "Optimize DOM size" insight and now triggers on actual style-recalc/layout work exceeding 40ms (a "large" style recalc affects >300 elements; a "large" layout involves >100 layout objects). A 10,000-node readable-card DOM is therefore a non-starter; even 500 rich cards each containing markdown + KaTeX sub-trees can blow past these thresholds in aggregate.

**Confirmation from a direct competitor.** Obsidian Canvas is DOM+SVG inside Electron/Chromium (confirmed by community fixes that manipulate `.canvas-wrapper` CSS and set SVG `shape-rendering: optimizeSpeed`, and by a developer's explicit wish for a "real HTML Canvas element + GPU" alternative that doesn't yet exist). Users report lag onset at roughly **40–200 cards depending on hardware and resolution** — e.g., ~100 single-line cards freeze on panning on a Ryzen 9 5900X/RTX 3060; ~140 nodes lag on an M1 Max — with the dominant failure being layout/paint churn as nodes enter/exit the viewport during pan/zoom, exactly the DOM weakness Figma described. Obsidian's team acknowledged the enter/exit-viewport bug ("This bug will be fixed in v1.7.2"). This is the single most relevant real-world data point you have: a beloved, well-funded, Chromium-based competitor hits a wall at low-hundreds of DOM cards.

**But DOM is right for near-zoom.** Rich markdown + KaTeX + (future) in-place editing inside cards is enormously cheaper to build and maintain with React + your existing react-markdown/rehype-katex stack than re-implementing text layout on canvas (Figma had to build "our own text layout engine"). For a solo/LLM-assisted team, re-implementing rich text + LaTeX on WebGL is a non-starter.

**The hybrid resolution (what the strongest products actually do):**
- **Near zoom (cards readable, ≤~500 in viewport):** Render nodes as absolutely-positioned React DOM cards on a single CSS-transformed layer (`transform: translate()/scale()` on a container). Cull aggressively — only materialize cards whose bounds intersect the viewport. tldraw uses exactly this: CSS-transform positioning + `display:none` culling driven by a spatial index — per its docs, "a canvas with 10,000 shapes might only render 50 if the rest are out of view," giving O(1) rendering relative to *visible* shapes.
- **Far zoom (dots, up to 10k):** Swap to a single canvas/WebGL layer that draws dots and edges from typed-array position buffers. gravity-ui (Yandex) documented this exact dual approach: "At far zoom levels… we draw lightweight Canvas primitives; as the camera zooms in… we switch to HTML mode with full detail," backed by rbush for culling — their stress test renders "111k nodes and 109k connections… in ~60ms… ~15–20 FPS" on an M3.
- **Edges:** Draw on a canvas/SVG layer beneath cards. At mind-map zoom, edge-routing quality matters (MarginNote tree-ish aesthetic); at dot zoom, straight lines suffice.
- **Ink:** A dedicated stroke layer (canvas) co-planar with the transform.

**LOD thresholds — where they live:** Keep an explicit, debounced `zoomTier` state (e.g., `card | title | dot`) derived from camera `z`, *not* recomputed per frame. tldraw's `getEfficientZoomLevel`/debounced-zoom pattern is the model: it returns the zoom from when the camera *started* moving when there are many shapes, avoiding per-frame re-render thrash. Avoid pure CSS `transform: scale()` of text as the LOD mechanism — Chromium produces blurry text and sub-pixel artifacts during scaled transforms (widely reported; fixes are hacky: `translateZ(0)`, even-pixel dimensions, removing `will-change`). Instead, swap representations at tier boundaries rather than scaling a card down to a dot, and render cards at integer (1:1) scale, repositioning via translate only.

**Verdict: compose primitives by hand for the core surface.** Reasoning: (1) Your two fixed principles plus "custom layout is first-class, externally driven" disqualify any library that owns layout/state/identity — that eliminates tldraw, Excalidraw, and partially React Flow as *the* surface. (2) No single library spans the card→dot continuum, so you are orchestrating an LOD swap regardless; building on a library only adds a fighting-the-framework tax. (3) The primitives you need are all healthy, MIT/ISC, large-corpus libraries (d3, rbush, graphology, perfect-freehand) — ideal for LLM-assisted development. (4) The "graph data model is the stable core; views are replaceable" principle is best served by owning the thin view layer.

**Second choice / hedge:** If hand-composition stalls, **React Flow (MIT, React 19-ready) for an MVP-only "cards + typed edges + manual drag" milestone**, with the explicit understanding that it does not deliver the far-zoom dot view and you will replace its renderer for the 10k path. gravity-ui's independent assessment is that React Flow is "good when you're confident graphs won't exceed 100–200 blocks" — so treat it as a fast UX-prototyping accelerator within that ceiling, not the 10k engine. Use its node `position` controlled-component API as your externally-driven-layout seam (it accepts your computed positions directly). Do **not** build ink or the whole-vault view on it.

**What would flip the decision:** (a) If tldraw shipped a permissive license tier → reconsider it as the core (its LOD/culling/ink are genuinely best-in-class). (b) If a benchmark on your target integrated-GPU hardware shows React Flow holding 60fps at ~2,000 custom markdown cards → React Flow could carry MVP further. (c) If you decide the far-zoom whole-vault dot view is *not* MVP → the pressure for a custom WebGL path drops and React Flow becomes more viable near-term.

### §3 Layout algorithms & the integration contract

The deliverable here is the *seam*, since the team writes its own algorithms.

**The contract (what your renderer must accept):** a flat, stable array of node ids with mutable `{x, y}` (and optionally `vx, vy`), plus a tick/commit signal. This is exactly d3-force's data contract: it mutates an array of node objects in place; `simulation.tick(n)` steps manually; `simulation.stop()` disables the internal timer so *you* own the clock. graphology's layouts assume node attributes `x`/`y` set before running and provide `forceAtlas2.assign(graph)` plus a `/worker` supervisor (`FA2Layout.start()/stop()/kill()`). Note graphology's documented edge case: ForceAtlas2 cannot compute if all nodes start at `x=0,y=0`, so seed with a circular/random layout first.

**Standard interfaces to mirror in your own engine:**
- **d3-force**: `force(alpha)` functions registered on a simulation; per-tick it applies forces then integrates velocity→position (velocity Verlet, constant Δt=1, mass=1). Model your custom forces as `(alpha) => void` mutators over a shared buffer.
- **graphology layouts**: pure `layout(graph, settings) → positions` for one-shot (tidy-tree, circular), plus iterative supervisors for force. Only `noverlap`/`force`/`forceatlas2` ship with built-in worker support.
- **WebCola**: constraint-based (alignment, non-overlap, flow) — the right reference if you later want the "select group → restructure into ideal arrangement" action, which is a constraint-satisfaction problem more than a force one.

**Off-main-thread architecture (answers "can we run our own sim in a worker and stream at 60fps?" — yes):**
- Run the simulation in a **dedicated worker**. Hold node positions in a `Float32Array` backed by a **SharedArrayBuffer** (available — Chromium-only, with cross-origin isolation you control in Electron) so the render thread reads positions with zero-copy; or use **transferables** to ping-pong buffers if you prefer no shared memory.
- The proven pattern (markuslerner/d3-webworker-pixijs): worker runs the CPU-heavy sim at its own (possibly <60) rate; main thread runs a 60fps RAF loop that **interpolates** between the last two position snapshots so motion looks smooth even if the sim ticks slower. d3's own docs recommend computing large static layouts in a worker "to avoid freezing the user interface."
- Position-driving for *animated relayout* ("button → ideal arrangement"): compute the target layout in the worker, then **tween** each node from current→target on the main thread over ~300–500ms with an easing curve. This is how you "animate between a manual layout and an algorithm-produced layout without disorienting the user." Preserve identity (animate the same DOM/GL node, never unmount/remount) and use FLIP-style or direct transform interpolation.

**Animating manual↔algorithmic transitions without disorientation:** stage it — (1) freeze user input, (2) snapshot start positions, (3) compute target, (4) interpolate with a single eased tween, (5) settle and re-enable drag. Keep edges following node positions during the tween (don't animate edges independently). React Flow's docs note the same trade-off: CSS transitions on position are cheaper but break edge tracking, so position interpolation must drive both.

### §4 Data structures & persistence

- **Spatial index for hit-testing + culling:** Use **rbush** (R-tree, ISC) for the dynamic case — it supports insert/remove/update as nodes move, "hundreds of times faster than looping," and is the choice of production canvas libs (gravity-ui). Use **flatbush** (static, ~2.4 kB gzipped, single ArrayBuffer that can be *transferred between threads*) for the far-zoom dot snapshot where positions are momentarily frozen — flatbush's own benchmark indexes 1,000,000 rectangles in 273ms vs rbush's 1143ms. Practical plan: rbush as the live index; rebuild a flatbush snapshot for the worker when entering dot mode.
- **In-memory graph ↔ SQLite:** SQLite (better-sqlite3) is the source of truth. Hydrate an in-memory graph (a `Map<id, node>` + adjacency, or a graphology instance) on canvas open via your Zod-validated IPC + react-query. Treat the in-memory graph as a cache/projection; writes go to SQLite and invalidate react-query keys.
- **Incremental updates (feed edit must update canvas card):** Since nodes are live references, key the canvas card component on `note.id` and source its body from the same react-query cache the feed uses. An edit in the feed mutates the note row → query invalidation → the canvas card (and the feed) re-render from one source. Positions are untouched (they live in `node_layouts`).
- **Undo/redo for spatial ops:** Keep a command stack of *layout deltas* (`{noteId, canvasId, fromXY, toXY}`) separate from note-content undo. Spatial undo only rewrites `node_layouts`, never note bodies — this clean separation falls directly out of "position is view-state."
- **Viewport virtualization:** Only mount React card components for nodes whose bounds (from rbush) intersect an inflated viewport rect. This is the tldraw model; the inflate margin prevents pop-in at edges (the exact Obsidian failure mode where nodes are removed/inserted at the canvas edge).
- **Where ink lives:** A per-canvas `strokes(id, canvas_id, points_blob, style, …)` table; store the raw input points (not the outline polygon) as a compact blob (Float32 x/y/pressure) so you can re-run perfect-freehand's `getStroke()` at any zoom for crisp output. A `stroke_groups`/promotion table or a nullable `promoted_note_id` on strokes records when a stroke-collection has been promoted to a node. This does not require finalizing the schema now; it only requires that strokes are addressable and groupable.

### §5 Architecture (where each concern lives in Electron)

- **Main process:** SQLite (better-sqlite3), migrations, FTS5, all persistence. Position writes land here.
- **Renderer main thread:** React, DOM cards, canvas/GL draw loop, react-query, interaction/gestures, LOD tier state.
- **Renderer worker(s):** layout simulation (d3-force-style, your own forces) over a SharedArrayBuffer; optionally the flatbush rebuild. Stream positions to the main thread.
- **Position-persistence cadence:** Do **not** write per drag-frame. During an active drag/sim, update only in-memory + the live transform. **Debounce/commit on drop** (drag end) and on sim "settle" (alpha below threshold). A reasonable policy: throttle to SQLite at most every ~500ms during long sims, and always flush on drag-end, canvas-close, and app-quit. This keeps write-amplification off your SQLite + raw-SQL migrations path.
- **Coexistence with the virtualized feed:** Both views subscribe to the same react-query note cache; the feed is a list-virtualized view (note: this is exactly where the cautionary precedent lives — see risk register), the canvas is a spatial-virtualized view. Neither owns note identity or content; both are projections.
- **Module boundary for survivability:** Three layers — **(a) Graph Core** (SQLite + the property-graph domain model + IPC contracts; stable, never depends on view code), **(b) Layout Engine** (pure functions/worker; input = graph topology + constraints, output = positions; no rendering deps), **(c) View/Render** (DOM+canvas+GL; replaceable). The Layout Engine talks to Core via plain data and to View via position buffers. If you ever swap the renderer (or adopt tldraw later), Core and Layout Engine survive untouched. This *is* the escape hatch.

### §6 Unknown-unknowns (mandatory)

**Why graph views become unused hairballs — and a direct challenge to the MVP framing.** The strongest finding in this research: Obsidian's community consensus is that the graph view is "beautiful and almost completely useless" past ~200 notes — "a tangled web that's more fun to look at than navigate" — because a force-directed flat graph of undifferentiated links collapses into dense clusters where "you cannot distinguish a highly connected MOC from a moderately connected note." The community threshold is roughly "200 notes for 'starts to degrade' and 500 notes for 'reliably a hairball,'" with link *density* mattering as much as count. The community's *fix* (Excalibrain) imposes **hierarchy and stable, predictable placement** (parent/child/sibling/friend) rather than physics. Meanwhile the tools whose spatial surfaces people genuinely live in — **Heptabase, Scapple, Tinderbox, MarginNote, Muse** — are **manual-placement-first**: the human's spatial memory does the organizing; structure is *incrementally formalized* (a concept from the VIKI/VKB spatial-hypertext lineage and Tinderbox: move information "gradually from implicit to explicit representation").

**Direct recommendation against part of the MVP framing:** The MVP's heavy investment in force/auto-layout as the primary arrangement mechanism is the *riskiest* assumption. **Lead with manual placement + persisted positions + typed-edge styling + tidy-tree-on-demand for sub-trees; treat global force layout as a secondary "explore" mode, not the default.** Force layout's real value here is (a) an initial seed for never-placed nodes and (b) the "select group → restructure" action — both *local and on-demand*, not a global animated physics default. This matches MarginNote's tree-ish-with-cross-links aesthetic and avoids reproducing the hairball. Note also the VIKI/VKB "spatial parser" idea — inferring structure from how a user *clustered* items — is a far more on-target future feature than force layout, and "piles/clusters as tentative groupings" (vs. formal collections) is a directly applicable UX primitive.

**Month-three traps practitioners report (with the substrate choices that avoid them):**
- **Text/KaTeX quality on transformed layers:** CSS `scale()` blurs text in Chromium and KaTeX sub-trees compound the cost. *Avoid scaling cards;* swap to title/dot representations at tier boundaries and render cards at integer (1:1) scale, repositioning via translate only.
- **IME / input on canvas:** Canvas has no native text input; any in-place edit must overlay a real DOM input/contenteditable. This is a strong reason to keep near-zoom cards as DOM (your edit-in-modal MVP sidesteps it, but the DOM path keeps in-place editing open). tldraw notes it excludes the editing shape from culling for exactly this reason.
- **Scroll-vs-zoom gesture conflict:** Decide wheel = pan vs zoom explicitly (tldraw exposes `wheelBehavior: 'pan'|'zoom'|'none'`); on trackpads, pinch=zoom, two-finger=pan; guard against the feed's scroll stealing canvas wheel events.
- **GPU memory with many rasterized cards:** If you ever rasterize cards to textures for far-zoom, you hit texture-memory limits and Pixi's canvas-count caps; prefer drawing dots as GL points/instanced quads, not cached card bitmaps.
- **Accessibility of canvas UIs:** Canvas is invisible to screen readers; keep a DOM fallback/aria layer (tldraw invested heavily in this in SDK 4.0). At minimum, the feed view remains the accessible path to the same notes.
- **Fuzzy hit targets at low zoom:** At dot zoom, dots are sub-pixel; use the spatial index with an inflated hit radius and snap selection to nearest-within-radius (d3-quadtree's `find(x,y,radius)` is built for this; sigma.js also ships a spatial index for this purpose).
- **Ink rendering performance & storage:** Store input points, not tessellated outlines; re-tessellate via perfect-freehand per zoom. Watch the documented "hot elbows" artifact on fast strokes. Cache the current stroke's outline during a single draw gesture; only persist on stroke-end.

**Adjacent paradigms worth stealing from (the "faster horse" check):**
- **Spatial hypertext (VIKI/VKB/Tinderbox):** *spatial parsers* that infer structure from how the user clustered/colored items; "piles and clusters" as tentative un-formalized groupings vs. formal collections — both more aligned with your goal than force layout.
- **Semantic-zoom literature (Perlin/Pad++, GraphMaps, ZMLT):** the principle "semantic consistency — items introduced at a level persist at all deeper levels" is a good invariant for your LOD tiers; Shneiderman's "overview first, zoom and filter, details on demand" is the mantra for your zoom-out → dots → zoom-in → cards flow.
- **Game-engine scene graphs / creative-tool node editors (Blender/Houdini):** their lesson is the *retained scene graph + dirty-flag repaint* model — only recompute/redraw what changed — which is exactly the rbush-cull + memoized-card approach.

**Ecosystem shifts that should affect today's decision:**
- **WebGPU** is maturing but not required; WebGL2 is sufficient for dots/edges/strokes at your scale and far better supported. Architect the far-zoom renderer behind a thin interface so a WebGPU backend can drop in later (the infinitecanvas.cc tutorial demonstrates a WebGL/WebGPU-swappable canvas).
- **CSS `zoom` / View Transitions API:** tempting for cheap zoom but unreliable for text crispness and per-node control; do not depend on them for the core continuum.
- **React Compiler (React 19):** auto-memoization reduces the manual `useMemo`/`React.memo` burden that dominates React Flow performance tuning — a real tailwind for a DOM-card approach, but it does not change the fundamental DOM node-count ceiling, so it does not rescue a DOM-only 10k-node view.

## Recommendations

**Stage 0 — Spike the substrate seam (1–2 weeks).** Build a throwaway that renders N absolutely-positioned DOM cards on a CSS-transformed layer with rbush culling, and a separate canvas layer drawing N dots from a Float32Array. Benchmark on your *target integrated-GPU hardware* at 500 cards (card mode) and 10,000 dots (dot mode). **Go/no-go threshold: 60fps pan/zoom at both.** If DOM cards can't hold 60fps at 500, lower the card-mode ceiling and lean harder on the canvas tier earlier.

**Stage 1 — MVP core.** (a) Graph Core layer over your existing SQLite schema; (b) DOM-card near-zoom view with manual drag → `node_layouts`, debounced-on-drop persistence; (c) typed edges on a canvas layer, visually distinguished by `edge_type`; (d) LOD tier state with a card→title→dot swap; (e) the far-zoom canvas dot renderer. Ship with one canvas but never assume singularity (carry `canvas_id` everywhere). **Default arrangement = manual placement**, not force.

**Stage 2 — Layout engine.** Worker-based, SharedArrayBuffer positions, your own forces using the d3-force tick/stop contract. Deliver: (a) seed-layout for unplaced nodes, (b) tidy-tree for a selected sub-tree, (c) the "select group → ideal arrangement" tween. Animate all transitions with a single eased position interpolation that also moves edges.

**Stage 3 — Ink.** perfect-freehand on a dedicated stroke layer; per-canvas stroke table storing input points; stroke selection + "promote to node" (insert note + layout + link rows). Nothing here is foreclosed by Stages 0–2.

**Benchmarks/thresholds that change the plan:**
- DOM holds 60fps at ≥2,000 markdown cards on target HW → widen card-mode ceiling; React Flow becomes a viable MVP accelerator.
- DOM struggles below 500 cards → move the LOD card→title boundary inward and consider a canvas/GL text-card renderer sooner (accepting higher build cost).
- tldraw relicenses permissively → re-evaluate adopting it for the core.

## Caveats
- Obsidian Canvas card-count lag figures (40–200) are consistent multi-user reports, not a controlled benchmark; your own Stage-0 numbers on target hardware supersede them.
- "Compose-by-hand" carries real build cost; the recommendation rests on the *combination* of your fixed constraints (live references, position-as-view-state, externally-driven layout) that no surveyed library satisfies together — not on a claim that the libraries are low quality.
- Library maintenance facts (stars, release dates, contributor counts) are point-in-time (mid-2025 / early-2026) and should be re-checked before commitment. The Lighthouse DOM-size thresholds changed semantics in Lighthouse 13 (Oct 2025) from static node counts to measured 40ms recalc/layout work — verify current behavior against the version you test with.
- The far-zoom 10k-dot @60fps target on integrated graphics is plausible per gravity-ui/Sigma evidence but is *their* hardware and scenes (e.g., gravity-ui's 111k-node figure was on an M3, yielding only ~15–20 FPS for the full scene before culling); it is not yet measured for your specific card/edge/ink mix on integrated graphics — hence Stage 0.
