# Prior-art research — iMessage-style send animation & animation library choice

This file captures, **verbatim**, the research that informed ADR 0018 (send
ghost clone) and ADR 0019 (Motion as the animation library):

1. An Opus research subagent's survey of whether anyone has already solved the
   "fly a message from the composer into a virtualized, async-inserted feed"
   animation.
2. Our own follow-up read of the two Motion GitHub issues the survey flagged
   (motion #1524 and #2111) — are they closed, solved, is there a workaround?

Sourcing caveats are preserved as written. Nothing here is paraphrased to look
cleaner than it was.

---

## 1. Research subagent report (verbatim)

**TL;DR:** No off-the-shelf library does the specific "fly from composer into a NEW async-arriving item inside a virtualized, transform-positioned list" motion — every FLIP/shared-element library (Motion `layoutId`, react-flip-toolkit, GSAP Flip, AutoAnimate, View Transitions) requires the destination node to exist at animation time and/or breaks on transformed-ancestor / cross-container / async-insert, all of which your case has. Your hand-rolled `position:fixed` ghost clone portaled to `document.body` is in fact the *canonical* pattern that drag-and-drop libraries (Angular CDK, dnd-kit, Elastic UI) use for exactly this clipping/transform/stacking-context escape — keep it.

---

### Libraries

| Name | Does it fit our case? | Evidence URL |
|---|---|---|
| **Motion / Framer Motion `layoutId` (shared element)** | **No.** Needs the destination motion node mounted to match `layoutId`; our target arrives async after IPC→SQLite→refetch, so at send-time there is nothing to match. Requires `layoutScroll` on scroll containers and `layoutRoot` on fixed elements; combining shared-layout + scroll + AnimatePresence variants produces documented "jumpiness / animates from a y value that doesn't make sense." Also breaks when portaled to `document.body`. | [motion.dev layout-animations](https://motion.dev/docs/react-layout-animations) · [motion #2111](https://github.com/framer/motion/issues/2111) · [motion #1524 (portal)](https://github.com/framer/motion/issues/1524) |
| **Motion `layout` projection (Magic Motion)** | **No.** Its distortion correction works by re-measuring `getBoundingClientRect` each frame and applying counter-transforms against ancestor transforms — fragile inside a virtualized list whose rows are themselves `transform: translateY(...)`. Children must *also* be `motion`+`layout` to avoid distortion. And it "assumes a layout change means the component just re-rendered" — it has no story for a node absent in the previous render. | [nan.fyi Magic Motion internals](https://www.nan.fyi/magic-motion) · [Frontend.fyi: challenges in layout animations](https://www.frontend.fyi/course/motion/07-layout-animations/04-challenges-in-layout-animations) |
| **react-flip-toolkit** | **No.** It explicitly advertises "real FLIP instead of cloning & crossfading," matching `flipId` across renders — but FLIP requires both first AND last states of the *same logical element* in the DOM. `portalKey` only widens selection scope; it doesn't conjure a not-yet-rendered async node. README has zero coverage of transformed ancestors / `position:fixed`. | [react-flip-toolkit README](https://github.com/aholachek/react-flip-toolkit/blob/master/README.md) |
| **GSAP Flip plugin** | **Partial, still no.** `onEnter` handles elements present in the *end* state but absent in the start state, and `absolute:true` solves flex/grid layout — but `Flip.from()` is synchronous (capture state → mutate DOM → animate), so the destination must exist *now*; ours doesn't until a later refetch tick. Docs warn `absolute:true` coords are viewport-based and break if scroll/resize happens during the flip; 3D transforms unsupported. | [gsap.com Flip docs](https://gsap.com/docs/v3/Plugins/Flip/) |
| **FormKit AutoAnimate** | **No.** Animates *only* immediate children of a single parent on add/remove/move; cross-container ("animate across lists," exactly the composer→list case) is an open/declined request. Also documented broken when the container is transformed/transitioned or not initially rendered. | [auto-animate #189 (across lists)](https://github.com/formkit/auto-animate/issues/189) · [#195 (transitioned container)](https://github.com/formkit/auto-animate/issues/195) · [#8 (not-initially-rendered)](https://github.com/formkit/auto-animate/issues/8) |
| **View Transitions API** | **No.** Captures `::view-transition-old`/`-new` snapshots at a single DOM-change commit; if the element only exists in the "after" state it "won't have a `::view-transition-old` … it'll start in its final position" (no fly). Virtual-DOM diffing creates fresh elements that confuse it, and it doesn't schedule your async IPC insert. Electron/Chromium-only, still maturing. | [MDN View Transition: Using](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API/Using) · [WICG explainer](https://github.com/WICG/view-transitions/blob/main/explainer.md) |

### Published implementations (chat/iMessage send specifically)

- **Josh W. Comeau — "Animating the Unanimatable" (FLIP in React).** Canonical React FLIP: `getBoundingClientRect` First in `componentWillReceiveProps`, Last in `componentDidUpdate`, Invert + Play via two `requestAnimationFrame`s. **Reorders existing list items only — does NOT handle new items flying in, no virtualization, no transformed-ancestor / `position:fixed` discussion, plain `transform 500ms` (no spring overshoot).** [joshwcomeau.com](https://www.joshwcomeau.com/react/animating-the-unanimatable/)
- **Makers' Den — "FLIP animation in React."** Same First/Last/Invert/Play recipe via `getBoundingClientRect` + delta transform + rAF. Reorder/layout focus; no async-insert or virtualization. [makersden.io](https://makersden.io/blog/flip-animation) / [CSS-Tricks FLIP](https://css-tricks.com/animating-layouts-with-the-flip-technique/)
- **Samuel Kraft — "iOS chat bubbles in CSS."** Builds iMessage *bubble visuals* (clip-path/pseudo-elements) "with a sprinkle of JS and Framer Motion" — styling and in-place entrance, **not** a composer→list fly. [samuelkraft.com](https://samuelkraft.com/blog/ios-chat-bubbles-css)
- **CodePen "iMessage conversation animation" (adesurirey).** jQuery `doBounce()` animating `marginTop` — messages pop/bounce *in sequence*; there is **no fly-from-input motion**. (Page is JS-gated; technique summarized from search index.) [codepen.io/adesurirey/pen/NvOgPz](https://codepen.io/adesurirey/pen/NvOgPz)
- **CodeSandbox "chat-message-animations-framer-motion."** Framer Motion message entrance animations; from the surrounding search corpus these are in-place enter/exit, not a shared-element send. (Could not fetch — CodeSandbox returns 403 to the fetcher; flagging as **unverified** rather than claiming its technique.) [codesandbox.io/s/...e4gs3l](https://codesandbox.io/s/chat-message-animations-framer-motion-e4gs3l)
- **TanStack Virtual Discussion #693** — not an implementation but the smoking gun: a user tries Framer Motion `motion`+`AnimatePresence` to animate a *newly prepended* item in a `@tanstack/react-virtual` list (rows absolutely positioned in a `position:relative` sizer, exactly your layout) and reports the animation simply **does not fire** for the new item, plus spurious animations on scroll-back. [github.com/TanStack/virtual/discussions/693](https://github.com/TanStack/virtual/discussions/693)

**Net:** I found **no** public implementation of the true iMessage *send* (bubble lifts off composer and flies into the feed's landing slot) for a virtualized, async-inserted web list. The closest production-grade prior art for the *mechanism* is drag-and-drop drag-previews (below), not chat demos.

### Pitfalls others hit (matching ours)

- **`position:fixed` inside a `transform`ed ancestor → containing-block trap.** A `transform` (even identity) on any ancestor makes `position:fixed` resolve against that ancestor, not the viewport — your virtualized rows live inside `transform: translateY(...)` wrappers, so a fixed ghost rendered *inside* the feed would be mis-anchored. Portaling the clone to `document.body` (outside all transformed ancestors) is the documented fix. [mtsknn.fi: breaking position:fixed](https://mtsknn.fi/blog/breaking-css-position-fixed/) · [aworkinprogress.dev: transform establishes containing block](https://www.aworkinprogress.dev/transform-establishes-containing-block-descendants) · [dev.to/salilnaik](https://dev.to/salilnaik/the-uncanny-relationship-between-position-fixed-and-transform-property-32f6)
- **Virtualized list + shared-element/layout animation conflict.** Framer Motion interpolates sizes/positions in JS while the virtualizer needs to measure and reposition rows; documented as freezing/unpredictable when `transform: translateY` rows meet `AnimatePresence`, and new-item animations silently failing. [TanStack #693](https://github.com/TanStack/virtual/discussions/693) · [answeroverflow: virtual + framer-motion](https://www.answeroverflow.com/m/1277664625298768012) (note: AnswerOverflow + the chat CodeSandbox both 403'd the fetcher — claims here rest on the TanStack issue + search index, flagged accordingly)
- **Async-arriving target node.** Every FLIP/shared-element tool assumes the "last" element exists at capture time (Motion `layoutId` match, GSAP `Flip.from`, View Transitions snapshot). With IPC→SQLite→`invalidate`→refetch, the landing node appears on a later tick — so a measured/derived landing rect (your FLIP-style approach) is the only option that doesn't require the node. [MDN View Transitions](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API/Using) · [TanStack #693](https://github.com/TanStack/virtual/discussions/693)
- **Shared layout breaks across portals / scroll roots.** Motion `layoutId` "renders only first and last states without interpolation" when teleported via a portal (the `ProjectionNode` keeps referencing the old motion parent), and shared-layout + `layoutScroll` + AnimatePresence variants produce position-jump artifacts. [motion #1524](https://github.com/framer/motion/issues/1524) · [motion #2111](https://github.com/framer/motion/issues/2111)
- **Clipping vs overshoot.** A spring-overshoot `cubic-bezier(0.34,1.56,0.64,1)` on an element rendered *inside* an `overflow:hidden`/clipped feed gets visually cut at the boundary; rendering the ghost on `document.body` keeps the overshoot fully visible — same reasoning drag libraries cite for cloning out of clipping parents. [Angular CDK drag-drop](https://angular.dev/guide/drag-drop) · [Elastic UI drag-and-drop (usePortal)](https://eui.elastic.co/docs/components/display/drag-and-drop/)

### Verdict

**Keep the hand-rolled `position:fixed` ghost clone portaled to `document.body`; it is the established correct pattern for this constraint set, not a workaround.** The single strongest reason: the production drag-and-drop libraries that solve the *identical* problem class — animate an element across clipping boundaries and out of transformed/stacking-context ancestors into a position the static DOM can't express — all converge on exactly your technique. Angular CDK "inserts the drag preview into `<body>` to avoid issues with positioning and overflow"; dnd-kit's `DragOverlay` and Elastic UI's `usePortal` render the moving element in a `document.body` portal with fixed positioning specifically because "this positioning logic does not work as expected inside containers that have their own stacking context" ([Angular CDK](https://angular.dev/guide/drag-drop) · [dnd-kit DragOverlay](https://docs.dndkit.com/api-documentation/draggable/drag-overlay) · [Elastic UI](https://eui.elastic.co/docs/components/display/drag-and-drop/)). Meanwhile every shared-element library that could "do it for you" is disqualified by a *hard* property of your case: the landing node doesn't exist at send-time (rules out Motion `layoutId`, GSAP `Flip.from`, react-flip-toolkit, View Transitions), and the ones that don't need it can't cross containers (AutoAnimate) — confirmed by a real user hitting precisely the Framer-Motion-on-`@tanstack/react-virtual` new-item failure in [TanStack #693](https://github.com/TanStack/virtual/discussions/693). The one refinement worth a glance: your optimistic launch + FLIP-style derived landing rect is sound, but since the destination node arrives async, make sure the landing target is computed from the virtualizer's known row geometry (or the feed's bottom anchor) rather than from `getBoundingClientRect` of a node that may not be mounted yet — that's the only place the published FLIP recipes (which all assume the target is already in the DOM) don't cover you.

**Caveats on sourcing:** AnswerOverflow's virtual+framer-motion thread and the `chat-message-animations-framer-motion` CodeSandbox both returned HTTP 403 to the fetch tool, so claims attributed to them rest on the search index plus the directly-verified TanStack #693 issue — treat those two as corroborating, not primary. The Motion API specifics (package now `motion`, prop `layoutId`, `layoutScroll`/`layoutRoot`) were verified against the live [motion.dev docs](https://motion.dev/docs/react-layout-animations) and the context7 library index (current canonical ID `/websites/motion_dev`).

## 2. Our follow-up: are motion #1524 / #2111 still open? solved? workarounds?

We read both issues' full comment threads via `gh` (repo moved `framer/motion`
→ `motiondivision/motion`). Findings, verbatim:

> Short version: **both are closed, both are about the *shared-layout*
> (`layoutId`) feature only, and both have comment workarounds.** Neither touches
> the gesture/spring core you actually want — so this *narrows* the risk to the
> one subsystem we already fenced off.
>
> **#1524 — shared layout animations break in a React portal** — CLOSED (Jun 2023).
> - **Root cause (understood):** a portal splits the React tree from the DOM
>   tree, so the portaled `motion` node reads the *wrong* `MotionContext` — you
>   get start→end snap with no interpolation. Exactly the "breaks across portals"
>   claim.
> - **Workaround in comments (two, both confirmed working):**
>   1. `birmitt` — one-liner: wrap the portal in `<MotionContext.Provider value={{}}>`
>      to *reset* the context (disconnect the portaled node from its React
>      parent). `ciampo` applied it to the repro and "the animations worked again."
>   2. `ciampo` — the proper fix: *forward* the MotionContext across the portal
>      (read at the slot, recreate in the fill); shipped in WordPress Gutenberg
>      (PR 50278). Closed on the back of this.
> - **Honest status:** closed via *community workaround*, not a Motion release fix.
>
> **#2111 — `layoutScroll` + shared layout** — CLOSED (Feb 2026), **but
> closed-as-stale**, not solved: `mattgperry` (maintainer) — "closing this out as
> the original example isn't available any more … open a new ticket with a
> reproduction."
> - **What it actually was:** the OP discovered it wasn't `layoutScroll`/`layoutRoot`
>   at all — it was putting **`<AnimatePresence>` + enter/exit `variants` on the
>   `layoutId` element**. Workaround: don't combine variants with `layoutId` on
>   the same node. One 2025 commenter reported residual jumpiness *without*
>   variants and got no reply — so there's an unresolved tail here.
>
> **What this means for us — it makes Motion *safer*, not riskier:** Both issues
> are confined to `layout`/`layoutId` **shared-element projection** — the *exact
> one feature* we already excluded (no `layout`/`layoutId` in the virtualized
> feed). Everything we actually want — `whileTap`/`whileHover` checkboxes,
> `drag`, `type:"spring"`, SVG `pathLength`, `AnimatePresence` for plain
> modal/toast mount-unmount — runs on a *different* subsystem and is untouched by
> either bug. And even the worst case (a Motion-based portaled shared-element)
> has a **proven one-line escape**: `<MotionContext.Provider value={{}}>`.

These two findings are codified as guardrails in ADR 0019:
- no `layout`/`layoutId` projection inside the `@tanstack/react-virtual` feed;
- if a `layoutId` element is ever portaled, reset/forward `MotionContext` (#1524);
- never put enter/exit variants on a `layoutId` node (#2111).
