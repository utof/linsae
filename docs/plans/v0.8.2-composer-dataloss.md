# v0.8.2 — composer data-loss + two orphans

Status: **draft** (awaiting review round 1)
Branch: `v0.8.2/composer-dataloss`
Issues: **#161**, **#176** (cluster A) · **#169** (cluster B) · **#189** (cluster C)

**No spec for this batch, deliberately.** Every issue already carries a traced cause with `file:line`
in its body — these are known bugs, not mysteries, so the spec→review→plan→review cycle is milestone
ceremony. What *does* need writing down is cluster A's shared contract decision, which is why this
plan exists. `/systematic-debugging` is held in reserve: if any stated cause below fails a one-step
trace during implementation, **stop and invoke it** rather than fixing the symptom (CLAUDE.md
disagreement protocol, "stated cause ≠ symptom after a 1-step trace").

---

## 1. Goal

Stop the app silently eating text the user typed, and re-attach two pieces of working code that were
orphaned by refactors.

### Success criteria

1. A failed send **never** loses the user's text — not the on-screen draft, not the persisted one.
2. Every composer in the app uses the **same** clear-on-success contract.
3. The docked YouTube player has a scrubber, speed control, follow-toggle and fullscreen again.
4. A multi-line PDF selection produces a locator with `prefix`/`suffix`/`textStart`/`textEnd`.
5. Each fix has a test that was **observed failing before the fix existed** (§6).

### Non-goals

- Retry UI, offline queueing, or draft history. Preserving the text and showing the error is enough.
- Redesigning the composers' visual chrome. Behaviour only.
- Fixing the duplicate-slug collision itself (#161's trigger). Colliding slugs are legitimate; the
  bug is that the failure destroys data.
- Any change to `notes.create`'s main-side contract.

## 2. Cluster A — the composer contract (#161, #176)

### 2.1 What is actually broken

Three composers exist. **One is already correct**, and it is the model:

| Composer | Behaviour on submit | Verdict |
|---|---|---|
| `composer/Composer.tsx` (feed) | `submit()` calls `onSubmit(...)` and **does not clear**. Parent remounts it via a `key` change on success (`App.tsx:1355`). Comment at `:149-153` explains it and cites issue #23 Option B. | **Correct — copy this** |
| `thread/SimpleComposer.tsx` | `submit()` at `:78-85` calls `onSubmit(t)` then **synchronously** `setBody('')` + `onDraftClear?.()`. `onSubmit` is typed `(body: string) => void` — fire-and-forget, so failure is unobservable. | Broken (#161) |
| `thread/ThreadComposer.tsx` | `submit()` at `:200-222` calls `onPost({body, t})` then `setDraft('')` + `onDraftClear?.()`. | Broken (#176) |

The upstream throw site is real and reachable: `ThreadView.postPlain` (`:580-590`) does
`await api.notes.create(...)` with **no try/catch**, and `save-note.ts:164` rejects with
`a note named "<slug>" already exists`. Two short identical replies ("yes", "ok") collide on the
body-derived slug. On failure today: text gone, no note, no error shown, unhandled rejection.

v0.7 made it worse rather than causing it: `onDraftClear?.()` now also drops the **durable**
`composer.draft.thread.v1` entry, so a restart cannot recover the text either.

`ThreadView` already has the right error surface for the *other* path — `postError` state
(`:382`), `onError: (err) => setPostError(err.message)` (`:544`), rendered at `:785-786`. The plain
path simply never got wired to it.

### 2.2 The decision — this is the part that must not be improvised

**Contract: a composer never clears its own draft. The parent clears it, on success only.**

Concretely:

1. **`SimpleComposer`'s `onSubmit` becomes async-aware:** `(body: string) => void | Promise<void>`.
   `submit()` awaits it, and clears local state **only if it resolves**. On rejection it leaves
   `body` and the persisted draft untouched and surfaces the error.
2. **`ThreadComposer`'s `onPost` gets the same treatment.**
3. **`onDraftClear?.()` moves to the success branch** in both — it must never fire on a path that
   kept the text, or the on-screen and persisted copies disagree.
4. **The feed `Composer` is not touched.** It is already correct and its remount-on-success
   mechanism is a different (also valid) expression of the same contract. Do **not** "unify" it by
   rewriting it — that is scope creep with regression risk, and #23 already settled its design.

**Why await-and-clear rather than extending the feed's remount-on-success to threads:** the feed's
`key` remount works because `App` owns feed submission and already re-keys on success. `ThreadView`
does not re-key its composers, and adding that would mean lifting per-thread draft state into `App`
— a much larger change touching v0.7's persistence wiring. Awaiting is local, and it is what the
`ThreadComposer` TSDoc *already claims* happens ("the draft is preserved so the user can edit +
retry" — currently false; #176 notes this).

**This changes an exported public surface** (two component prop types), so it is milestone work, not
an inline fix — exactly why #161 was deferred rather than patched.

### 2.3 Tasks

- **A1 — `SimpleComposer` async submit.** Widen `onSubmit` to `(body: string) => void | Promise<void>`.
  Make `submit` async: `await onSubmit(t)` in a `try`, then `setBody('')` + `onDraftClear?.()`; on
  `catch`, leave both and set an error. Guard against double-submit while in flight (Enter held /
  double-click) with an `isSending` ref or state — a second `notes.create` for the same body is
  itself a duplicate-slug throw.
- **A2 — `SimpleComposer` error surface.** It currently has *none* ("No error surface — this is the
  minimal case", TSDoc `:9`). Add a minimal inline error line using the same v21 tokens; mirror
  `ThreadComposer`'s existing `error` / `onClearError` prop shape so the two are consistent rather
  than inventing a third pattern. Clear the error on the next successful send and on edit.
- **A3 — `ThreadView.postPlain` propagates failure.** It currently `await`s with no try/catch. It
  must reject (so A1's `catch` fires) **and** feed `setPostError`. Keep the existing
  `invalidateQueries` calls on the success path only — invalidating after a failed create is
  pointless work.
- **A4 — `ThreadComposer` async post.** Same shape as A1 for `onPost`, moving `setDraft('')`,
  `onDraftClear?.()`, `setManuallyFrozen(false)` and `setAnchorless(false)` into the success branch.
  **Careful:** `pendingFrame` must also survive a failure — a captured screenshot that vanishes on a
  failed post is the same data-loss bug with a more expensive payload. Verify what currently clears
  it and keep it symmetric with the draft.
- **A5 — ADR.** `adrs/0063-composer-clears-on-success.md`: the contract, why the feed composer is
  exempt (different mechanism, same guarantee), and the trap that produced this — *an optimistic
  local clear is invisible until the async path fails, and nothing in the type system flags a
  fire-and-forget `() => void` that is actually async.*

## 3. Cluster B — restore the docked player transport (#169)

`v0.6.4` B5 (commit `4ab51f0`) lifted the player into `yt/PlayerPane.tsx` and dropped `ThreadView`'s
`TransportBar` without re-surfacing it. Native controls are suppressed
(`youtube-guest.ts:121`, `v.controls = false`), so the docked player has no scrubber, speed badge,
follow-toggle or fullscreen button. Play/pause survives only because the webview stays interactive.

**Orphaned but alive — the "tests keep dead code alive" trap.** `thread/TransportBar.tsx` (exports
`TransportBarProps` `:17` and `TransportBar` `:103`) is imported by **no production module**, only
its own test. Same for `rail-layout.ts:126`'s `markerPositions`. knip passes because a test import
counts as a use. Worth noting in the ADR: **knip cannot detect this class of dead code**, so a
test-only importer is not evidence a component is wired up.

### Tasks

**Verified before writing the tasks — B1 is feasible, but not as trivially as #169 implies.**
`usePlayerState` returns `{ player: playerRef.current, currentTime, state, duration }`
(`yt/usePlayerState.ts:58`). It **does** hand back the imperative `player` handle, so
`onPlayPause` / `onSeek` / `onFullscreen` can be wired **without** a second `usePlayer` call — the
single-mount invariant (ADR 0016/0049) is safe. That was the blocker risk and it does not
materialize.

Two of `TransportBar`'s props have **no source at all**, and this is a design decision the plan must
make rather than hand to an implementer:

- **`followOn` / `onToggleFollow`.** `ThreadView.tsx:260` is literally `const followOn = true`, above
  a comment reading *"After B5 the follow-toggle lived in TransportBar (now in PlayerPane)"* — which
  is already false, since `PlayerPane` has no toggle. Worse, follow-scroll scrolls **ThreadView's**
  notes list, so a toggle rendered in a dock pane must reach across into a component that currently
  holds this as a local `const`. That needs shared state (a zustand slice or an app-setting) that
  does not exist.
- **`rate` / `onRate`.** No rate state exists in `ThreadView` either.

- **B1 — mount `TransportBar` in `PlayerPane`, wiring only what has a real source.** Render it via
  `usePlayerState`; wire `state`, `currentTime`, `duration` from the hook and
  `onPlayPause` / `onSeek` / `onFullscreen` through the returned `player` handle. **Do not add a
  second `usePlayer` call.**
- **B2 — `followOn` and `rate`: descope, do not invent.** Ship the scrubber, play/pause and
  fullscreen. Pass `followOn` as a fixed `true` **only if** `TransportBar` renders acceptably that
  way; otherwise make both props optional so the bar can render without them. **Do not build
  cross-component follow state in a bugfix batch** — that is a feature, it touches ThreadView's
  scroll behaviour (the thing v0.7 spent a whole ADR stabilising), and #169's own text says the
  player is *"degraded"*, not broken. File a follow-up for the follow-toggle and the speed control,
  and fix `ThreadView.tsx:257-259`'s comment, which currently documents a state of the world that
  never existed.
- **B3 — markers.** `markerPositions` (`rail-layout.ts:126`) needs the thread's annotation
  timestamps and `PlayerPane` does not know the thread. **Ship `markers: []`.** A scrubber without
  ticks is a working scrubber; an over-reaching data dependency in a bugfix batch is not. File the
  follow-up.
- **B4 — verify the fix in real Electron.** happy-dom has no layout and no media element; a scrubber
  is geometry. Extend an existing `scripts/*.mjs` smoke or add one. **Do not** claim this fixed on
  unit tests alone — that is precisely how #169 shipped in the first place.

## 4. Cluster C — PDF multi-line locator (#189)

`pdf/useExcerptCapture.ts:102-116` builds the disambiguation context as:

```ts
const fullText = await entry.page.getTextContent()
  .then((tc) => tc.items.map((i) => ('str' in i ? i.str : '')).join(' '))
const idx = fullText.indexOf(text)
```

`getTextContent()` items are joined with a **space**; `sel.toString()` joins visual lines with a
**newline**. So for any selection spanning more than one line `indexOf` returns `-1` and all four of
`prefix`, `suffix`, `textStart`, `textEnd` are dropped. Confirmed against the committed fixture: a
4-span drag on page 3 of `tests/fixtures/multi-feature.pdf` yields
`"Third page\nA third page..."` with empty prefix/suffix.

The existing comment at `:109-111` explains `idx === -1` as the honest cross-page case. That
explanation is **correct but incomplete**, and its presence is why this went unnoticed — it makes a
failing path look intended. Fix the comment as well as the code.

### Tasks

- **C1 — normalize before matching.** Extract a pure helper (own file, own test) that normalizes
  whitespace on both sides — the page text and the selection — so a multi-line quote matches. The
  offsets it produces must remain meaningful for `textStart`/`textEnd`; **if normalization shifts
  offsets relative to the string those fields are supposed to index, say so and pick one consistent
  basis rather than silently mixing them.** This is the one genuinely subtle thing in the batch.
- **C2 — keep `clientRectsToPdfRect` and `computePdfRender` byte-identical.** v0.8 held these fixed
  on purpose (ADR 0058); this fix is upstream of both and must not touch them.
- **C3 — real-Electron proof.** `scripts/pdf-multipage-smoke.mjs` **found** this bug; extend it to
  assert non-empty prefix/suffix on a multi-line drag so it cannot regress. A happy-dom test cannot
  produce a real selection.

## 6. Testing — the non-negotiable part

**Every test must be observed failing before its fix exists.** v0.8 shipped ten tests that were
provably incapable of failing, caught only by mutating the implementation. This batch is unusually
easy to get wrong the same way: a test that mocks `notes.create` to *resolve* and asserts the draft
cleared will pass against the buggy code and the fixed code alike.

Minimum per cluster:

- **A** — component tests via `renderWithProviders` + `installMockApi` (`tests/setup.tsx`), with
  `notes.create` mocked to **reject**. Assert: textarea still holds the text, `onDraftClear` was
  **not** called, an error is visible. Then a resolving case asserting the inverse.

  **Correction to an earlier draft of this section:** it claimed the mock "cannot currently express
  rejection" and made fixing that a prerequisite for all of cluster A. That was wrong — rejection is
  expressible today, either by mutating the returned object after install
  (`const api = installMockApi(); api.notes.create = vi.fn().mockRejectedValue(new Error(...))`,
  which works because `installMockApi` assigns that same object to `window.api` by reference) or by
  overriding the whole `notes` namespace. Cluster A is **not** gated on a test-harness change.

  What *is* true and worth fixing while here: `installMockApi` applies `...overrides` as a
  **shallow top-level spread** (`tests/setup.tsx`, end of the function), so a partial
  `{ notes: { create } }` silently drops `list`, `get`, `listTitles` and the rest — which is why
  existing call sites carry `as never` casts (`palette/QuickSwitcher.test.tsx:31,46,75,107`). And
  the default `create: vi.fn()` returns `undefined` rather than a `Note` (issue #7 item 3). Both are
  worth fixing, but as a **convenience**, not a blocker — do not let this grow into a test-harness
  refactor inside a data-loss batch.
- **B** — a real-Electron smoke (B3). Unit tests may assert the props wiring but cannot prove the
  scrubber works.
- **C** — a unit test on the C1 helper with a genuine multi-line fixture string, **plus** the
  extended smoke (C3).

Run the specific file during the loop (`vitest run <file>`), never the full suite — lefthook is the
authoritative gate (CLAUDE.md orchestration rule).

## 8. Risk

Cluster A touches two exported prop types consumed by `ThreadView`. Everything else is additive or
internal. The realistic failure mode is **fixing the clear and forgetting the error surface**, which
converts silent data loss into silent *nothing happening* — still a bug, and one the tests in §6
catch only if they assert the error is visible, not merely that the text survived.

## 9. What comes after this batch

**Next milestone: semantic zoom** — top of the `docs/canvas-vision.md` queue since v0.6.2 and now
deferred by five consecutive amendments (v0.6.4, v0.7, v0.8, v0.8.1, and this batch). It is the next
real feature; v0.8.2 is a papercut batch that jumped the queue because it is data loss.

The seam already exists and is deliberately half-built: `canvas/lod.ts:8` defines
`LodTier = 'card' | 'title' | 'dot'` with `TIER_THRESHOLDS = { title: 0.5, dot: 0.15 }` and
`tierForZoom()`; v0.4 shipped the **card** renderer only. `canvas/dev-lod.ts` provides a DEV HUD that
force-selects a tier and unclamps zoom past the production `[0.5, 2.0]` range, so the empty tiers are
already inspectable before a line is written.

Scope per `canvas-vision.md:115-123`: title tier + dot tier on the underlay, zoom-threshold UX,
card⇄title⇄dot transitions under a **semantic-consistency invariant** (anything visible at a tier
persists at all deeper tiers), dot hit-testing with inflated radius + snap-to-nearest, labels on
hover/proximity at dot zoom. The strategic payload: the **dot tier doubles as the minimap and the
whole-vault lens** — notes without manual positions get *computed* positions there, not on the card
tier. Perf is pre-cleared (v0.4.0 spike: 10k canvas-2D dots at 60fps; no WebGL).

**Two things gate starting it, both already written down and both easy to miss:**

1. **#96 (switchable arrangements)** — `memory/progress.md` flags it "evaluate before the next canvas
   milestone", and the dot tier is exactly where that decision lands.
2. **#18 (esc-precedence)** — `canvas-vision.md:213` says re-audit *every* canvas milestone;
   semantic zoom adds zoom-tier modes, so it triggers.

**Semantic zoom needs the brainstorm step** (CLAUDE.md workflow step 1) before its spec — unlike this
batch. Real open product questions: what the title tier shows for a note with no title line, whether
unplaced notes appear at dot zoom at all, and whether the minimap *is* the dot tier or a separate
surface. Those want deciding before a spec, not during one.

After semantic zoom, `canvas-vision.md:217`'s non-binding order is: layout engine → canvas ink
(Stage 3) → nested canvases → multi-canvas → channels → **PDF annotation (Stage 2, blocked behind
ink)** → layers. Only two orderings are binding, both user-stated: PDFs after the
node/edge/tab/pane workflow (cleared by v0.6.2–v0.6.5), and **layers only after PDFs**.
