# v0.8.2 — composer data-loss + two orphans

Status: **reviewed** (round 1 applied; review cap reached per CLAUDE.md)
Branch: `v0.8.2/composer-dataloss`
Issues: **#161**, **#176** (cluster A) · **#169** (cluster B) · **#189** (cluster C)

**No spec for this batch, deliberately.** Every issue carries a traced cause with `file:line`, so
the spec→review→plan→review cycle is milestone ceremony for known bugs. What needs writing down is
the decisions, which is why this plan exists.

**`/systematic-debugging` is held in reserve.** An issue body is a hypothesis. If a stated cause
below fails a one-step trace, **stop and invoke it** rather than fixing the symptom (CLAUDE.md
disagreement protocol).

**Implementer model: NOT Sonnet-as-transcriber.** By CLAUDE.md's four-part test, none of A/B/C is
"simple" — each modifies pre-existing files and touches exported symbols already consumed
downstream. Round-1 review found three blockers that a transcriber would have shipped silently.

---

## 1. Goal

Stop the app silently eating text the user typed, and re-attach two pieces of working code orphaned
by refactors.

### Success criteria

1. A failed send **never** loses the user's text — not the on-screen draft, not the persisted one.
2. Every composer uses the **same** clear-on-success contract.
3. The docked YouTube player has a working scrubber, play/pause, fullscreen, speed and follow-toggle.
4. A multi-line PDF selection produces a locator with `prefix`/`suffix`/`textStart`/`textEnd`.
5. Each fix has a test **observed failing before the fix existed** (§7).

### Non-goals

- Retry UI, offline queueing, draft history.
- Redesigning composer chrome. Behaviour only.
- Fixing the duplicate-slug collision itself. Colliding slugs are legitimate; the bug is that the
  failure destroys data.
- Any change to `notes.create`'s main-side contract.

## 2. Cluster A — the composer contract (#161, #176)

### 2.1 What is broken

Three composers exist. **One is already correct and is the model:**

| Composer | On submit | Verdict |
|---|---|---|
| `composer/Composer.tsx:146-154` (feed) | Calls `onSubmit(...)`, **does not clear**. Parent remounts via `key={`${draftBody ?? 'fresh'}-${successCount}`}` (`App.tsx:1451`, ticked at `:653`) on success only. | **Correct — do not touch** |
| `thread/SimpleComposer.tsx:74-81` | Calls `onSubmit(t)` then synchronously `setBody('')` + `onDraftClear?.()`. `onSubmit` is `(body: string) => void` — failure unobservable. | Broken (#161) |
| `thread/ThreadComposer.tsx:200-231` | Calls `onPost({body,t})` then clears **five** pieces of state. | Broken (#176) |

Throw site is real: `ThreadView.postPlain` (`:580-590`) `await`s `api.notes.create(...)` with no
try/catch; `save-note.ts:164` rejects with `a note named "<slug>" already exists`. Two short
identical replies ("yes", "ok") collide on the body-derived slug.

v0.7 worsened it: `onDraftClear?.()` now also drops the durable `composer.draft.thread.v1` entry, so
a restart cannot recover the text.

### 2.2 The contract

**A composer never clears its own draft. The parent clears it, on success only.**

1. `SimpleComposer.onSubmit` and `ThreadComposer.onPost` become `=> void | Promise<void>`; `submit()`
   awaits and clears **only on resolve**.
2. On rejection: draft, persisted draft, and all dependent state survive untouched.
3. **Error state is parent-owned.** Not composer-local — see A2.
4. **The feed `Composer` is not touched.** It already implements the same guarantee via a different
   (also valid) mechanism, settled by #23. Rewriting it is pure regression risk.

**Why await rather than extending the feed's remount-on-success:** `App` owns feed submission and
already re-keys. `ThreadView` does not re-key its composers, and adding that means lifting per-thread
draft state into `App` — a much larger change through v0.7's persistence wiring. Awaiting is local,
and it is what `ThreadComposer`'s TSDoc already falsely claims happens.

This changes two exported prop types, so it is milestone work, not an inline fix — why #161 was
deferred rather than patched.

### 2.3 Tasks

- **A0 — migrate the 7 tests that assert synchronously. DO THIS FIRST.**
  Making `submit()` async defers post-submit state by ≥1 microtask. These assert on the same stack as
  `fireEvent` and will go red: `SimpleComposer.test.tsx:14, :26, :89, :97`;
  `ThreadComposer.test.tsx:110-123, :306-327, :343-351`. All pass `onSubmit: vi.fn()` /
  `onPost: vi.fn()`, so the post-await `setState` also lands outside `act()`.
  Migrate to `await waitFor` / `await act`. **A red sync assertion here is the EXPECTED signal, not
  evidence the contract is wrong.** Doing this first removes the pull toward "the clear must stay
  synchronous" — i.e. toward reverting the fix.

- **A1 — `SimpleComposer` async submit.** Widen `onSubmit` to `(body: string) => void | Promise<void>`.
  `submit` becomes async: `await onSubmit(t)` in a `try`, then clear; on `catch`, clear nothing.
  Guard double-submit (Enter held / double-click) with an in-flight flag — a second `notes.create`
  for the same body is itself a duplicate-slug throw.
  **Clobber window:** `setBody('')` after an await would discard text typed *during* the in-flight
  post. Today that window is zero. Use `setBody((prev) => (prev.trim() === t ? '' : prev))` — no
  visual change, no lost keystrokes. Apply the same to `ThreadComposer.tsx:218`'s `setDraft('')`.

- **A2 — error surface, parent-owned.** `SimpleComposer` currently has none (TSDoc `:9`: *"No error
  surface"*). Give it `error` / `onClearError` props mirroring `ThreadComposer.tsx:79-81`. **Neither
  composer holds local error state** — `ThreadView` already owns `postError` (`:382`, set at `:544`,
  rendered `:785-786`) and A3 feeds it. Two owners that can disagree is how this bug class recurs.
  Wire at `ThreadView.tsx:964-969`.

- **A3 — `postPlain` propagates failure.** Currently `:580-590`, no try/catch. It must reject so A1's
  `catch` fires, **and** feed `setPostError`. Keep `invalidateQueries` on the success path only.
  **Also fix the silent no-op:** `:582` `if (!note?.slug) return` *resolves*, so under the new
  contract the draft clears with no note created — the same bug in a new place. Make it throw, as the
  youtube path already does (`:509`, `throw new Error('video note not loaded')`).

- **A4 — `ThreadComposer` async post.** Defer **all five** post-submit updates to the success branch:
  `setDraft('')` `:218`, `onDraftClear?.()` `:221`, `setManuallyFrozen(false)` `:222`,
  `setAnchorless(false)` `:224`, and **`setFocused(false)` `:230`** — the fifth is easy to miss and an
  earlier draft of this plan did, by citing the range as `:200-222`.
  Deferring is correct for each: `chipTime` returns `frozenAt` unless `!focused && !hasDraft`
  (`composer-chip.ts:40`) and the freeze effect deps are `[focused, hasDraft, manuallyFrozen]`
  (`:197`), so on failure with everything deferred the draft stays → `hasDraft` stays true → no dep
  changes → `frozenAt` preserved → **the retry posts the same `t`**. A retry that silently
  re-anchors to a different second is a second, subtler data-loss bug. Resetting `setFocused(false)`
  on failure would strand the component in `!focused && hasDraft`, which `composer-chip.ts:54-55`
  documents as *"should not occur in normal UX"*.
  **`pendingFrame` needs NO change** — `ThreadView.tsx:532-533` already clears it in `onSuccess`.

- **A4a — `onPost` must actually be awaitable. WITHOUT THIS, A4 IS A NO-OP.**
  `ThreadView.tsx:794-796` is `onPost={({body,t}) => { post.mutate({body,t}) }}`. TanStack Query v5's
  `mutate` returns **`void`**; only `mutateAsync` returns a promise that rejects. So `await onPost(...)`
  awaits `undefined`, resolves on the next microtask, and the success branch runs **unconditionally** —
  the fix would look done and do nothing.
  Change to `onPost={async ({body,t}) => { await post.mutateAsync({body,t}) }}`. `onError` (`:544`)
  still fires and sets `postError`; the composer's `catch` exists only to swallow the rejection so it
  is not unhandled.

- **A5 — ADR `0063-composer-clears-on-success.md`.** The contract; why the feed composer is exempt;
  and the trap that produced this — *an optimistic local clear is invisible until the async path
  fails, and nothing in the type system flags a fire-and-forget `() => void` that is actually async.*
  Record the `mutate`/`mutateAsync` distinction: it is the same trap one layer up.

## 3. Cluster B — restore the docked player transport (#169)

`v0.6.4` B5 (`4ab51f0`) lifted the player into `yt/PlayerPane.tsx` and dropped `ThreadView`'s
`TransportBar`. Native controls are suppressed (`youtube-guest.ts:121`, `v.controls = false`), so the
docked player has no scrubber, speed badge, follow-toggle or fullscreen. Play/pause survives only via
the webview staying interactive.

**Orphaned but alive — the "tests keep dead code alive" trap.** `TransportBar.tsx` (`:17` props,
`:103` component) is imported by no production module, only its test. Same for `rail-layout.ts:126`'s
`markerPositions`. knip passes because a test import counts. **knip cannot detect this class of dead
code** — record that in the ADR.

### 3.1 Verified: the callbacks are NOT a problem

`usePlayerState` returns `{ player: playerRef.current, currentTime, state, duration }`, and
`playerRef = useRef(getPlayer())` (`:24`) is the full `PlayerInstance` exposing `play()` `:309`,
`pause()` `:321`, `seekTo()` `:325`, `setPlaybackRate()` `:337`, `toggleFullscreen()` `:352`
(`playerSingleton.ts`). The single-mount invariant concerns `mount()`/`load()`, which only
`usePlayer` calls (the `player.mount(…)` / `player.load(videoId)` pair in its effect body). **Calling
methods on the singleton mounts nothing.** No second `usePlayer`; ADR 0016/0049 is not at risk.

(`TransportBarProps` has **five** callbacks and six data props — an earlier draft said six callbacks.)

### 3.2 The decision: a shared transport store

Three of the six data props have no source, and two are **cross-pane**, which is the real work:

- **`followOn` is not a display flag.** It drives `ThreadView`'s follow auto-scroll (`:303-305`) and
  `jumpPillDirection({ followOn, … })` (`:322-329`). `ThreadView.tsx:260` is `const followOn = true`
  under a comment claiming the toggle "now lives in PlayerPane" — which was never true. `PlayerPane`
  (right dock) and `ThreadView` (center stage) are **siblings**, so local state in `PlayerPane` would
  recolor a button and change nothing. #169's acceptance names the hardcode explicitly, and
  `docs/specs/v0.2-youtube-annotation.md:318-321` defines follow as auto-scroll behaviour.
- **`rate` does not exist anywhere.** No `getPlaybackRate()` on `Player` (`src/shared/player.ts:10-23`).
  Pre-B5 it was local `useState(1)` + `RATES` + `cycleRate` in `ThreadView`, all deleted in `4ab51f0`.
- **`markers`** needs the thread's annotation timestamps, which `PlayerPane` does not have.

**Decision: add `yt/transportState.ts`, a small zustand store holding `{ followOn, rate, markers }`**,
following the existing `pendingJumpState.ts` / `excerptState.ts` / `dockStore.ts` pattern. `PlayerPane`
reads and writes; `ThreadView` reads `followOn` (replacing `:260`) and publishes `markers`. One
mechanism covers all three, and it survives `ThreadView` unmounting while the docked player keeps
playing — which is the entire point of B5.

**Rate sequence, literal, do not re-invent:** `const RATES = [1, 1.25, 1.5, 1.75, 2]`, cycling.

### 3.3 Tasks

- **B1 — `yt/transportState.ts`.** zustand store, `{ followOn: true, rate: 1, markers: [] }` +
  setters. New file, no existing consumer — the one genuinely simple task here.
- **B2 — mount `TransportBar` in `PlayerPane`.** `state`/`currentTime`/`duration` from
  `usePlayerState`; the five callbacks through the returned `player` handle; `followOn`/`rate`/
  `markers` from the store. `onRate` cycles `RATES` and calls `player.setPlaybackRate`.
- **B3 — `ThreadView` reads the store.** Replace `const followOn = true` (`:260`) with the store
  value, and publish markers: the memo deleted in `4ab51f0` is one line —
  `markerPositions(sorted, duration).map((m) => m.t)`. Fix the stale comment at `:257-259`, which
  documents a state of the world that never existed. Update the `:52` doc pointer per #169.
- **B4 — verify in real Electron.** happy-dom has no layout and no media element; a scrubber is
  geometry. Extend an existing `scripts/*.mjs` smoke. **Do not claim this fixed on unit tests alone**
  — that is precisely how #169 shipped.

Wiring markers here is what lets #169 actually **close**: `markers: []` would leave `markerPositions`
as orphaned as before and leave the issue's headline complaint untouched (#169 offers only "wire both"
or "delete both"), and it contradicts `docs/specs/v0.2-youtube-annotation.md:240-243` and `:317`.

## 4. Cluster C — PDF multi-line locator (#189)

`pdf/useExcerptCapture.ts:102-116`:

```ts
const fullText = await entry.page.getTextContent()
  .then((tc) => tc.items.map((i) => ('str' in i ? i.str : '')).join(' '))
const idx = fullText.indexOf(text)
```

Items join with a **space**; `sel.toString()` joins visual lines with a **newline**. Any multi-line
selection → `indexOf` returns `-1` → all four of `prefix`/`suffix`/`textStart`/`textEnd` dropped.
Confirmed against the committed fixture: a 4-span drag on page 3 of `multi-feature.pdf` yields
`"Third page\nA third page..."` with empty prefix/suffix.

The comment at `:109-111` explains `idx === -1` as the honest cross-page case. **Correct but
incomplete**, and its presence is why this went unnoticed — it makes a failing path look intended.
Fix the comment too.

### 4.1 Nothing consumes these fields yet — but the basis still matters

Verified: the only non-test, non-doc references to `textStart`/`textEnd` are the schema
(`shared/zod-schemas.ts:55-56`), the type (`shared/types.ts:39-40`), and the **write** site
(`useExcerptCapture.ts:115-116, 132-133`). **No production reader exists.** ADR 0059 is categorical:
*"`rect` is the primary anchor. Text selectors are advisory"* (`:24`), *"Full text-based re-anchoring
is deferred"* (`:63`).

So nothing breaks either way — but the choice is still not free, because the offsets are **persisted**.

### 4.2 Decision: raw basis, with an offset map

- **(A) normalized basis** — `textStart = idx` into the normalized string. Simple, but every
  already-persisted single-line locator indexes the *raw* `join(' ')`. Collapsing whitespace earlier
  in the page shifts them → two silently-mixed bases in persisted data with no version marker.
- **(B) raw basis — CHOSEN.** Normalize for *matching only*, map the match offset back to raw. Old
  rows stay comparable. This is what #189's own "Likely fix" asks for.

**The trap under (B):** `textEnd` **cannot** be `textStart + text.length` (the current `:116`),
because `text` is the raw selection carrying `\n` where page text has `' '`. Both ends need the map.

Build the normalized string with a parallel `srcIndex[]`, then
`rawStart = srcIndex[idx]`, `rawEnd = srcIndex[idx + normLen - 1] + 1`.

### 4.3 Tasks

- **C1 — the pure helper**, own file, own test. Its contract *is* the spec: collapse `/\s+/g` to a
  single space on both page text and selection, trim the selection, and emit `srcIndex[]` mapping
  each normalized char to its raw offset. ~15 lines plus its test.
- **C2 — wire it into `useExcerptCapture`**, using the raw offsets for `textStart`/`textEnd` and the
  raw string for `prefix`/`suffix` slices. **Do not touch `clientRectsToPdfRect` or `pdfRectToCssBox`**
  — ADR 0059 Consequences (`:140-142`) names that pair as load-bearing.
  (An earlier draft cited `computePdfRender` + ADR 0058 here; `computePdfRender` appears nowhere in
  ADR 0058. Corrected.)
- **C3 — the regression guard is already written.** `useExcerptCapture.test.ts:192-224`
  (*"PAGE-1 NO-REGRESSION… identical v0.6 locator"*, cited by `adrs/0058:121`) pins
  `textStart: 7 / textEnd: 24` on a single-spaced fixture where normalization is identity. **It must
  stay green untouched** — that is the cheapest signal the basis did not move. The cross-page test at
  `:280-309` also survives (a concatenated cross-page quote cannot match under any normalization).
- **C4 — real-Electron proof.** `scripts/pdf-multipage-smoke.mjs` *found* this bug; extend it to
  assert non-empty prefix/suffix on a multi-line drag. happy-dom cannot produce a real selection.

## 7. Testing — the non-negotiable part

**Every test must be observed failing before its fix exists.** v0.8 shipped ten tests provably
incapable of failing, caught only by mutating the implementation. This batch is unusually easy to
fake: a test that mocks `notes.create` to **resolve** and asserts the draft cleared passes against
the buggy code and the fixed code identically.

- **A** — component tests via `renderWithProviders` + `installMockApi`, `notes.create` mocked to
  **reject**. Assert: the textarea still holds the text, `onDraftClear` was **not** called, and the
  error is visible. Then a resolving case asserting the inverse.
  **Rejection is already expressible** — `App.test.tsx:739` does exactly
  `mockApi.notes.create.mockRejectedValue(new Error('create failed'))` inside *"B4: restores the
  excerpt when the create fails (no silent data-loss)"* (`:736`), structurally the same test.
  An earlier draft claimed the mock could not express rejection and made fixing `tests/setup.tsx` a
  prerequisite — **false, and now deleted.** `installMockApi` has ~35 test-file fan-in; changing its
  defaults could flip assertions elsewhere and has no business riding along in a data-loss batch.
  Where a resolved note is needed (the youtube path reads `created.id` at `ThreadView.tsx:529`), use
  a per-test `mockResolvedValue`, as `App.test.tsx:771` already does.
- **B** — unit tests may assert props wiring; only B4 proves the scrubber works.
- **C** — a unit test on the C1 helper with a real multi-line fixture string, the untouched C3 guard,
  and the extended smoke (C4).

Run only the changed file during the loop (`vitest run <file>`); lefthook is the authoritative gate.

## 9. Risk

Cluster A changes two exported prop types consumed by `ThreadView`. The realistic failure mode is
**fixing the clear and forgetting the error surface**, converting silent data loss into silent
*nothing happening* — still a bug, and one §7's tests catch only if they assert the error is
*visible*, not merely that the text survived.

Second-most-likely: A4a is skipped or reverted because A4 "looks fine" without it.

## 10. What comes after this batch

**Next milestone: semantic zoom** — top of the `docs/canvas-vision.md` queue since v0.6.2, deferred by
five consecutive amendments (v0.6.4, v0.7, v0.8, v0.8.1, and this batch). v0.8.2 jumped the queue only
because it is data loss.

The seam exists and is deliberately half-built: `canvas/lod.ts:8` defines
`LodTier = 'card' | 'title' | 'dot'` with `TIER_THRESHOLDS = { title: 0.5, dot: 0.15 }` and
`tierForZoom()`; v0.4 shipped the **card** renderer only. `canvas/dev-lod.ts` provides a DEV HUD that
force-selects a tier and unclamps zoom past the production `[0.5, 2.0]` range, so the empty tiers are
inspectable before a line is written.

Scope per `canvas-vision.md:115-123`: title + dot tiers on the underlay, zoom-threshold UX,
card⇄title⇄dot transitions under a **semantic-consistency invariant** (anything visible at a tier
persists at all deeper tiers), dot hit-testing with inflated radius + snap-to-nearest, labels on
hover/proximity at dot zoom. Strategic payload: the **dot tier doubles as the minimap and the
whole-vault lens** — notes without manual positions get *computed* positions there, not on the card
tier. Perf pre-cleared (v0.4.0 spike: 10k canvas-2D dots at 60fps; no WebGL).

**Two gates before starting, both easy to miss:**

1. **#96 (switchable arrangements)** — `memory/progress.md` flags it "evaluate before the next canvas
   milestone", and the dot tier is where that decision lands.
2. **#18 (esc-precedence)** — `canvas-vision.md:213` mandates a re-audit *every* canvas milestone;
   zoom tiers add modes.

**Semantic zoom needs the brainstorm step** (CLAUDE.md workflow step 1), unlike this batch. Real open
questions: what the title tier shows for a note with no title line, whether unplaced notes appear at
dot zoom at all, and whether the minimap *is* the dot tier or a separate surface.

After it, `canvas-vision.md:217`'s non-binding order: layout engine → canvas ink (Stage 3) → nested
canvases → multi-canvas → channels → **PDF annotation (Stage 2, blocked behind ink)** → layers. Two
bindings, both user-stated: PDFs after the node/edge/tab/pane workflow (cleared by v0.6.2–v0.6.5), and
**layers only after PDFs**.
